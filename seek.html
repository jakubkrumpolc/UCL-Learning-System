Where tables physically live, and the tricks (indexes and hashing) that find one row without reading them all.

Where data lives: memory vs. disk

A database has to live somewhere on the computer. The DBMS wants to store it so that reading it back costs as little time as possible.

Main memory (RAM)

Primary · Fastest · smallest · volatile: gone when the power goes

Solid-state drive (SSD)

Secondary · Flash memory · non-volatile · much faster than a hard disk

Magnetic hard disk

Secondary · Non-volatile · large and cheap · slow to read

Tape, archive drives, CDs

Tertiary · Archive: data that rarely changes or is rarely read

↑ faster and dearer per GB  ·  ↓ bigger and cheaper per GB

Primary storage

Where the computer works on data: main memory. Fast, but small and volatile.

Secondary storage

Where data is kept when not in use: hard disks and SSDs. Survives power loss.

Tertiary storage

Archives: data not expected to change, or even be read, very often.

Remember: the database lives on disk but is worked on in memory. Every trip to disk is the slow part.

More detail

The lecture opens with the reason storage matters: the contents of a database must physically sit on the computer, and we want to arrange them so that retrieving data spends as little time as possible reading. This overlaps heavily with operating systems: the same principles appear there, and many DBMSs deliberately replace the operating system’s default memory and file management with their own, tuned for database workloads.

Traditionally there are two kinds of storage. Main memory is fast but volatile: its contents disappear if the power is lost. Magnetic disk (hard drives) is non-volatile, though still subject to occasional failures and data loss. The more recent trend is flash memory and solid-state drives (SSDs): still non-volatile, much faster than spinning disks, but not quite as fast (or as expensive) as high-end main memory.

By role: primary storage is memory used for working and calculation (main memory); secondary storage keeps data while it isn’t being used (hard disks, SSDs); tertiary storage archives data that is no longer expected to change or even be read frequently (archive drives, tapes, CDs). The rest of the lecture assumes tables sit in secondary storage and must be brought into memory to be used.

Blocks: the unit the disk reads

Block

Fixed-length unit of storage: the smallest piece the disk can read or allocate. Usually about 4–8 KB.

Page

Fixed-length unit of data used in memory management. Often the same size as a block; sometimes not.

One row (record) is usually much smaller than a block, so the DBMS packs several records into each block.

Fixed-length records

  • Records per block known in advance
  • A new row can reuse a deleted row’s slot
  • Empty slots tracked in a free list

Variable-length records

  • VARCHAR, TEXT… make rows differ in size
  • A bit more bookkeeping
  • Still very feasible: see the next section

Remember: the disk never hands over “one row”. It hands over a whole block, so put rows that are read together in the same block.

More detail

A block is a fixed-length unit of storage and the smallest unit of data that can be read from or allocated on the disk, typically around 4–8 KB. A page is a fixed-length unit of data used in memory management. Both are fixed-size chunks; depending on the system the two words are sometimes synonyms and sometimes not.

Leaving aside large objects (images, files), a record in a relational table is typically much smaller than a block, so many records are packed into one block. There are two designs. If every field, and therefore every record, is fixed-length, storage is simple: the number of records per block is known in advance, and when order doesn’t matter a new record can simply fill the space of a deleted one. The empty slots are kept in a “free list”.

Variable-length fields (VARCHAR, TEXT and so on) mean records differ in size, which adds some complication but is very workable, as the slotted-page structure shows. Because the disk transfers whole blocks, the cost of a query is roughly the number of blocks it has to read.

Part 5 · Seek · Storage

Variable-length records: the slotted page

1

Each record gets two numbers: its offset (where it starts) and its length.

2

The header at the top of the block holds one slot per record with those numbers.

3

The records are packed from the bottom.

4

Both ends “eat” the block and meet in the middle: the gap is the free space.

Remember: header at the top says where, records at the bottom are what. They grow towards each other.

More detail

Records with variable-length fields can be handled by storing two pieces of metadata per record: its offset (location within the block) and its length (size). The slotted-page structure organises a block (or page) around this. The top of the block holds a header with the offset/length entry for every record in that block (plus the number of entries and where the free space ends). The records themselves are stored contiguously from the bottom of the block.

Storage is therefore consumed from both ends and meets in the middle. To insert a record, the DBMS adds a slot to the header and writes the record just above the existing ones; to delete one, it marks the slot empty and can slide the remaining records along to close the gap, updating their offsets. Anything outside the block only needs to remember the slot number, so records can move inside the block without breaking references to them.

Operating systems use the same technique. The diagram is a sketch; the lecture shows the idea in words, and textbooks (Silberschatz, Korth and Sudarshan) draw it the same way.

Buffers and dirty pages

Buffer

Anywhere that holds temporary copies of database data outside the main database, for reading or updating. Can be in memory or on disk.

Dirty page

A page in the buffer that has been changed but not yet written back to the database.

Flushing

Writing everything in the buffers to long-term storage, so all the temporary space is free again.

1

A query needs a page → it is copied from disk into the buffer.

2

An UPDATE changes the copy in memory → the page is now dirty.

3

The buffer is full → the DBMS picks a page not used recently to throw out.

4

If that page is dirty, it must be written to disk first, or the change is lost.

Remember: clean pages can just be dropped; dirty pages must be saved first.

More detail

“Buffer” has many meanings. Originally it is something that sits in front of something else and is interacted with instead of it; the usual computing meaning is temporary memory for data that is being processed or transferred elsewhere. In databases, a buffer is anywhere that stores temporary copies of data outside the main database, for reading or updating, whether in primary or secondary storage.

Buffers hold data temporarily loaded from the database. When space runs out, some pages that are not being (or not recently) used are overwritten. If such a page holds updated data (a dirty page), that data must first be written back to the database. Flushing the buffers means writing all data held in them to long-term storage, which clears them so the whole temporary space can be used again.

This is why a DBMS cares about memory management: keeping the right pages in memory saves disk reads, and writing dirty pages back at the right moment protects your updates (this links to transactions and recovery later in the module).

Part 5 · Seek · Indexing

The real problem: finding one row

  • Tables live on disk as records packed into blocks.
  • To answer a query, (parts of) the table must be loaded into memory.
  • Reading from disk is slow.
  • Tables are often much bigger than memory.

SELECT * FROM Staff
WHERE staffNo = 'SG37';

-- no help: read every block until SG37 turns up
-- with an index or hash: jump to its block

Two ways to jump straight to the row

Indexes: a sorted lookup structure (sections 15–20). Hashing: compute the address from the key (sections 21–23).

Remember: the goal of the rest of this lecture is fewer, smarter disk reads.

More detail

The summary slide restates the situation: tables are stored in secondary storage (“disk”) as a series of records, organised into blocks. Queries need (parts of) a table loaded into working memory before it can be returned or processed. Reading from secondary storage is slow and costly, and tables are often much larger than working memory.

So what if you want just one row? Without help, the DBMS would have to read block after block, scanning every record (a full table scan). The aim is to find the row with as few unnecessary disk reads as possible. The two techniques that follow are indexes, which keep a sorted structure of key values pointing at where the records are, and hashing, which calculates a storage location directly from the key.

Index of last names (nonclustered)

lastNameblocks

Allen7, 21, 24

Clustering / primary index

The attribute(s) that decide the physical order of the records on disk. Usually the primary key, but not necessarily.

Nonclustered / secondary index

An extra index on another attribute. It doesn’t match the storage order, so it points into blocks all over the table.

A table can be sorted one way only, so it has at most one clustered index, but as many secondary indexes as you like.

Remember: clustered = how the books stand on the shelf. Nonclustered = the catalogue that tells you which shelves to visit.

More detail

An index is a data structure that helps retrieve specific records in a table quickly (random access) instead of scanning. The lecture sorts index types along three axes: clustering vs nonclustered (also called primary vs secondary), dense vs sparse (for clustered indexes) and single-level vs multilevel.

A clustering (primary) index is on the attribute or set of attributes that determines the order in which records are physically stored. It is usually the primary key, but doesn’t have to be. In the slide’s example the records are stored sorted by userID, so block 1 holds aaa, aardvark, abcd…, block 2 card190, cats00, ccard… and so on.

A nonclustered (secondary) index is an additional index on some other attribute, which comes apart from the table’s intrinsic storage order. The index of last names says Adams is in block 2, Ahmad in blocks 1 and 10, Allen in blocks 7, 21 and 24: matching rows are scattered. Think of it as sorted vs non-sorted attributes: a table can only be stored sorted along one dimension (its clustered index), so every other search key needs a secondary index. In MySQL’s InnoDB engine the primary key is always the clustered index.

Dense vs. sparse indexes

Dense: every key

userIDblock
aaa1
aardvark1
abcd1
card1902
cats002
……

Sparse: one per block

userIDblock
aaa1
card1902
dray013
……

Dense

Every value of the indexed attribute has its own pointer. Bigger index, direct hit.

Sparse

Only some values have a pointer. Find the nearest entry at or below your key, go to that block, then read forward. Works only because the data is sorted.

So sparse indexes only make sense for clustered indexes. A secondary index must be dense. The usual compromise: one entry per block.

Remember: sparse only works when the data is sorted the same way as the index.

More detail

A dense index has a direct pointer for every unique value of the indexed attribute(s). A sparse index has pointers for only some of the values; to find a key that isn’t listed, you use the sort order: find the largest index entry that is less than or equal to the key, go to that position, and scan forward from there.

Example with the userID index: the sparse index lists aaa → block 1, card190 → block 2, dray01 → block 3. To find “cats00”, the largest entry ≤ “cats00” is card190, so read block 2 and look inside it. This only works if the records themselves are stored in userID order, which is why sparse indexes are only relevant to clustered indexes. A secondary index has no order to fall back on, so it must be dense to be usable.

The common compromise is a sparse index with one entry per block: it is small (one entry per few dozen records) yet still takes you straight to the right block, and you would have to read the whole block anyway.

Part 5 · Seek · Indexing

When the index is too big: multilevel

1

Load the index into memory and look up the key.

2

The index gives the exact block (dense) or a range (sparse).

3

Load just that block from disk.

4

Index too big for memory? Build a sparse index of the index.

5

Repeat as needed: the layers form a tree. Keep the root in memory.

Remember: an index of an index is a tree. Keep the root in memory and each level costs one disk read.

More detail

To find a search key: load the index, look through it in memory for the entry you need, which tells you the exact location in secondary storage (dense) or a range (sparse), then load that block (or blocks) from disk. If the index is small enough, the DBMS can keep it in memory permanently and reuse it for later lookups.

If the index itself is too large to keep comfortably in memory, build another, sparse, index over the index records: it gives the addresses of the blocks that store each range of index entries (A–B, C–E, F–H…). From this “index of the index” you can load exactly the one index block you need. Add more layers as needed; the result is a tree, and keeping its root in memory at all times means each lookup reads one block per level.

Example: with 1,000,000 index entries and 200 entries per block, the bottom level has 5,000 blocks, the next level 25 blocks, and a single root block covers those 25. Any key is found with about 3 block reads.

Part 5 · Seek · Indexing

B+ trees: short and fat

Balanced

Every leaf is the same distance from the root, so there is a guaranteed upper bound on depth. Insert, update and delete keep it balanced in logarithmic time.

Short and fat

Each node is one block, packed with as many keys and pointers as fit (often hundreds). So the tree is only 3–4 levels deep even for millions of rows.

Leaves are the records

The bottom level holds the actual rows, kept in sorted order and linked left to right, so ranges and ORDER BY are cheap.

Remember: B+ tree = a multilevel index that keeps itself balanced and sorted, with one block per node.

More detail

A B+ tree is one of many balanced tree data structures. Balanced trees guarantee an upper bound on the depth of the tree, and they come with specialised insert, update and delete algorithms that keep the tree balanced in logarithmic time.

B+ trees differ from other balanced trees (such as binary search trees) by being “short” and “fat”: each node is block-sized and is packed with as many pointers to other blocks as will fit. With hundreds of children per node, three or four levels cover millions of records, so a lookup needs only three or four block reads.

In the lecture’s description, the leaves of the B+ tree are the records of the database, which are different from the interior index nodes. The B+ tree also manages how records are placed in blocks on disk so the table stays in sorted order as items are inserted and deleted. The diagram uses the six staffNo values sorted as text (SA9 < SG14 < SG37 < SG5 < SL21 < SL41); real nodes hold hundreds of keys, not one. To find SG5: at the root SG5 ≥ SG37, go right; at SL21, SG5 < SL21, go left; read that leaf. MySQL’s InnoDB stores every table as a B+ tree on its primary key, which is why lookups and ranges on the primary key are fast.

Hashing: compute the address

h( search key ) → bucket address

1

Feed the search key into the hash function.

2

It returns a storage location (a bucket).

3

Store the record there…

4

…and later look in the same place to find it again.

Toy hash: number part mod 4

staffNodigitsmod 4bucket
SG373737 mod 41
SG141414 mod 42
SL212121 mod 41
SA999 mod 41

A good hash function is…

Deterministic

The same key must always give the same address.

Total

It gives an answer for every possible key.

Uniform

It spreads keys evenly across the buckets.

Fast

Quick to calculate, or the shortcut isn’t worth it.

Remember: an index looks the key up; a hash works the address out.

More detail

Hashing is an alternative storage and retrieval system that allows (near) instantaneous insert, update and delete. A hash function takes the search-key value as input and outputs an address. Because the function is deterministic, you can compute where a record goes, store it there, and later compute the same location to retrieve it, with no index to search.

An ideal hash function for database storage has four properties: deterministic behaviour (the same search key sent in twice must give the same output); it gives an answer for every possible search key; it distributes keys over the available storage as uniformly as possible; and it is quick to calculate.

The toy function in the table takes the number in the staffNo and uses the remainder after dividing by 4 (mod 4). It is deterministic, total and fast, but not very uniform: SG37, SL21 and SA9 all land in bucket 1. Real systems use better-mixing functions. When too many keys land in one bucket, you need an overflow strategy, which is the next section.

Part 5 · Seek · Hashing

When a bucket is full: overflow

Open hashing

The key always goes to its own bucket. Extra records go into overflow buckets chained on with a linked list. Needs a second structure besides the table.

Closed hashing

Overflow is pushed into another bucket, e.g. the next free one (linear probing). Where a key ends up depends on what was already in the table.

What databases use

The linked-list (open hashing) kind, because deleting is easy: you never have to worry that a later key was pushed past the one you remove.

Remember: open hashing = queue behind your own door. Closed hashing = take the next free door.

More detail

Sometimes the hash function assigns more items to a bucket than it can hold: bucket overflow. There are two strategies, with confusingly opposite names.

Open hashing uses an extra structure, such as a linked list of overflow buckets, to give a full bucket more room. Every key is definitely stored at the location the hash function gave (so it is also called closed addressing), but you need a secondary data structure besides the hash table itself (hence open hashing). In the slide, address 18 is full and so is its first overflow bucket, so the new record goes in a third bucket on the chain.

Closed hashing uses a rule such as linear probing to choose another hash location for the overflow item: if 18 is full, try 19; if 19 is full, try 20. Keys are therefore not necessarily stored where the hash function says (open addressing), and where a key ends up depends on the contents of the table at the time. Deletion becomes awkward, because removing a key can break the probe path to keys stored after it. That is why the linked-list type is the one commonly used in databases.

Part 5 · Seek · Summary

Index or hash? Pick by the query

Clustered index (B+ tree)Hashing
OrderStored sorted: ranges and ORDER BY are easyStored in random order: ranges and sorting are hard
CostO(log n) per operationO(1) in the typical case
RobustnessOne implementation suits any dataDepends on a good hash function; a change in the key distribution can hurt it

Which one?

WHERE staffNo = …

Exact match on a key: hash is ideal; an index is fine too.

WHERE salary BETWEEN …

Range, or ORDER BY: index. A hash can’t help.

Remember: hash for “exactly this one”, index for “everything between these”.

More detail

The lecture’s comparison: with a clustered index the data is stored in sorted order, so reading data in ranges or in sorted order is simple; operations cost O(log n); and a single implementation works for any type of data. With hashing the data is stored in effectively random order, so ranges and sorted reads are non-trivial; operations are O(1) in the typical case; and performance depends on choosing a good hash function, so a change in the distribution of search keys can change how well it performs.

The concepts from this lecture set up how a DBMS processes queries (coming next): primary vs secondary storage and their trade-offs; packing records into pages or blocks; and the two kinds of search aid, indexes (direct pointers to where data is, in various types, implemented as multilevel B+ trees) and hashing (a repeatable mapping from search key to storage location, giving near-instant lookup from the value itself).

In MySQL: CREATE INDEX idx_lname ON Staff(lName); adds a secondary B+ tree index (InnoDB’s default). The MEMORY engine can use HASH indexes. EXPLAIN SELECT … shows whether a query uses an index.
