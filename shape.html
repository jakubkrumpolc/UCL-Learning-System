From idea to tables in four steps

1

Requirements

What data, who uses it, what must the app do?

2

Conceptual design

ER diagram: things, links, properties. No tech limits yet.

3

Logical design

Turn the diagram into tables and keys; normalise.

4

Physical design

CREATE TABLE in MySQL: types, indexes.

Top-down

Draw the ER diagram, then translate it into tables (sections 49–50).

Bottom-up

Start from one big table of everything, then normalise it (sections 52–57).

Coursework

50% of the module: your own SQL database. ER diagram due end of Week 3.

Remember: draw it, table it, tidy it.

More detail

Before designing anything you gather requirements: what data will be used, who will use the system, and which features it needs. For the coursework, the brief already does most of this for you. Design then has two main steps. Conceptual design uses ER modelling and diagrams; it is “blue-sky thinking” where the only limits come from the data itself, not from any technology.

Logical design adds the constraints of the chosen kind of database; for a relational database that means deciding every table, and it is still independent of any particular DBMS product. There are two strategies for logical design: top-down (translate the ER diagram into tables using fixed rules) and bottom-up (start from one big table holding all the interesting data, and normalise it). In practice you do both: translate first, then check the result with normalisation.

The final step, physical design, is writing the actual MySQL: data types, CREATE TABLE statements, indexes. From the Week 1 lecture: coursework is worth 50%, groups and peer-marking criteria are finalised by the end of Week 2, and the ER diagram for your project is due at the end of Week 3.

Remember: boxes = things (entities) · lines = how they relate · text inside = their properties.

More detail

The conceptual model is a picture of all parts of the database: what the data is and how pieces relate. The entity–relationship (ER) model describes everything as one of three things. An entity is a thing (not necessarily physical: a Viewing or a Lease is an entity too). A relationship is a connection between two or more entities. An attribute is a property describing an entity or a relationship. This module draws ER diagrams in UML (Unified Modeling Language) style.

Entities are rectangles with UpperCamelCase names; attributes are listed underneath in lowerCamelCase. Relationships are lines between entities with an UpperCamelCase name and a small arrow showing which way to read it: Staff ◂Has Branch reads “Branch has Staff”. Attribute types: a candidate key uniquely identifies an instance ({CK}); the primary key is the candidate chosen as THE identifier ({PK}, or simply listed first); a composite key is made of several attributes, each marked {PPK}.

A composite attribute is made of smaller pieces (address = street, city, postcode), drawn indented. A multi-valued attribute holds a list of values of the same type, with its allowed count, e.g. telNo [1..3]. A derived attribute can be calculated from others, marked with a slash (/monthlySal = salary / 12), and doesn’t need to be stored. The numbers at the ends of the line are multiplicities (next section).

Multiplicity: how many can be linked?

Staff

Manages

1..1

0..*

Property

Fix ONE Staff member → read the Property end

0..* : manages zero or more properties.

Fix ONE Property → read the Staff end

1..1 : managed by exactly one staff member.

WriteMeans
0..1zero or one
1..1 or 1exactly one
0..* or *any number
1..*at least one

Lower bound = participation: 0 optional, 1+ mandatory.

Upper bound = cardinality: 1 or many (*).

Remember: the number sits next to the thing being counted.

More detail

Structural constraints are properties of entities and relationships that must always be true. The main one shown on an ER diagram is multiplicity: how many occurrences of one entity may be related to a single occurrence of the other. It is written as a range min..max at each end of the relationship line. The lecture’s rule: given a single, fixed entity at the FAR end, the range at the NEAR end says how many near entities can be related to it.

So 0..* next to Property means one Staff member manages zero or more Properties; 1..1 next to Staff means one Property is managed by exactly one Staff member. Shorthand: 1..1 can be written 1, and 0..* can be written *; * means no upper bound. Multiplicity has two parts. The upper bound is the cardinality (one or many). The lower bound is the participation: 0 means optional participation (a staff member doesn’t have to manage anything), 1 or more means mandatory participation (every property must have a manager).

A good way to find the numbers: for each relationship, ask the two questions on the left out loud, using your own requirements. The annotated lecture adds an example of “1:3”: one staff member associated with up to 3 branches would be written 0..3 or 1..3 at the Branch end.

More detail

For relationships between two entities (binary relationships, degree 2), the possible multiplicities fall into three types, judged only by the upper bounds (cardinalities), not by participation. One-to-one (1:1): each entity on either side is associated with at most one entity on the other side, like a branch and its manager. One-to-many (1:*): one “subject” entity can be linked to many “object” entities, but each object has at most one subject, like a staff member and the properties they manage.

Many-to-many (*:*): entities on both sides can be linked to many on the other, like newspapers and the properties they advertise. A semantic net is NOT the same as a UML/ER diagram: the ER diagram shows generic entities and relationships, while a semantic net draws a few sample instances (dots) and their links (lines). Use one when you are unsure of a multiplicity: draw some realistic example data and see whether any dot needs more than one line.

In the first net, SG37 has no line, which shows that participation on the Staff side is optional (0..1). In the second, SG14 has two lines, so one staff member can manage many properties. In the third, both sides have dots with several lines. Each type is turned into tables differently (section 49): 1:* adds a foreign key; *:* needs a new table.

Remember: diamond for 3 or more · role names on loops · dashed box for facts about the link.

More detail

The degree of a relationship is how many entities take part in it. Most are binary (degree 2); degree 3 is ternary and degree 4 is quaternary. For degree 3 or more, put the relationship name in a diamond and connect it to every entity involved. You can no longer use a reading arrow, so add a sentence underneath: “Staff registers a client at a branch”. The lecture’s quaternary example: “A solicitor arranges a bid on behalf of a buyer, supported by a financial institution”

(Solicitor, Buyer, FinancialInstitution, Bid around an Arranges diamond); if any one of the four is missing, it is not a valid instance of the relationship. Reading multiplicities on a ternary: fix one instance of each of the OTHER entities, then the number at the near end says how many are allowed. Staff 1, Branch 1, Client *: for one staff member at one branch, any number of clients; for one client at one branch, exactly one staff member registered them.

Role names are labels at the ends of a line that say what part each entity plays. They are essential for recursive relationships (an entity related to itself, like Staff Supervises Staff, where one end is the supervisor and the other the supervisee) and helpful when two entities share several relationships (Staff Manages Branch and Staff WorksAt Branch). Relationship attributes describe the link itself rather than either entity: when a client viewed a property, and their comment.

They are drawn as a box joined to the relationship line by a dashed line. Later they become columns of the table that represents the relationship (Viewing).

Inheritance: one parent, special children

Staff

staffNo {PK}
name
salary

{Optional, And}

Manager

bonus

SalesPersonnel

salesArea

Secretary

typingSpeed

Mandatory or Optional?

Must every Staff member be in a subclass?

Mandatory = yes · Optional = no

And or Or?

Can one Staff member be in two subclasses?

And = yes · Or = at most one

Turning it into tables: pick by the label

{Mandatory, And}

One table holding everything, with yes/no flags.

{Mandatory, Or}

One table per subclass, Staff columns copied in.

{Optional, And}

Staff table + one shared subclass table with flags.

{Optional, Or}

Staff table + one table per subclass (FK → Staff).

Remember: Mandatory/Optional = must they join? · And/Or = can they join more than one?

More detail

Enhanced ER (EER) modelling adds object-oriented ideas to ER diagrams. Inheritance: a child class (subclass) automatically receives all of its parent’s (superclass’s) attributes and relationships, and adds its own. Specialisation is the top-down way of finding subclasses: look for differences between kinds of a thing and split it. Generalisation is the bottom-up way: notice what several entities have in common and pull it out into a parent.

Example from the lecture: all staff have a number, a name and a salary; managers also have a bonus, sales staff a sales area (and a car allowance), secretaries a typing speed. In UML, draw a line from each subclass to the superclass with a hollow arrowhead pointing at the parent, and write the constraints in curly brackets on the line. There are two constraints. Participation: must every superclass member also belong to at least one subclass (Mandatory) or not (Optional)?

Disjointness: may a member belong to more than one subclass (And, called nondisjoint) or to at most one (Or, disjoint)? So the four combinations mean: Mandatory Or = exactly one subclass; Optional Or = zero or one; Mandatory And = at least one; Optional And = any number. Here {Optional, And} means a plain assistant is just Staff, and one person could in principle be both a Manager and a Secretary.

The four cards at the bottom are the lecture’s recommended table designs for each label; you will use them in logical design. Flags are yes/no columns such as isManager. With one big table, columns that don’t apply to a row are simply left NULL.

How to draw your own ER diagram

1

Nouns → entities

Branch, Staff, Property, Client become boxes.

2

Verbs → relationships

“has”, “manages”, “views” become named lines.

3

Attributes and a primary key

List what you store about each; mark the {PK}.

4

Multiplicities at both ends

Ask both ways: one A links to how many B?

5

Facts about a link go on the link

viewDate belongs to Views, not to Client.

6

Check with example data

Sketch a semantic net; fix any number that breaks.

Try it on a brief

“Each branch has several staff. A staff member manages properties. Clients view properties, and we record the date.”

Branch 1..1 —Has— 1..* Staff
Staff 1..1 —Manages— 0..* Property
Client 0..* —Views— 0..* Property
        └ viewDate

Draw it in draw.io (free), Lucidchart or MySQL Workbench, or on paper first.

Remember: nouns → boxes · verbs → lines · questions → numbers.

More detail

This is a practical recipe for the coursework ER diagram (and any lab that asks you to model a scenario); it is not a lecture slide but applies the lecture’s notation. 1) Read the brief and underline the nouns: things you need to store several of, each with its own details, are entities.

Watch for nouns that are really just attributes (a “date” or a “price” describes something else). 2) Circle the verbs that connect two nouns: they become relationships, named in UpperCamelCase with a reading arrow. 3) For each entity, list the attributes you need and choose a primary key. If nothing natural is unique, invent an ID (staffNo, clientNo).

Mark composite, multi-valued and derived attributes with the notation from section 42. 4) For every relationship ask the two multiplicity questions: “for one A, how many B: at least? at most?” and the same the other way round. 5) If a piece of data only makes sense when two things are linked (when a client viewed a property, their comment), it is a relationship attribute; draw it in a dashed-line box. 6) Check by inventing a few realistic rows and drawing a semantic net: if a dot needs more lines than your multiplicity allows, the number is wrong.

Tools: draw.io (diagrams.net) is free in the browser and has UML class shapes; Lucidchart is similar; MySQL Workbench can also draw a diagram from tables you have already created (Database → Reverse Engineer), which is a good way to check your SQL matches your design.

More detail

This is one possible answer to the design lab’s conceptual question (a chatroom system). Work through the brief with the recipe from the previous section. Nouns that need their own details: Space, Channel, User, Message, so four entities. Verbs: users belong to spaces, spaces consist of channels, users join channels, users post messages, channels consist of messages.

Multiplicities: a space has at least one member (its creator), and a user can be in any number of spaces; a space has one or more channels, each channel belongs to exactly one space; a message has exactly one author and sits in exactly one channel. Facts that need two things: a user’s role depends on which space we mean (moderator in one, plain member in another), so role is an attribute of the BelongsTo relationship, with values member, moderator or admin; the creator is the one admin.

Muting is per user AND per channel, so muted belongs on Joins. Channel order: position on Channel (it could also be an attribute of Contains). Permissions: viewRole and postRole on Channel hold the lowest role allowed, so “mod announcements” has viewRole = member and postRole = moderator, and “moderator discussion” has viewRole = moderator.

Alternatives that are also fine: a separate Creates relationship (User 1..1 to Space 0..*) and a Moderates relationship instead of the role attribute; a Role entity if roles get complicated; displayName on BelongsTo if users can use a different name in each space. When this is translated to tables (next sections), BelongsTo and Joins are *:* so they become their own tables: Membership(userId, spaceId, role) and ChannelMember(userId, channelId, muted).

The 1:* relationships become foreign keys: Channel.spaceId, Message.userId, Message.channelId.

Turning a diagram into tables: 3 core rules

1

Each entity → a table

Split composites into parts; leave out derived attributes.

Branch(branchNo, street,
  city, postcode)

2

1:* → FK on the many side

Staff registers many Clients, so Client gets staffNo.

Client(clientNo, fName,
  lName, staffNo)

3

*:* → a new linking table

Both PKs together make its PK, plus any link attributes.

Viewing(clientNo, propertyNo,
  viewDate, comment)

-- rule 3 in SQL. Above: bold = primary key, purple = foreign key
CREATE TABLE Viewing (
  clientNo VARCHAR(5), propertyNo VARCHAR(5), viewDate DATE, comment VARCHAR(200),
  PRIMARY KEY (clientNo, propertyNo),
  FOREIGN KEY (clientNo)   REFERENCES Client(clientNo),
  FOREIGN KEY (propertyNo) REFERENCES Property(propertyNo));

Remember: the foreign key lives with the many. Many-to-many gets its own table.

More detail

Logical design turns the ER diagram into a set of tables (a relational schema) with primary and foreign keys. Rule 1, entities: every strong entity becomes a table whose columns are its simple attributes. Composite attributes are flattened into their parts (address becomes street, city, postcode). Derived attributes (/monthlySal) are usually not stored, because the database can calculate them in a query. Multi-valued attributes can’t go in one cell; they get their own table (next section).

Rule 2, one-to-many: the “1” side is the parent and the “many” side is the child. Copy the parent’s primary key into the child’s table as a foreign key, plus any attributes of the relationship. Staff 1..1 Registers 0..* Client becomes Client(clientNo, fName, lName, telNo, staffNo). It can’t go the other way, because one staff row would need a list of clientNos. Rule 3, many-to-many (and complex relationships of degree 3+): create a new table for the relationship itself.

It holds a foreign key to each participating table; together they form its primary key; relationship attributes become its other columns. Client *:* Property with viewDate and comment becomes Viewing(clientNo, propertyNo, viewDate, comment). With PRIMARY KEY (clientNo, propertyNo), a client can view each property only once; if repeat viewings are allowed, add viewDate to the key or give the table its own viewingId.

In MySQL, write foreign keys as separate FOREIGN KEY … REFERENCES lines as above: InnoDB ignores a REFERENCES clause written inline after a column. After translating, check the result with normalisation (sections 52–56).

The special cases

1:1, mandatory both sidesMerge into one tableUser + UserPreferences → one User table
1:1, mandatory one sideFK goes in the mandatory (forced) sideBranch(branchNo, …, mgrStaffNo)
1:1, optional both sidesPick a parent; FK goes in the otherParent = the side that takes part less

Weak entity: can’t exist without its owner. A Preference means nothing once its Client is gone.

Ternary PK: lean on the “many” end. Registration’s PK is clientNo.

Remember: lists and three-way links get their own table; loops get a second key.

More detail

One-to-one relationships are the awkward case, because it isn’t obvious which side is the parent, so the lecture uses participation to decide. Mandatory on both sides (every instance on each side must be paired): combine both entities and any relationship attributes into one table and use one of their PKs, e.g. if every user must have exactly one preferences record, just put the preference columns in User.

Mandatory on one side: the optional participant is the parent and the forced one is the child, which gets the FK, exactly like 1:*. Every branch must have a manager but most staff don’t manage a branch, so Branch gets mgrStaffNo; the FK can also act as the child’s key. Optional on both sides: choose either as parent (preferably the one where fewer instances take part) and put its PK in the other as an FK. Recursive relationships relate rows of a table to other rows of the same table.

With mandatory participation, add a second copy of the PK under a new name (supervisorNo references staffNo in the same table); with optional participation on both sides, create a new table with two copies of the PK, such as Supervision(staffNo, supervisorNo). Multi-valued attributes go in a new table with the owner’s PK as an FK and one row per value: BranchTelephone(branchNo, telNo).

A weak entity depends on another entity to exist (a user’s preferences, a client’s requirements) and often has no key of its own; it still becomes a table, and its PK is decided after the others, usually the owner’s PK plus a distinguishing attribute. Complex relationships (degree 3+) become a table with every participant’s PK; for its own PK, favour the PK of the entity with the “many” (*) multiplicity, so Registration(clientNo, branchNo, staffNo, dateJoined) uses clientNo.

Super/subclasses use the four strategies on section 46.

More detail

This is one reasonable answer to logical design question 1; compare it with the posted solution, because translation sometimes has more than one defensible result. Work through the diagram one element at a time using sections 49–50 and 46. Instructor is a plain entity: its own table, with email marked UNIQUE because it is a candidate key {CK}.

Class is a superclass with {Mandatory, Or}: every class is exactly one subclass, so the lecture’s recommendation is one table per subclass, each carrying the superclass’s columns (classCode, title, description, cost) plus its own. MultisessionClass 1 Has * Session is one-to-many, so the FK goes on the many side: Session gets classCode referencing MultisessionClass.

DayClass 1 Occurs 1 Session is one-to-one with 1 at both ends, i.e. mandatory on both sides, so the rule says merge: a day class’s single session (day, time, location) becomes columns of DayClass, and the Session table only holds sessions of multisession classes. The catch: classCode in TaughtBy may name a MultisessionClass or a DayClass, and a MySQL foreign key can only reference one table. You can still store it (and make sure class codes are unique across both tables), or choose a design with a Class table holding the shared columns and two subclass tables that reference it, which gives TaughtBy a single table to point at.

The alternative for Occurs keeps Session for both kinds of class and puts sessionID in DayClass as an FK; that also follows the 1:1 rules if you treat the Session side as optional.

Why tidy tables? Anomalies

ViewingLog · PK = clientNo + propertyNo · orange = the same fact stored again

clientNocNamepropertyNopAddressstaffNostaffNameviewDate
CR56Aline StewartPA1416 HolheadSA9Mary Howe2025-05-24
CR56Aline StewartPG46 Lawrence StSG14David Ford2025-05-26
CR56Aline StewartPG362 Manor RdSG37Ann Beech2025-04-28
CR62Mary TregearPA1416 HolheadSA9Mary Howe2025-05-14
CR76John KayPG46 Lawrence StSG14David Ford2025-04-20

Update anomaly

Aline changes surname: 3 rows to edit. Miss one and CR56 has two names.

Insert anomaly

A new property with no viewings can’t be added: clientNo is part of the key.

Delete anomaly

Delete CR76’s only viewing and John Kay disappears too.

Remember: store each fact once. Repeats are where anomalies breed.

More detail

Normalisation is the bottom-up route to a good design, and also the check you run after translating an ER diagram. Its goal, in the lecture’s words, is to minimise unnecessary duplicated data, because duplicates cause update anomalies. This table logs property viewings in one place. It is legal (every cell holds one value, and clientNo + propertyNo identifies each row), but facts are repeated: Aline Stewart’s name is stored three times, and the address and manager of PA14 and PG4 are stored twice each.

Three things go wrong. Update anomaly: the same fact lives in several rows, so a change must be made everywhere; if one row is missed the data contradicts itself (the lecture: “inconsistent data when data is updated in one storage location and not another”). Insert anomaly: you can’t record a fact until an unrelated fact exists; a property nobody has viewed has no clientNo, and a primary key column can’t be NULL.

Delete anomaly: deleting one fact removes another by accident; John Kay has one viewing, so deleting it also deletes the only record that he is a client (the lecture: “unintended loss of data”). The cure is to split the table so each fact is stored once, using functional dependencies (next sections) to decide where to cut, and checking that joins on the foreign keys rebuild the original rows exactly (the lossless-join property) and that every rule can still be enforced (dependency preservation).

Functional dependencies: what decides what

A → B

Fix the value of A, and B can only have one value. “A decides B.”

staffNo → fName: SG37 is always Ann.

fName ↛ staffNo: two staff could both be Ann.

It must hold for any possible data, not just today’s rows.

Full · needs the whole key

(clientNo, propertyNo) → viewDate

Partial · part of the key is enough · breaks 2NF

clientNo → cName

Transitive · via a middle-man · breaks 3NF

propertyNo → staffNo → staffName

Examples from ViewingLog on the previous section.

More detail

A functional dependency (FD) is a rule about the meaning of the data. For attributes (or sets of attributes) A and B, A → B (“A functionally determines B”) means each value of A is associated with exactly one value of B. staffNo → fName holds: once you know the staff number, the first name is fixed. fName → staffNo does not hold (written fName ↛ staffNo), because two people can share a first name.

The lecture stresses that an FD must hold in theory, not just in one snapshot of the table: even if no two current staff share a full name, staffNo → fullName holds but fullName ↛ staffNo, because a duplicate name is possible. Three kinds matter for normalisation. Full: B depends on the whole of A, e.g. a viewing date needs both the client and the property.

Partial: when the key is composite, some column depends on only part of it, e.g. a client’s name depends only on clientNo; partial dependencies are what 2NF removes, so they can only occur when the PK has more than one column. Transitive: A → B and B → C, where B is not a key (B doesn’t decide A), so C depends on the key only through the “middle-man” B; e.g. a property decides its manager’s staffNo, and the staffNo decides the staff name; 3NF removes these.

The lecture’s own transitive example: (propertyNo, inspectionDate) → staffNo and staffNo → staffName. Practical tips from the lecture: keep the left side minimal, skip dependencies that are just two simpler ones chained together, and ignore trivial ones like A → A.

Lab 2: what decides what in LibraryRental?

LibraryRental(transactionID, renterID, renterName, rentalDate, dueDate, loanItemID, loanItemMedia, homeLibrary)

The dependencies

transactionID → all other columns (the PK)

renterID → renterName, homeLibrary

A renter has one name and one home library.

loanItemID → loanItemMedia

An item is a book or a DVD, whoever borrows it.

rentalDate, loanItemMedia → dueDate

Only if the loan length is fixed per media type.

Assumed: homeLibrary belongs to the renter.

So: 2NF yes, 3NF no

One-column key, so nothing depends on part of it. But renterName hangs on renterID, a middle-man.

Rental(transactionID, renterID,
  loanItemID, rentalDate, dueDate)
Renter(renterID, renterName,
  homeLibrary)
LoanItem(loanItemID, loanItemMedia)

Remember: one-column key? 2NF comes free. Go hunting for middle-men.

More detail

This is a worked answer to the design lab’s logical question 2. Method: for each column, ask “if I fix this, what else is fixed?”, using what the names mean in a real library rather than any sample rows. transactionID is the primary key, so it decides every other column. renterID decides renterName, because a renter has one name; it also decides homeLibrary if that means the library the renter is registered at.

If homeLibrary instead means the library an item belongs to, then loanItemID → homeLibrary; state your assumption in an answer, as either reading is defensible. loanItemID decides loanItemMedia (each item is one kind of media). dueDate is usually decided by the transaction alone, but if the library has a fixed loan period per media type (say 21 days for books, 7 for DVDs), then rentalDate and loanItemMedia together decide it; that is a business rule you would confirm with the client.

Note what does NOT hold: renterName ↛ renterID (two renters can share a name), and rentalDate ↛ renterID. Consequences: the key is a single column, so there can be no partial dependencies and the table is already in 2NF. But renterID → renterName and loanItemID → loanItemMedia are transitive dependencies (transactionID → renterID → renterName), so it is not in 3NF; a renter’s name is repeated on every rental and an item’s media type on every loan, which allows update anomalies.

Splitting off Renter and LoanItem, with renterID and loanItemID left in Rental as foreign keys, gives 3NF. If you keep the dueDate rule, a strict 3NF design would also compute dueDate rather than store it.

Part 3 · Shape · Normalisation

The normal-form staircase

1NF

One value per cell

Fix: flatten lists into rows, or give the list its own table.

✗ telNo = '0207…, 0779…'
✓ one row per number

2NF

Nothing depends on part of the key

Fix: move it out with that part of the key.

Lease(clientNo, propNo, cName, …): cName moves to Client

3NF

Nothing depends on a non-key column

Fix: move the middle-man and what it decides to a new table.

staffNo → staffName moves to Staff

BCNF

not examinable

Every decider is a candidate key

Rarely differs from 3NF: only with overlapping composite keys.

Teaching(pupil, subject, teacher): teacher → subject

Remember: the key (1NF), the whole key (2NF), and nothing but the key (3NF), so help me Codd.

More detail

Normal forms are levels of tidiness, and each one includes all the ones below it: a table in 3NF is also in 1NF and 2NF, and BCNF implies 3NF. They only apply to relational tables. Unnormalised form (UNF) has no rules. 1NF: every cell holds a single value; no lists or repeating groups (a multi-valued attribute or a repeated set of columns like item1, item2, item3).

Two equivalent fixes from the lecture: flatten the list into several rows (copying the other data), or move the list to its own table keyed by the original table’s PK, one row per value. 2NF: no non-key column is fully determined by only PART of the primary key (no partial dependency), so it only needs checking when the key has more than one column. Fix: for each such dependency, create a new table with that part of the key and the columns it determines, and remove those columns from the original.

The lecture example: Lease(clientNo, propNo, cName, address, leaseStart) becomes Client(clientNo, cName), Property(propNo, address) and Lease(clientNo, propNo, leaseStart). 3NF: no non-key column depends on the key only through another non-key column (no transitive dependency). Fix: if A → B and B → C, move B and C into their own table with B as its key, and keep B in the original table as a foreign key.

Lecture example: (propertyNo, inspectionDate) → staffNo and staffNo → staffName, so staffName moves to a Staff table. BCNF (marked not examinable in the annotated slides): the left side of every FD must be a candidate key. It only bites when a table has two overlapping composite candidate keys.

Teaching(pupil, subject, teacher), where each teacher teaches one subject, has keys {pupil, subject} and {pupil, teacher} plus teacher → subject; the fix is Teaching(pupil, teacher) and TaughtSubject(teacher, subject), at the cost of no longer being able to enforce (pupil, subject) → teacher. The memory line is a play on the courtroom oath; E. F. Codd invented the relational model.

Worked example: ViewingLog to 3NF

1NF: one big table

ViewingLog(clientNo,
  propertyNo, cName,
  pAddress, staffNo,
  staffName, viewDate)

cName needs only clientNo; pAddress, staffNo and staffName need only propertyNo.

2NF: split by key part

Client(clientNo, cName)
Property(propertyNo,
  pAddress, staffNo,
  staffName)
Viewing(clientNo, propertyNo,
  viewDate)

Still: staffName depends on staffNo, a middle-man.

3NF: split the middle-man

Client(clientNo, cName)
Property(propertyNo,
  pAddress, staffNo)
Staff(staffNo, staffName)
Viewing(clientNo, propertyNo,
  viewDate)

Each fact once. Joining on the FKs rebuilds ViewingLog exactly.

Remember: 2NF: split by part of the key. 3NF: split by the middle-man.

More detail

This follows the ViewingLog table from the anomalies section through each normal form; bold columns form each table’s primary key. Start: it is already in 1NF (one value per cell) with the composite key (clientNo, propertyNo).

List the FDs: clientNo → cName; propertyNo → pAddress, staffNo; staffNo → staffName; (clientNo, propertyNo) → viewDate. 1NF to 2NF: cName depends on only part of the key (clientNo), and pAddress and staffNo depend on only the other part (propertyNo); staffName comes along with them, since it depends on propertyNo through staffNo.

So make Client(clientNo, cName) and Property(propertyNo, pAddress, staffNo, staffName), and leave Viewing(clientNo, propertyNo, viewDate) holding only what needs the whole key. 2NF to 3NF: Property still has propertyNo → staffNo → staffName, a transitive dependency. Move staffNo and the column it decides into Staff(staffNo, staffName) and keep staffNo in Property as the foreign key.

Check the result: each fact is now stored once (Aline’s name once, Mary Howe’s name once), so the update, insert and delete anomalies are gone: a property can exist without viewings, deleting a viewing doesn’t delete a client, and renaming a member of staff touches one row. Lossless join: Viewing JOIN Client JOIN Property JOIN Staff on the foreign keys gives back exactly the original rows.

Notice that this is the same schema you would get by drawing the ER diagram (Client, Property, Staff entities; Viewing as a *:* relationship with viewDate) and translating it with the rules on sections 49–50: the top-down and bottom-up routes meet.

Lab 2: one anomaly per normal form

Q3 · UNF → 1NF

Order(orderID, custID,
  items)

items = 'S7 ×2, U2 ×1'

Anomaly: item S7 is renamed S8, so every order’s text list must be edited. Miss one and orders disagree.

1NF fix: one row per order line, so one UPDATE … WHERE itemID = 'S7' catches all.

Q4 · 1NF → 2NF

OrderLine(orderID, itemID,
  quantity, orderDate)

orderDate repeats on every line

Anomaly: the date is corrected on one line but not the others, so the order has two dates.

2NF fix: orderDate needs only orderID, so move it to Order(orderID, orderDate).

Q5 · 2NF → 3NF

Order(orderID, orderDate,
  custID, custState)

custState repeats on every order

Anomaly: a customer moves, so all their orders must change. Miss one and they live in two states.

3NF fix: custState hangs on custID, a middle-man. Move it to Customer(custID, state).

Remember: each step removes one kind of repeat: lists, part-key facts, middle-man facts.

More detail

Design lab questions 3 to 5 ask you to invent a schema at one level and an update anomaly that the next level prevents. These examples reuse the Shop database from Lab 1 so the tables feel familiar; any domain works as long as you name the dependency that causes the repeat. Q3, UNF to 1NF: storing a list in one cell (a repeating group) breaks 1NF. If an item code changes, or one quantity changes, you have to find and edit text inside many cells, and nothing stops two orders formatting the same item differently.

You also can’t put a foreign key on a list. In 1NF each order line is its own row, so a single UPDATE statement finds every S7 reliably. Q4, 1NF to 2NF: OrderLine has the composite key (orderID, itemID), but orderDate depends on orderID alone, a partial dependency. The date is copied onto every line of the order, so fixing it in one place leaves the others wrong. 2NF moves orderDate (and custID) into an Order table keyed by orderID.

Q5, 2NF to 3NF: in Order(orderID, orderDate, custID, custState) every column depends on the whole single-column key, so it is in 2NF, but custState depends on custID, which is not a key: orderID → custID → custState, a transitive dependency. The customer’s state is repeated on each of their orders. 3NF moves it to Customer(custID, state) and keeps custID in Order as the foreign key. A good exam-style answer names the table, the dependency, the anomaly, and the split that fixes it.
