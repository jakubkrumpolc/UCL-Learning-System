Debug the page: source, Inspect, Console

View page source

Right-click → View page source. Shows the HTML the server sent. For a PHP page, that’s the output of your PHP, so it’s the quickest way to see what your code actually printed.

Inspect element

Right-click → Inspect. Hover the code to highlight that part of the page; switch CSS rules off and on live to see what each one does.

Console

The dev-tools tab with error messages and print output (e.g. JavaScript’s console.log). First place to look when the page won’t display properly.

Network

Lists every request. Click your form’s POST to see exactly which fields were sent to the PHP script, and what came back.

Part 7 · Setup · Git

How Git thinks: four places for your work

Saves snapshots

Each commit records the state of the project, with a message. You can go back to any of them.

Lets you work at once

Everyone has a full copy. Work in parallel, then merge.

Keeps the history

git log shows who changed what, when and why.

Local vs remote

commit only saves on your machine. Nobody sees it until you push.

Remember: add → commit → push sends work up; pull brings everyone else’s down. Commit is local until you push.

More detail

A version control tool (the tutorial mentions Subversion and git) saves the current state of your project, allows several people to access and edit the files at the same time, and keeps a record of how the project has changed over time. Git is the standard choice, and GitHub hosts the shared copy.

It helps to picture four places. Your working folder holds the files you edit. git add copies chosen changes into the staging area: the list of changes you are proposing for the next snapshot. git commit turns everything staged into a commit in your local repository, with a message describing it. git push uploads your new commits to the remote (GitHub), where teammates can get them with git pull, which downloads their commits and merges them into your files. git clone is the one-off command that copies a whole remote repository to your machine to start with.

The key surprise for beginners: commit is local. You can commit ten times and your team sees nothing until you push. Conversely, their pushed work only reaches your files when you pull.

Start the team repository

1

Install Git: git-scm.com/downloads (macOS: it may already be there; run git --version).

2

One team member creates a private repository on GitHub (web interface) and adds the others under Settings → Collaborators.

3

Everyone clones it into their *AMP web folder (htdocs), so Apache serves it straight away.

4

Open http://localhost/auction/ (MAMP: port 8888) to see it running.

# once per computer
git config --global user.name "Your Name"
git config --global user.email "you@ucl.ac.uk"
git config --global pull.rebase false

# Mac XAMPP · Windows: cd C:\xampp\htdocs
cd /Applications/XAMPP/xamppfiles/htdocs
# URL from the green Code button on GitHub
git clone https://github.com/team/auction.git

A tidy project folder

htdocs/auction/
├── .gitignore
├── README.md how to set it up
├── config.example.php template, committed
├── config.php passwords: NOT committed
├── db.php one shared connection
├── index.php, browse.php, …
└── sql/
├── 00_create_db.sql
├── 01_schema.sql
└── 02_seed.sql

.gitignore

config.php
.DS_Store
*.log
backups/

Remember: one person creates the repo, everyone clones it into htdocs. Passwords stay out of Git.

More detail

The tutorial’s steps: install git (git-scm.com/downloads); create a shared repository on GitHub using its web interface; check it out from the command line with git clone [the URL GitHub gives you] (some IDEs, and GitHub Desktop, will do this for you). It may be helpful to clone straight into your *AMP www directory (htdocs), so the web server can run the code without copying files around. This week’s to-do: one team member sets up the GitHub project and the rest clone it.

Set your name and email once per computer so commits are labelled correctly. Setting pull.rebase false tells git that git pull should merge; recent git versions otherwise stop with “Need to specify how to reconcile divergent branches” the first time your copy and the remote have both changed. When you first push over HTTPS, GitHub will not accept your account password: sign in through the browser window Git Credential Manager opens, use GitHub Desktop or the gh CLI (gh auth login), or set up an SSH key.

Keep secrets out of the repository: a config.php holding the database password is listed in .gitignore, and a config.example.php with placeholder values is committed instead, so each teammate copies it and fills in their own. Ignore system junk (.DS_Store), logs and local database dumps too. A short README saying how to create the database and which config to copy saves your teammates (and markers) time.

Part 7 · Setup · Git

The daily loop: pull, add, commit, push

git pull  # start of a session: get teammates’ work
# … edit files, test in the browser …
git status  # what changed? what’s staged?
git diff  # the exact lines you changed
git add browse.php sql/02_seed.sql  # stage these changes
git commit -m "Browse page lists live auctions"  # snapshot + message
git pull  # anything new since? merge it first
git push  # publish your commits

git log --oneline --graph  # history at a glance
git restore file.php  # throw away uncommitted edits

Small, frequent commits

One idea per commit (“Add bid form”), not one per day. Easy to understand, easy to undo.

Good messages

Say what and why: “Fix bid check: reject bids below current price”, not “stuff”.

Push often

Pull before you start and before you push. The longer you wait, the bigger the conflicts.

git add specific files

Check git status first; git add . happily stages files you didn’t mean to share.

Remember: pull → work → add → commit → pull → push. Little and often keeps conflicts small.

More detail

Stage changes with git add [filename]: this adds the changes in that file to the list of changes you are proposing to make. git commit then updates your local repository with a snapshot of everything you have added; give it a message describing what you did (-m "…" on the command line, otherwise an editor opens).

Use git pull frequently to get the most up-to-date changes from the remote repository; a pull also automatically tries to merge them into your files. Once you have committed, publish with git push. Stage, commit and push frequently to keep the rest of your group in the loop and to prevent conflicts. If git push is rejected because the remote has commits you don’t have, git pull first, then push again.

Useful extras: git status (what changed and what is staged), git diff (the exact changed lines), git log --oneline --graph (history), git restore file (discard uncommitted changes to a file) and git revert (undo a pushed commit safely by adding a new commit that reverses it; avoid rewriting history that teammates already have). The tutorial points to Roger Dudler’s “git – the simple guide” (rogerdudler.github.io/git-guide) for a one-page reference.

Part 7 · Setup · Git

Merge conflicts, calmly

$ git pull
Auto-merging browse.php
CONFLICT (content): Merge conflict in browse.php
Automatic merge failed; fix conflicts and then commit the result.

browse.php now contains both versions:

<<<<<<< HEAD ← yours
$title = "Live auctions";
=======
$title = "Current auctions";
>>>>>>> 3f9c2e1 (Rename title) ← theirs

1

Open the file. Find the <<<<<<< markers (git status lists the files).

2

Decide: keep yours, keep theirs, or combine. Talk to your teammate if unsure.

3

Delete all three marker lines.

4

Test the page still works.

5

git add the file, git commit, git push.

Prevent them

Pull often, push often, and split work by file or feature so two people rarely edit the same lines.

Remember: git merges what it can. When two people change the same line, it asks you to decide.

More detail

A pull merges the remote changes into your files. Git does sensible merges automatically (different files, or different parts of the same file, are combined without fuss), but it is not a mind-reader: if you and a collaborator changed the same line in different ways, it can’t know which is right. It reports a merge conflict, and you need to resolve it manually and commit the final decision.

In the file, git marks the conflicting region: the lines between <<<<<<< HEAD and ======= are your version, the lines between ======= and >>>>>>> are the incoming one. Edit the region into what it should be (one version, the other, or a combination), delete the three marker lines, save, check the page still works, then git add the file and git commit (git pre-fills a merge message) and push. If it all goes wrong, git merge --abort returns you to the state before the pull.

Editors such as VS Code show “Accept current / Accept incoming / Accept both” buttons above each conflict, which is the same decision with less typing. Never commit a file that still contains the marker lines: PHP will refuse to run it.

Branches: work on a feature without breaking main

git switch -c feature/bidding  # new branch from where you are
# … edit, add, commit as usual …
git push -u origin feature/bidding  # first push of the branch
# on GitHub: open a Pull Request → teammate reviews → Merge

git switch main  # back to the shared branch
git pull  # now includes the merged feature
git branch -d feature/bidding  # tidy up

Why bother?

main stays working at all times, so the demo never breaks because someone is half-way through a change.

Pull requests

A page on GitHub showing the branch’s changes. A teammate reads it before it’s merged: a free code review.

Keep it simple

Optional for a small team. If you use branches, keep them short-lived (a day or two) and merge often.

Remember: main = always works. Build features on a branch, merge them back through a pull request.

More detail

This is not on the tutorial slides, but it is the natural next step once the daily loop is comfortable. A branch is a separate line of commits. git switch -c feature/bidding creates one and moves you onto it; your commits there don’t affect main until the branch is merged.

Push the branch with git push -u origin feature/bidding (-u links your local branch to the remote one, so later plain git push / git pull work). On GitHub, open a pull request from the branch into main: it shows every changed line, teammates can comment, and the Merge button combines it into main. Afterwards everyone switches to main and pulls.

Conflicts still happen with branches (they appear in the pull request, or when you merge main into your branch), and are resolved exactly as in the previous section. For a coursework team of three or four, working directly on main with frequent small commits is fine; branches are worth it when a change takes more than a session or would leave the site broken part-way.

Keep the database in SQL scripts

mysql command line

Type SQL directly. Fast once you know it.

phpMyAdmin

Web interface that comes with XAMPP/MAMP. Point and click, or paste SQL.

MySQL Workbench

Desktop app: diagrams, query editor.

The tutorial’s suggestion

1

Write SQL scripts in your editor or IDE.

2

Share them with teammates through Git, like any other code.

3

Load them with phpMyAdmin (or the mysql console).

4

So your database and table definitions are properly recorded.

sql/
├── 00_create_db.sql database + app user
├── 01_schema.sql CREATE TABLE …
└── 02_seed.sql INSERT sample rows

Why scripts beat clicking

Anyone can rebuild an identical database in seconds. Changing the design = edit the script, re-run it. And Git shows how the schema changed.

One rule

If you change a table in phpMyAdmin by clicking, also change the script, or your teammates’ databases will drift apart.

Remember: the scripts are the real database design. Git shares them; phpMyAdmin just runs them.

More detail

Many tools work with MySQL: the mysql command-line client, phpMyAdmin, MySQL Workbench and others. The tutorial’s suggestion is to create SQL scripts, edited in an editor or IDE and shared with teammates via git, and load them using phpMyAdmin, so your database and table definitions are properly recorded.

Each teammate runs MySQL on their own computer, so the database itself is not shared through GitHub, only the scripts that build it. Numbering the scripts (00, 01, 02…) makes the run order obvious: create the database and user, then the tables (parents before children because of foreign keys), then the sample data. Because 00 drops and recreates the database, re-running all three gives everyone the same fresh state.

Scripts allow rapid experimentation with table designs without locking you in: change the CREATE TABLE, re-run, and test. The next sections build these three files for the auction app from Part 4.

Part 7 · Setup · Backend

Create the database and its user

-- sql/00_create_db.sql
DROP DATABASE IF EXISTS auction;

CREATE DATABASE auction
DEFAULT CHARACTER SET utf8mb4
DEFAULT COLLATE utf8mb4_unicode_ci;

CREATE USER IF NOT EXISTS 'auction_app'@'localhost'
IDENTIFIED BY 'change-me';
GRANT SELECT, INSERT, UPDATE, DELETE
ON auction.* TO 'auction_app'@'localhost';

USE auction;

IF EXISTS

The first run has nothing to drop; without it the script stops with an error.

utf8mb4

MySQL’s full UTF-8 (accents, all languages, emoji). Its older “utf8” stores only 3 bytes per character.

A separate app user

Your PHP connects as auction_app, not root. It can read and change rows but can’t DROP tables: least privilege.

MySQL 8 change

The slide’s GRANT … IDENTIFIED BY no longer works in MySQL 8: create the user first, then GRANT.

Remember: run once as root: drop, create, make a limited user, grant it rights. Your app logs in as that user.

More detail

The tutorial’s script is DROP DATABASE Example; then CREATE DATABASE Example DEFAULT CHARACTER SET utf8 DEFAULT COLLATE utf8_general_ci; then GRANT SELECT, UPDATE, INSERT, DELETE ON Example.* TO 'exampleuser'@'localhost' IDENTIFIED BY 'mypassword'; and finally USE Example;. The version above keeps the same structure with three updates.

DROP DATABASE IF EXISTS doesn’t fail when the database isn’t there yet, so the script works the first time too. utf8mb4 is MySQL’s real UTF-8: its “utf8” (an alias for utf8mb3) can’t store 4-byte characters such as emoji, which users will type into item titles. MySQL 8.0 removed the IDENTIFIED BY clause from GRANT, so the user is created first with CREATE USER (MariaDB, which XAMPP ships instead of MySQL, still accepts the old form, but the two-step version works on both).

The GRANT gives the application user only SELECT, INSERT, UPDATE and DELETE on the auction database: everything a website needs, and nothing that can drop tables or touch other databases. This limits the damage of a bug or an SQL injection (Part 4, section 63). Run this script as root (phpMyAdmin’s default login on XAMPP); the password here is for a local test database only and, like config.php, real passwords never go into Git.

Tables and engines: use InnoDB

-- sql/01_schema.sql (first table)
CREATE TABLE Member (
memberId INT AUTO_INCREMENT PRIMARY KEY,
email VARCHAR(100) NOT NULL UNIQUE,
displayName VARCHAR(50) NOT NULL
) ENGINE = InnoDB;

Same pattern as the slide’s Users table. The full Member/Item/Bid schema is in Part 4, section 60.

InnoDBMyISAM
Default?Yes (MySQL 5.5+)Used to be
Foreign keysSupportedIgnored
TransactionsSafe, row-level lockingNot transaction-safe
SpeedPerceived as slowerFast for simple reads
Full-text searchYes since MySQL 5.6Yes

Remember: InnoDB: foreign keys and transactions. Your ER diagram’s lines only mean something on InnoDB.

More detail

A table definition looks like the tutorial’s first example: CREATE TABLE Users (id INTEGER AUTO_INCREMENT PRIMARY KEY, first_name VARCHAR(40) NOT NULL, family_name VARCHAR(40) NOT NULL) ENGINE = InnoDB;. Table design is important, and scripts let you experiment with designs quickly without locking yourself in.

MySQL supports several storage engines, even within the same database. MyISAM used to be the default: fast but not transaction-safe, up to 64 keys per table with a maximum key length of 1024 bytes, full-text columns and search, and no foreign keys (it accepts the FOREIGN KEY syntax but silently ignores it). InnoDB is transaction-safe with row-level locking and supports foreign keys, at the cost of (perceived) slower performance.

The slide says InnoDB has no full-text search; that was true of old versions, but InnoDB has supported FULLTEXT indexes since MySQL 5.6 (and MariaDB 10.0.5), and it has been the default engine since MySQL 5.5. For the project, use InnoDB everywhere: without it your FOREIGN KEY and ON DELETE rules do nothing. Week 3a’s storage lecture is about how an engine like InnoDB lays those tables out on disk (as a B+ tree on the primary key).

Seed data, load the scripts, check it worked

-- sql/02_seed.sql
INSERT INTO Member (email, displayName) VALUES
('ann@example.com', 'Ann'),
('raj@example.com', 'Raj'),
('mei@example.com', 'Mei');

INSERT INTO Item (sellerId, title, startPrice, endsAt) VALUES
(1, 'Vintage camera', 40.00, '2026-12-01 18:00'),
(2, 'Road bike', 150.00, '2026-11-20 12:00');

-- check it worked
SHOW DATABASES;  # which databases exist
SHOW TABLES;  # tables in the current database
DESCRIBE Member;  # column definitions
SELECT * FROM Member;  # are the rows there?

Three ways to load a script

phpMyAdmin → SQL tab

Paste the script, press Go. (Or the Import tab to upload the .sql file.)

mysql console

source sql/01_schema.sql

Terminal

mysql -u root < sql/00_create_db.sql

Fake data, real tests

Seed enough rows to test every page: an item with no bids, one that has ended, a member with two items.

Remember: never type test data twice: put it in 02_seed.sql and re-run it whenever you rebuild.

More detail

It is often useful to add sample data with a script, so you don’t have to type it in repeatedly. Plain SQL INSERTs are enough (the tutorial inserts three Users rows one statement at a time; a single INSERT with several value lists, as above, does the same). For larger data sets, LOAD DATA INFILE reads rows from a stored CSV file.

Load whole scripts into MySQL with the source command in the mysql console (source createdb.sql), or copy and paste a script into phpMyAdmin’s SQL tab. In phpMyAdmin you may need to create the database first with its create-database form (or run 00_create_db.sql first). Once the database has data, confirm it with SELECT * FROM Users; and look around with SHOW DATABASES; (list databases), SHOW TABLES; (tables in the current database) and DESCRIBE Users; (column definitions), or use phpMyAdmin’s tabs.

With XAMPP the command-line client lives in /Applications/XAMPP/xamppfiles/bin/mysql on a Mac and C:\xampp\mysql\bin\mysql.exe on Windows (root has no password by default on a fresh XAMPP). memberId and itemId aren’t listed in the INSERTs because AUTO_INCREMENT fills them in, which is why the items can refer to sellers 1 and 2.

Part 7 · Setup · Backend

Back up before you break it

phpMyAdmin → Export

Creates a dump: a text file of SQL commands (CREATE TABLE + INSERTs) that rebuilds the database with its data.

phpMyAdmin → Import

Runs a dump to restore it.

When

Before changing the schema, before a demo, and whenever there’s data you’d hate to retype.

# Mac XAMPP (Windows: C:\xampp\mysql\bin\mysqldump.exe)
/Applications/XAMPP/xamppfiles/bin/mysqldump -u root auction \
> backups/auction-2026-10-21.sql  # save

/Applications/XAMPP/xamppfiles/bin/mysql -u root auction \
< backups/auction-2026-10-21.sql  # restore

Dump vs. scripts

Scripts (sql/) are the design, shared in Git. Dumps (backups/) are snapshots of data, kept out of Git by .gitignore.

Remember: Export before you experiment. A dump is a script that puts everything back.

More detail

Use phpMyAdmin’s Export tab to create a dump of a database: all the data saved as a text file of SQL commands. Use the Import tab to load it back. The same can be done from the command line with mysqldump, which the tutorial notes is more complicated to get working with XAMPP on the lab machines (mainly because the XAMPP binaries are not on the PATH, hence the full paths above).

Make a dump before changing table definitions, before deleting test data and before a demo. Because the schema and seed scripts already live in Git, a fresh database can always be rebuilt; the dump additionally preserves whatever data you have added since, such as accounts and bids created while testing the site.

Keep dumps out of the repository (the backups/ line in .gitignore): they change on every export, can be large, and may contain personal or password data from testing.

Connect PHP to the database, safely

// config.php (ignored by Git; copy config.example.php)
<?php
return [
'host' => 'localhost', 'db' => 'auction',
'user' => 'auction_app', 'pass' => 'change-me',
];

// db.php (committed; every page does require "db.php")
<?php
$c = require __DIR__ . '/config.php';
$pdo = new PDO(
"mysql:host={$c['host']};dbname={$c['db']};charset=utf8mb4",
$c['user'], $c['pass'],
[PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC]);

// item.php
require 'db.php';
$st = $pdo->prepare(
"SELECT title FROM Item WHERE itemId = ?");
$st->execute([$_GET['id']]);
$item = $st->fetch();

One connection file

Every page includes db.php, so the connection is set up in exactly one place.

Exceptions on

ERRMODE_EXCEPTION makes SQL errors stop the page loudly instead of failing silently.

Always prepare

Values from forms or URLs go in as ? placeholders. See section 63.

Remember: config.php = secrets (not in Git) · db.php = one shared PDO connection · every query with user input = prepare + ?.

More detail

This section joins the tutorial’s database setup to the PHP code from Part 4 (sections 62–63). Instead of writing new PDO(…) with a password on every page, keep the connection details in config.php, which returns an array and is listed in .gitignore. Commit a config.example.php with the same keys and placeholder values; each teammate copies it to config.php and fills in their own password.

db.php reads the config and creates one PDO connection. charset=utf8mb4 matches the database’s character set so non-English text survives the round trip. PDO::ERRMODE_EXCEPTION throws an exception on any SQL error (the default in PHP 8 too, but saying it explicitly protects older setups), and FETCH_ASSOC returns rows as arrays keyed by column name, e.g. $item["title"]. Every page then starts with require "db.php"; and has $pdo ready.

Any value that comes from the user (form fields, $_GET ids, cookies) goes through prepare() and execute() with ? placeholders, never string concatenation, and anything printed back into HTML goes through htmlspecialchars(). The app user from section 14 has no DROP rights, as a second line of defence.

The tutorial’s to-dos for this week: upload your draft ER diagram; one member of your team sets up a GitHub project and the rest clone it to an appropriate place on their computers; and play around with making SQL databases and scripts for your server, remembering that you can make changes in the future.

The suggested steps turn that into a working skeleton: shared settings and ignore rules first (so nobody commits a password by accident), the database as numbered scripts generated from your ER diagram using the translation rules from Part 3, everyone able to rebuild it locally, and one page that connects through db.php and lists some seed rows. Once that page works on every teammate’s machine, the rest of the project is adding pages and queries.
