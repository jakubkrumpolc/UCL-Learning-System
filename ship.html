A tiny auction site: from brief to diagram

The brief

Members sign up with an email and a display name.

A member sells items, each with a start price and an end time.

Members bid on items; we keep each bid’s amount and time.

The home page lists live items with their top bid.

Remember: every app starts here. Nouns → boxes, verbs → lines, facts about a bid → on the line.

More detail

Apply the recipe from Part 3 to a four-sentence brief. Nouns with their own details: Member and Item. Verbs: a member sells an item, and members bid on items. Multiplicities: each item has exactly one seller and a member may sell none or many, so Member 1..1 Sells 0..* Item; a member can bid on many items and an item can receive many bids, so Bids on is 0..* to 0..* (many-to-many).

The amount and the time belong to a bid, not to the member or the item alone, so they are attributes of the Bids on relationship, drawn in a box on a dashed line. email is marked {CK}: it is unique, so it could identify a member, but we choose a short numeric memberId as the primary key because emails can change. One subtlety that matters on the next section: a member can bid on the same item several times (raising their own bid).

A linking table keyed only by (memberId, itemId) would allow just one bid per pair, so the Bid table will get its own key, bidId. Some designers draw Bid as a third entity for exactly this reason; both diagrams lead to the same tables. The “top bid” on the home page is not stored anywhere: it is derived with MAX(amount) in a query, which avoids keeping a copy that could get out of date (an update anomaly).

Part 4 · Ship · Step 2

Create the tables

CREATE TABLE Member (
  memberId INT AUTO_INCREMENT PRIMARY KEY,
  email VARCHAR(100) NOT NULL UNIQUE,
  displayName VARCHAR(50) NOT NULL);

CREATE TABLE Item (
  itemId INT AUTO_INCREMENT PRIMARY KEY,
  sellerId INT NOT NULL,
  title VARCHAR(100) NOT NULL,
  startPrice DECIMAL(8,2) NOT NULL,
  endsAt DATETIME NOT NULL,
  FOREIGN KEY (sellerId)
    REFERENCES Member(memberId));

CREATE TABLE Bid (
  bidId INT AUTO_INCREMENT PRIMARY KEY,
  itemId INT NOT NULL,
  bidderId INT NOT NULL,
  amount DECIMAL(8,2) NOT NULL,
  placedAt DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (itemId) REFERENCES Item(itemId)
    ON DELETE CASCADE,
  FOREIGN KEY (bidderId)
    REFERENCES Member(memberId));

AUTO_INCREMENT: MySQL picks the next id for you.

bidId: one member can bid on an item many times.

CASCADE: delete an item and its bids go too.

Remember: money → DECIMAL · ids → AUTO_INCREMENT · diagram lines → FOREIGN KEYs.

More detail

This is the physical design: the diagram from the previous section written as MySQL, using the types and constraints from Part 2 and the translation rules from Part 3. Create the tables in this order, parents first, because a FOREIGN KEY can only reference a table that already exists (and drop them in the reverse order).

Member: memberId is an INT with AUTO_INCREMENT, so when you INSERT a member without an id MySQL assigns 1, 2, 3… for you (in code you can read the new id back, e.g. PDO’s lastInsertId()). email is NOT NULL UNIQUE because it was a candidate key: the database itself refuses a second account with the same email. Item: Sells is 1:*, so the FK sellerId sits on the many side (Item).

Money uses DECIMAL(8,2): exact, up to 999999.99; never FLOAT, which stores binary approximations, so 0.1 + 0.2 isn’t exactly 0.3. endsAt is a DATETIME so you can compare it with NOW(). Bid: Bids on is *:*, so it becomes its own table with an FK to each side. It gets its own bidId rather than the composite key (itemId, bidderId), because a member may bid on the same item several times. placedAt defaults to the current time, so the app doesn’t need to send it.

ON DELETE CASCADE on itemId means deleting an item removes its bids automatically (section 19); bidderId uses the default (RESTRICT), so you can’t delete a member who has bids. All of this needs the InnoDB engine, which is MySQL’s default. You can paste the whole script into phpMyAdmin’s SQL tab and press Go.

Part 4 · Ship · Step 3

One query behind each page

Sign-up page

INSERT

INSERT INTO Member (email, displayName)
VALUES ('ann@example.com', 'Ann');

“Place bid” button

INSERT

INSERT INTO Bid (itemId, bidderId, amount)
VALUES (7, 2, 25.00);

Home page: live items

LEFT JOIN + MAX

SELECT i.itemId, i.title, MAX(b.amount) AS topBid
FROM Item i LEFT JOIN Bid b ON b.itemId = i.itemId
WHERE i.endsAt > NOW()
GROUP BY i.itemId, i.title
ORDER BY i.endsAt;

“My bids” page

JOIN + ORDER BY

SELECT i.title, b.amount, b.placedAt
FROM Bid b JOIN Item i ON i.itemId = b.itemId
WHERE b.bidderId = 2
ORDER BY b.placedAt DESC;

Remember: each page is a question for the database. Write and test its SQL first, then build the page.

More detail

A practical way to build a database-backed site: list the pages, write down the question each page asks, and get its SQL working in phpMyAdmin before writing any app code. Sign-up: INSERT a member; memberId is filled in by AUTO_INCREMENT, and the UNIQUE constraint on email rejects a duplicate account. Place bid: INSERT a bid; placedAt defaults to now.

In a real app you would also check the bid is higher than the current top bid and that the auction hasn’t ended, either with a query first (SELECT MAX(amount) FROM Bid WHERE itemId = 7) or inside a transaction (section 35) so two people bidding at the same moment can’t both win. Home page: a LEFT JOIN (section 30) keeps items that have no bids yet; for those, MAX(b.amount) is NULL, which the page can show as “no bids, starts at £…”. The top bid is derived with MAX rather than stored, so it can never go stale.

WHERE i.endsAt > NOW() keeps only live auctions, and GROUP BY makes one row per item. My bids: an inner JOIN (section 29) from the member’s bids to the items they were on, newest first. The literal values here (7, 2, 'Ann') stand in for what the page sends: the logged-in member’s id, the item they clicked and the amount they typed. In real code these must be passed as placeholders, never pasted into the SQL text (section 63).

Part 4 · Ship · Step 4

The code that runs a query

1. Browser asks for /browse.php

2. PHP on the server sends SQL

3. MySQL returns rows

4. PHP turns rows into HTML

Python works the same way: mysql.connector, cursor.execute(), fetchall().

<?php // browse.php
$pdo = new PDO("mysql:host=localhost;dbname=auction",
               "app", "secret");
$rows = $pdo->query("SELECT title, startPrice FROM Item
                     WHERE endsAt > NOW()")->fetchAll();
?>
<ul>
<?php foreach ($rows as $r): ?>
  <li><?= htmlspecialchars($r["title"]) ?></li>
<?php endforeach; ?>
</ul>

Remember: connect, query, fetch, show. Every database-backed page is those four verbs.

More detail

This is the three-tier architecture from section 9 in action: the browser (client) never talks to MySQL; it asks the web server for a page, and server-side code queries the database and builds the HTML. MySQL with phpMyAdmin usually comes as part of a local stack such as XAMPP or MAMP (Apache web server + MySQL + PHP), so PHP is a natural fit; use whatever language your coursework template uses.

The PHP above uses PDO (PHP Data Objects), PHP’s standard database interface. new PDO(…) opens a connection: the DSN string names the server and database, followed by a username and password (keep real passwords out of code you share or commit, e.g. in a separate config file). query() sends the SQL and fetchAll() returns the result rows as arrays, so $r["title"] is one row’s title.

The page then loops over the rows and prints one list item per item. htmlspecialchars() escapes characters like < and > so a seller can’t put HTML or JavaScript into a title and have it run in other people’s browsers (cross-site scripting). This query has no user input in it, so query() is fine here; as soon as a value comes from the user (a search box, an item id in the URL, a form), use prepare() with placeholders instead, as the next section shows.

In Python the same four steps are: mysql.connector.connect(host=…, user=…, password=…, database=…), cur = db.cursor(), cur.execute(sql), rows = cur.fetchall(); frameworks such as Flask add the URL routing and HTML templates.

Part 4 · Ship · Security

Never glue user input into SQL

Unsafe: string glue

$name = $_GET["name"];
$sql = "SELECT * FROM Member
        WHERE displayName = '$name'";
$rows = $pdo->query($sql)->fetchAll();

Someone types the name x' OR '1'='1 and the database runs:

… WHERE displayName = 'x' OR '1'='1'

'1'='1' is always true, so every member comes back.

Safe: placeholders

$stmt = $pdo->prepare("SELECT * FROM Member
                       WHERE displayName = ?");
$stmt->execute([$_GET["name"]]);
$rows = $stmt->fetchAll();

The ? is a placeholder. The value travels separately, so it can never become SQL.

The same input now just matches nobody.

Python: cur.execute("… = %s", (name,))

Remember: placeholders, always. User input is data, never SQL.

More detail

SQL injection is one of the most common and damaging web security bugs, and it is entirely avoidable. It happens when an app builds a SQL statement by pasting user input into the SQL text. The quote character in the input closes the string early, and whatever follows is run as SQL. With x' OR '1'='1, the WHERE clause becomes a condition that is true for every row, so a search or login check returns all members.

Worse inputs can read other tables (with UNION SELECT) or, where several statements are allowed, change or delete data: the famous xkcd cartoon “Exploits of a Mom” names a child Robert'); DROP TABLE Students;-- (“little Bobby Tables”). The fix is a prepared statement with placeholders. prepare() sends the SQL with a ? where each value goes; execute() sends the values separately, and the database treats them purely as data, so a quote inside a name is just a character.

PDO also supports named placeholders (:name with execute(["name" => $x])). Python’s mysql.connector uses %s placeholders with the values passed as a tuple: cur.execute("SELECT * FROM Member WHERE displayName = %s", (name,)); note this is not Python’s % string formatting, because the values are passed as a second argument.

Rules of thumb: use placeholders for every value that comes from outside (forms, URLs, cookies), even numbers; placeholders can’t stand in for table or column names, so pick those from a fixed list in your code; and escape output with htmlspecialchars() (previous section), which guards against a different attack, cross-site scripting. The database user your app connects as should also have only the privileges it needs (GRANT, section 35).
