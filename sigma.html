Why “relational”? Tables are relations

Set { }

An unordered collection with no repeats.

Tuple ( )

An ordered list: a 2-tuple is a pair, a 3-tuple a triple…

Cartesian product A × B

Every possible combination: all pairs (a, b).

Relation

Given sets A1…An, a relation is a subset of A1 × … × An. Each Ai is a domain.

In SQL you say…In maths it’s…Example (Staff)
tablerelation = a set of tuplesStaff
row / recordtuple in the relation(“SG37”, “Ann”, “Beech”, …)
column / attributedomain the values come fromstaffNo = all possible staff numbers

A pair (a, b) being in the relation means “a is related to b”. A pair that’s missing means they aren’t. A table works the same way: a row is in it, or it isn’t.

Because every table is the same simple 2-D shape (a relation), tables can be manipulated mathematically. That maths is relational algebra.

Remember: relation = table, tuple = row, attribute = column. The name “relational” comes from the maths, not from the links between tables.

More detail

Recall from week 1: relational database management systems are formalised by relational algebra and calculus, standardised by the SQL standard, and implemented by products such as MySQL, Oracle, MariaDB, SQLite, PostgreSQL, Microsoft SQL Server and IBM Db2. This lecture is the “formalised” part.

A set is an unordered collection of data without repeats, written with curly brackets {}. A tuple is an ordered list, written with round brackets (): a 2-tuple is an ordered pair, a 3-tuple a triple and so on. The Cartesian product of sets is the set of all possible combinations of their elements: A × B contains every ordered pair (a, b). A mathematical (binary) relation describes a connection between elements of two sets: if (a, b) is in the relation, a is related to b; if (c, d) is missing, c and d don’t have that relationship. For n sets A1, A2, …, An, a relation is a particular subset of A1 × A2 × … × An, and each Ai is the domain that member of the tuple is drawn from.

In a relational database every table is such a relation. Attributes (columns) are the domains: staffNo is the set of all possible staff numbers, fName the set of all possible strings (perhaps up to some length). Records (rows) are the tuples included in the relation, e.g. (“SG37”, “Ann”, “Beech”, …). A table is a relation: a set of tuples. Strictly, a set has no order and no duplicates, which is why the theory says rows have no order and a table should have no duplicate rows (SQL is a little looser and allows duplicates unless you say DISTINCT).

Relational algebra: operations on tables

Closure

Every operation takes relation(s) in and gives a relation out. So you can feed one result into the next and chain operations, like + and × in ordinary algebra.

Unary

Takes one relation: σ, Π.

Binary

Takes two relations: ∪, −, ×, and the derived ∩, ⋈, ÷.

OperationSymbolKindRoughly in SQL
Selectionσbasic · unaryWHERE
ProjectionΠbasic · unarySELECT col, col
Union∪basic · binaryUNION
Set difference− or \basic · binaryEXCEPT
Cartesian product×basic · binaryFROM A, B
Intersection∩derivedINTERSECT
Join (θ, natural, outer, semi)⋈derivedJOIN … ON / USING
Division÷derived“for all” queries

Remember: five basic operations: σ Π ∪ − ×. Everything else can be built from them.

More detail

Relational algebra performs transformations on relations to produce new relations. It has the property of closure: applying an operation to a relation yields another relation, of the same type. That is what lets you string several operations together into one expression, and it is why a SQL query can use a subquery’s result as if it were a table.

There are five basic operations: selection, projection, union, set difference and Cartesian product. Three derived operations can be expressed using the basic ones: intersection, join (several types) and division. A unary operation takes one relation as input (selection and projection); a binary operation takes two (union, set difference and Cartesian product, and the derived ones).

The SQL column is a guide, not an exact match: SQL tables can contain duplicates and have an order once you ORDER BY, whereas relations are sets. The highlighted rows are the five basic operations.

Row filter

Keeps only the tuples for which the predicate is true. Like the WHERE clause.

Predicates

Can combine conditions: σsalary > 10000 ∧ branchNo = ‘B003’(Staff) (∧ = AND, ∨ = OR, ¬ = NOT).

Remember: σ = Sieve: it lets some rows through.

More detail

Selection (also called restriction), written σpredicate(R), works on a single relation R. It produces a new relation containing only the tuples of R that satisfy the predicate. The columns stay the same; only rows are removed. In the example σsalary > 10000(Staff), Mary Howe (SA9) and Julie Lee (SL41), who earn 9,000, are dropped, leaving four staff.

The predicate can use comparisons (<, ≤, >, ≥, =, ≠) and combine them with the logical connectives ∧ (and), ∨ (or) and ¬ (not). Selection corresponds to the WHERE clause in SQL. Don’t be confused by names: SQL’s SELECT keyword does projection (choosing columns); relational algebra’s selection σ chooses rows, which is SQL’s WHERE.

All 6 tuples, but only the 4 listed attributes: a 4-column relation.

SELECT staffNo, fName,
lName, salary
FROM Staff;

Column filter

Keeps every tuple but masks out the attributes not listed. Like SELECT [list].

No duplicates

A relation is a set, so Πposition(Staff) has 3 tuples (Manager, Assistant, Supervisor), not 6. In SQL you need SELECT DISTINCT for that.

Remember: Π = Pick columns. σ cuts rows, Π cuts columns.

More detail

Projection, written Πa1,…,an(R), produces a new relation with all of R’s tuples but only the listed attributes; the others are masked out. ΠstaffNo, fName, lName, salary(Staff) gives a four-column table: a relation of 4-tuples.

It corresponds to the column list after SELECT in SQL. One difference matters in exams: relational algebra works on sets, so if removing columns makes two tuples identical, they collapse into one. Πposition(Staff) gives {Manager, Assistant, Supervisor}. SQL keeps duplicates by default (SELECT position FROM Staff returns six rows), so the exact SQL equivalent of a projection is SELECT DISTINCT.

Difference − (or \)

Tuples in R that are not in S. “Cities with a branch but no property.” SQL: EXCEPT.

Remember: R and S must be union compatible: same columns, same domains. You can’t stack a list of cities on a list of salaries.

More detail

Union, R ∪ S, combines (without duplicates) the tuples of two relations that have identical schemas: the same list of (attribute name, domain) pairs. It is a “vertical join”: one table stacked on top of the other. Example: list all cities where there is either a branch office or a property for rent: Πcity(Branch) ∪ Πcity(PropertyForRent). It is the same as UNION in SQL.

Set difference, R − S (also written R \ S), removes from R every tuple that also appears in S. Like union, both sides must be union compatible. Example: cities with a branch office but no property for rent: Πcity(Branch) − Πcity(PropertyForRent). With our rows only Bristol qualifies. It corresponds to EXCEPT in SQL; MySQL supports EXCEPT from version 8.0.31, and before that you write it with NOT IN or NOT EXISTS.

The property rows used here (PA14 Aberdeen, PL94 London, PG4, PG36, PG21, PG16 Glasgow) are from the lecture’s DreamHome example. Note why both sides are projected onto city first: Branch and Property have different columns, so they are not union compatible until you project them.

R × S

Pairs everything with everything

Each tuple of R glued to each tuple of S. Result: |R| × |S| tuples and cols(R) + cols(S) columns.

Staff × Branch

6 × 4 = 24 rows, 6 + 2 = 8 columns. Most of them pair a person with a branch they don’t work at.

SELECT *
FROM Staff, Branch; -- 24 rows

Remember: product = every combination. On its own it’s rarely what you want; add a σ and it becomes a join.

More detail

The Cartesian product R × S is a “horizontal join”: pairwise concatenation of tuples. Every tuple in R is combined with every tuple in S, giving a table with |R| × |S| tuples and numcols(R) + numcols(S) columns. With P = {a, b} and Q = {1, 2, 3}, P × Q has 2 × 3 = 6 tuples.

In SQL it is what you get by listing two or more tables after FROM with no join condition. Staff × Branch has 24 rows, because each of the 6 staff is paired with each of the 4 branches. Only 6 of those rows are “true” (a staff member with their own branch); filtering them is exactly what a join does (two sections on).

θ-join (theta join)

Predicate uses any comparison: < ≤ > ≥ = ≠. Flexible and all-purpose.

Equijoin

A θ-join whose predicate is =. The most common kind; note both branchNo columns stay.

Intersection ∩

Tuples in both R and S. Derived: R ∩ S = R − (R − S).

SELECT *
FROM Staff s JOIN Branch b
ON s.branchNo = b.branchNo;

Remember: join = × then σ. The predicate decides which pairs are “true”.

More detail

The derived operations are shorthand for combinations of basic ones. Intersection R ∩ S keeps tuples in both relations and equals R − (R − S). Division is covered later. Join is the frequently used operation that consists of a Cartesian product followed by a selection; the selection differs by type of join.

The theta join R ⋈predicate S is equivalent to σpredicate(R × S). The predicate involves a comparison (<, ≤, >, ≥, =, ≠); joins whose predicate uses = are called equijoins. It is the same as FROM … JOIN … ON in SQL and is flexible and all-purpose. Joining Staff to Branch on equal branchNo keeps the 6 meaningful pairs out of the 24 in the product. Both branchNo columns are kept in a theta join; the natural join (next) removes the copy.

A DBMS never actually builds the full product and then filters it (that would be far too slow on big tables); it uses indexes and smarter join algorithms. Relational algebra describes what the answer is, not how to compute it. The next lecture, query processing, is about the how.

Remember: natural join = equijoin on all same-named columns, minus the duplicate column.

More detail

The natural join R ⋈ S (no subscript) is an equijoin that checks for equality on all attributes with the same name in both relations and removes the duplicate column(s) from the result. It is equivalent to Πreduced list(σR.c1=S.c1, etc.(R × S)): take the product, keep tuples where every shared attribute matches, then project away the second copy of each shared column.

In the lecture’s example T(A, B) and U(B, C) share B. T’s tuple (a, 1) matches U’s (1, x) and (1, y), giving (a, 1, x) and (a, 1, y); T’s (b, 2) matches nothing, so it is lost. SQL’s closest form is FROM … JOIN … USING (column); there is also NATURAL JOIN, but it silently joins on every same-named column, which breaks if someone later adds, say, a “name” column to both tables, so explicit USING or ON is safer.

Inner join (default)

Only pairs where the condition holds. Unmatched rows vanish.

Left / right outer

Also keeps unmatched rows of the first (left) or second (right) table; the other side is filled with NULL.

Full outer

Keeps unmatched rows from both. MySQL has no FULL JOIN: UNION a LEFT and a RIGHT join.

SELECT b.*, s.staffNo
FROM Branch b LEFT JOIN Staff s
ON b.branchNo = s.branchNo;

Remember: LEFT keeps everything on the left. The gaps become NULL.

More detail

By default joins are inner joins: they only contain tuples where the join condition was fulfilled. Outer joins also retain tuples from one or both relations even if they didn’t match anything, filling the attributes that would have come from the other table with nulls. A left (outer) join preserves all rows of the first table, a right (outer) join all rows of the second, and a full outer join does both.

In the lecture’s picture T ⟕ U keeps (b, 2) with C = NULL. With our data, Branch LEFT JOIN Staff keeps Bristol (B004), which has no staff, as a row with staffNo NULL; an inner join would silently drop it. The lecture’s SQL pattern is SELECT b.*, p.* FROM Branch b [LEFT | RIGHT | FULL] JOIN Property p ON b.bCity = p.pCity; to list branches and properties in the same city along with the unmatched branches, properties, or both.

MySQL supports LEFT and RIGHT JOIN but not FULL OUTER JOIN; write it as a LEFT JOIN UNION a RIGHT JOIN. A handy trick: LEFT JOIN … WHERE s.staffNo IS NULL finds the left rows with no match at all (“branches with no staff”).

Use S to filter R

Like a θ-join, but the result keeps only R’s attributes. “Which T tuples have a partner in U?”

Example

Branch ▹Branch.branchNo = Staff.branchNo Staff = branches that have staff: B003, B005, B007 (each once). Bristol is out.

SELECT * FROM Branch b
WHERE EXISTS (SELECT 1 FROM Staff s
WHERE s.branchNo = b.branchNo);

Remember: semijoin = “keep the R rows that have a match”, without bringing S’s columns along.

More detail

The semijoin R ▹predicate S is the same as a θ-join, except that the final result contains only R’s attributes. It is equivalent to ΠR’s attribute list(σpredicate(R × S)): S is used purely to filter R’s tuples. (Textbooks also write it ⋉.)

In the lecture’s picture T ▹B U gives just (a, 1): the T tuples whose B value appears in U. Because the result is a set, a T tuple with several matches still appears once. In SQL a semijoin is written with EXISTS or IN: SELECT * FROM Branch WHERE branchNo IN (SELECT branchNo FROM Staff). Query optimisers like semijoins because they never need to build the wide joined rows.

Which clients viewed every 3-room property?

CR56 viewed PG4 and PG36. CR76 only saw PG4, so it’s out.

R ÷ S = T

Attributes of T = attr(R) − attr(S). T is every value that appears in R paired with all of S: S × T gives nothing that isn’t already in R.

T₁ ← Πattr(T)(R)  ·  T₂ ← Πattr(T)( (T₁ × S) − R )  ·  T ← T₁ − T₂

R = ΠclientNo, propertyNo(Viewing)  and  S = ΠpropertyNo(σrooms = 3(Property))

Step 1 · T₁

Every candidate (all clients in R): CR56, CR76, CR62.

Step 2 · T₂

T₁ × S − R: pairs a candidate should have but doesn’t. Their owners: CR76, CR62.

Step 3 · T₁ − T₂

The candidates missing nothing: CR56.

Remember: division answers “… for all …” questions. Start with everyone, remove anyone missing something.

More detail

Division R ÷ S (= T) selects (part of) the tuples of R that match every value in S. The attributes of the result T are attr(R) − attr(S), and T is the largest relation such that S × T produces no tuples that weren’t already in R. It can be built from basic operations: Πattr(T)(R) − Πattr(T)((Πattr(T)(R) × S) − R). Read it as three steps: start with all candidate tuples in R; build every pairing that would be needed to “fully cover” S and subtract what R actually has, leaving only the missing pairs; remove the candidates that own a missing pair.

The lecture’s example: identify all clients who have viewed all properties with three rooms: (ΠclientNo, propertyNo(Viewing)) ÷ (ΠpropertyNo(σrooms = 3(PropertyForRent))). The 3-room properties are PG4 and PG36. CR56 viewed both, CR76 viewed only PG4, CR62 only PA14, so the result is CR56. In the abstract example V ÷ W with V = {(a,1), (a,2), (b,1), (b,2), (c,1)} and W = {1, 2}, the answer is {a, b}: c lacks (c, 2).

SQL has no division operator. The usual translation is a double NOT EXISTS (“clients for whom there is no 3-room property they have not viewed”), or GROUP BY clientNo HAVING COUNT(DISTINCT propertyNo) = (SELECT COUNT(*) …) on the filtered viewings.

Aggregation ℑ

Applies COUNT, SUM, AVG, MIN, MAX to a relation, as in SQL. Result: a one-value relation.

Grouping

Attributes written before ℑ form groups; the function runs per group. = GROUP BY.

Rename ρ

Gives the result relation (and its columns) a better name. = AS.

SELECT branchNo, COUNT(staffNo),
SUM(salary)
FROM Staff
GROUP BY branchNo;

Remember: ℑ = the aggregate functions; the attributes on its left are the GROUP BY.

More detail

The lecture lists aggregation and grouping as “proposed” extensions to relational algebra. Aggregation, ℑ list of pairs(R), applies aggregate functions (COUNT, SUM, AVG, MIN and MAX, as in SQL). Grouping, grouping attr(s) ℑ list of pairs(R), forms groups based on the attributes on the left and calculates the aggregate function for each group.

Either way the output is again a relation (a single value, a column or a table), so closure still holds. The rename operation ρ gives the new relation a better name: ρR(myCount) ℑ COUNT propertyNo(σrent > 350(PropertyForRent)) counts the properties renting for more than 350 and calls the result R with one column myCount. With our six properties, PG4 at exactly 350 is excluded, so myCount = 5.

Grouped by branch, the Staff salaries total 54,000 for B003 (12,000 + 18,000 + 24,000), 39,000 for B005 and 9,000 for B007. Bristol has no staff, so it does not appear: grouping only sees rows that exist.

Part 6 · Sigma · Putting it together

Reading a long expression

ΠfName, lName, city( σsalary > 15000( Staff ⋈ Branch ) )

1

Start at the innermost brackets: Staff ⋈ Branch. Every staff member with their branch’s city (6 rows).

2

Then the σ around it: keep salary > 15000 (3 rows).

3

Finally the outer Π: keep only fName, lName, city.

Result

fNamelNamecity
JohnWhiteLondon
DavidFordGlasgow
SusanBrandGlasgow

SELECT fName, lName, city
FROM Staff
JOIN Branch USING (branchNo)
WHERE salary > 15000;

Reading order

SQL is written outside-in (SELECT first) but runs inside-out: FROM/JOIN → WHERE → SELECT. RA shows that order directly.

Most used

σ and Π (unary), × and θ-joins (binary). Query processing (next week) is built on these.

Remember: read RA inside-out: innermost relation first, outermost operation last.

More detail

The summary: relational algebra is the mathematical formalisation of relational databases. Tables are relations, and relations can be manipulated with RA operations that yield more relations. There are 5 basic operations (σ, Π, ∪, \, ×), 3 derived operations (intersection; joins: theta, natural, outer, semi; division) and the proposed aggregation operations. The most important are σ and Π (unary) and × and θ-joins (binary); these are used extensively in query processing, next week.

The third learning objective is to read expressions built from several operations. Work from the innermost brackets outwards, writing down the intermediate relation at each step, exactly as above. To translate to SQL: relations being joined go in FROM/JOIN, σ predicates go in WHERE, and the outermost Π becomes the SELECT list (with DISTINCT if duplicates matter).

Translating the other way is good exam practice: for any SQL query from Part 2, try writing the RA expression. A DBMS does the same internally: it turns SQL into a tree of RA operations and then rearranges it into a cheaper but equivalent tree (for example, applying σ before the join so fewer rows get joined).
