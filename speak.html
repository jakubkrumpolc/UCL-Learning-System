How a SQL statement is built

-- SQL is declarative: say WHAT you want, not HOW to get it
SELECT fName, salary    -- clause 1: what to show
FROM   Staff            -- clause 2: which table
WHERE  salary > 20000;  -- clause 3: which rows

Keyword

SELECT FROM WHERE

SQL’s own words. Any case works; we write them in CAPS.

Name

Staff  fName

Your tables and columns, spelt exactly as you created them.

Value

20000  'Glasgow'

Numbers as they are; text and dates in 'single quotes'.

Operator

>  =  <>  COUNT(*)

Compare or calculate; functions like COUNT summarise.

; ends every statement

Clause = keyword + parts

Line breaks don’t matter

-- starts a comment

Remember: a statement is a sentence: clauses are its parts, and ; is the full stop.

More detail

SQL (Structured Query Language, often said “sequel”) is the ISO-standard language for relational DBMSs. It is declarative: you describe the result you want, and the DBMS works out how to compute it. This section is the grammar you need before any command makes sense. A statement is one complete instruction to the DBMS and ends with a semicolon; phpMyAdmin’s SQL tab will run several in a row as long as each ends with one. A statement is made of clauses.

Each clause starts with a keyword (SELECT, FROM, WHERE) followed by its parts; here, three clauses make one query. Every word in a clause is one of four kinds. Keywords are SQL’s own vocabulary: case-insensitive, but written in capitals by convention so they stand out.

Names (identifiers) are your databases, tables and columns: spell them exactly as you created them, because MySQL table names can be case-sensitive on Linux servers; if a name contains a space or clashes with a keyword, wrap it in backticks, like `order`. Values (literals): numbers are written as they are (20000, 3.5); text and dates go in single quotes ('Glasgow', '2025-05-24'). Operators and functions compare (=, <>, >), calculate (+, -, *, /) or summarise many rows into one value (COUNT, SUM, AVG).

Spaces and line breaks don’t matter, so long statements are split over lines, usually one clause per line. Two dashes and a space start a comment that runs to the end of the line; /* … */ wraps a longer comment. Stored data keeps its case: 'Glasgow' and 'GLASGOW' are different stored values (although MySQL’s default settings compare text case-insensitively). The next section explains the syntax boxes used for every command, and the one after lists every command in this site.

How to read a syntax box

A light box shows a command’s general pattern. A dark box is real SQL you can run.

SELECT

Keyword. Type it exactly as shown.

table

Placeholder. Put your own name or value here.

[WHERE ...]

Optional. Use it or leave it out.

ASC | DESC

Or. Pick one of the options.

{ANY | ALL}

Must choose. One option is required.

column, ...

Repeat. As many as you need, with commas.

( ) , ;

Punctuation. Type it exactly as shown.

Worked example

This pattern:

DELETE FROM table [WHERE condition];

gives two valid statements:

DELETE FROM Staff;
DELETE FROM Staff WHERE staffNo = 'SG17';

The first leaves WHERE out (every row goes); the second fills it in.

Remember: purple = type it · orange = fill it in · grey [ ] { } | ... = notation, never typed.

More detail

Syntax boxes describe every allowed form of a command in one pattern. This site uses the same notation as the lecture slides and the MySQL Reference Manual (dev.mysql.com/doc), so once you can read it you can look up any command yourself. Light purple boxes always hold a pattern; dark boxes always hold real SQL you can paste into phpMyAdmin. In a pattern: words in purple capitals are keywords, typed exactly as shown (any case works).

Orange italic words are placeholders: replace each with something of your own, such as a table name, a column, a value or a condition. Square brackets [ ] mark an optional part: include it or leave it out. A vertical bar | means “or”: inside square brackets you may pick one option or none; inside curly braces { } you must pick exactly one. Three dots ... mean “repeat the previous part as often as you need”, usually with commas between.

Brackets can nest: [ORDER BY column [ASC | DESC]] means the whole ORDER BY clause is optional and, if you use it, ASC or DESC is optional too. Round brackets, commas and semicolons are real SQL punctuation and are typed exactly. The notation symbols themselves ([ ] { } | ...) are never typed. A second example to try: ORDER BY column [ASC | DESC], ... allows ORDER BY lName, ORDER BY salary DESC, and ORDER BY salary DESC, lName ASC.

More detail

This is every SQL command used anywhere in this site, grouped by what it does; the grey number is the section that teaches it. DDL (data definition language) creates and changes structure: databases, tables, views and indexes. DML (data manipulation language) works with the rows inside the tables: INSERT, UPDATE and DELETE change data, and SELECT reads it (some books put SELECT in its own group, DQL, the data query language). DCL (data control language) controls permissions.

TCL (transaction control language) groups changes so they all happen or none do. SHOW TABLES and DESCRIBE are MySQL helpers, not standard SQL, for looking around a database; phpMyAdmin shows the same information in its Structure tab. Everything else you will see, such as WHERE, GROUP BY, JOIN, LIKE or COUNT, is not a command on its own: these are clauses, operators and functions used inside a command, mostly inside SELECT. The SELECT syntax section shows where each one goes.

The functions used in this site are the five aggregates COUNT, SUM, AVG, MIN and MAX (section 26) and NOW(), which returns the current date and time (section 61). Every command ends with a semicolon.

Syntax: CREATE DATABASE and CREATE TABLE

CREATE DATABASE [IF NOT EXISTS] db_name;
USE db_name;
 
CREATE TABLE [IF NOT EXISTS] table (
  column TYPE [column_rules],
  column TYPE [column_rules],
  ...,
  [PRIMARY KEY (column, ...),]
  [FOREIGN KEY (column) REFERENCES parent(column)
     [ON DELETE action] [ON UPDATE action],]
  [CHECK (condition)]
);

TYPE: INT · VARCHAR(n) · DECIMAL(p,s) · DATE · DATETIME (section 17)

Column rules · after one column’s type

NOT NULL

a value is required

DEFAULT value

used when no value is given

AUTO_INCREMENT

numbers new rows 1, 2, 3… for you

UNIQUE

no two rows may repeat it

PRIMARY KEY

this one column is the key

CHECK (condition)

every value must pass the test

Table rules · after the last column

Needed when a rule names 2+ columns: PRIMARY KEY (clientNo, propertyNo).

Always write FOREIGN KEY here: MySQL ignores a REFERENCES written after one column.

action: CASCADE, SET NULL or NO ACTION (section 19).

Remember: column rules follow one column’s type; table rules come after the last column and can cover several.

More detail

The full pattern for building a database. CREATE DATABASE makes a new, empty database; IF NOT EXISTS avoids an error when it is already there. USE picks the database that the following statements work in (in phpMyAdmin, clicking a database in the left panel does the same). CREATE TABLE names the table and then lists, inside one pair of round brackets, first the columns and then any table rules, all separated by commas, with no comma after the last item and a semicolon after the closing bracket.

Each column is: name, data type, then optional column rules in any order, separated by spaces, for example salary DECIMAL(8,2) NOT NULL DEFAULT 0.

Column rules affect only that column: NOT NULL makes a value required; DEFAULT gives the value used when an INSERT leaves the column out; AUTO_INCREMENT (MySQL, integer key columns only) fills in 1, 2, 3 and so on automatically; UNIQUE forbids duplicates (a candidate key); PRIMARY KEY marks the column as the key (it implies NOT NULL and UNIQUE); CHECK tests each value (enforced from MySQL 8.0.16).

Table rules come after the columns and can name several columns: a composite primary key such as PRIMARY KEY (clientNo, propertyNo) must be written this way. FOREIGN KEY (column) REFERENCES parent(column) says each value must match an existing row in the parent table, which must already exist and the referenced column must be a key there. MySQL quietly ignores REFERENCES written as a column rule, so always use the table-rule form.

The optional ON DELETE and ON UPDATE actions decide what happens to these child rows when the parent row is deleted or its key changes (section 19). The next section fills this pattern in for the Staff table.

Build it: CREATE TABLE

CREATE DATABASE EstateAgent;   -- a new, empty database
USE EstateAgent;               -- work inside it

CREATE TABLE Staff (
  staffNo   VARCHAR(5)    PRIMARY KEY,
  fName     VARCHAR(20)   NOT NULL,
  lName     VARCHAR(20)   NOT NULL,
  position  VARCHAR(20),
  salary    DECIMAL(8,2)  CHECK (salary > 0),
  branchNo  VARCHAR(4),
  FOREIGN KEY (branchNo) REFERENCES Branch(branchNo)
);

1

Name the table, then list its columns inside ( ).

2

Each column: name, TYPE, then optional rules.

3

Commas between columns; a semicolon at the very end.

4

Create Branch first: a foreign key can only point at a table that exists.

5

Check your work: SHOW TABLES; and DESCRIBE Staff;

Remember: one column per line: name, TYPE, rules, comma.

More detail

CREATE DATABASE makes a new, empty database (you can optionally choose a character set); USE makes it the current one, so later statements apply to it. CREATE TABLE gives the table a name and lists its attributes, each with a name and data type, optionally followed by properties (constraints) such as PRIMARY KEY, NOT NULL or CHECK. Table-level constraints, such as a FOREIGN KEY or a composite PRIMARY KEY (col1, col2), go after the column list.

The Branch table it refers to would be: CREATE TABLE Branch (branchNo VARCHAR(4) PRIMARY KEY, street VARCHAR(50) NOT NULL, city VARCHAR(30) NOT NULL); Note two fixes compared with the lecture’s version: the lecture uses salary DECIMAL(5,2), which can only hold numbers up to 999.99, so a salary of 21000 would be rejected; DECIMAL(8,2) allows up to 999999.99. The lecture also stores DOB as VARCHAR; a DATE column is better because you can sort and compare dates.

You can also name a constraint, e.g. CONSTRAINT pkStaff PRIMARY KEY (staffNo), which makes it easier to drop later. In MySQL you can set the storage engine with ENGINE = InnoDB at the end; InnoDB is the default and is the one that supports foreign keys and transactions.

Choosing a data type for each column

TypeHoldsExample
INTWhole numbersrooms INT → 3
DECIMAL(p,s)Exact numbers: p digits, s after the pointsalary DECIMAL(8,2) → 18000.00
FLOATApproximate decimals (science, not money)temperature FLOAT → 21.7
CHAR(n) / VARCHAR(n)Text: exactly n chars / up to n charsCHAR(1) → 'F' · VARCHAR(20) → 'Ann'
DATE / DATETIMEA date / date + time, as 'YYYY-MM-DD'viewDate DATE → '2025-05-24'
BOOLEANTrue or false (MySQL stores 1 or 0)isActive BOOLEAN → TRUE
TEXT / BLOBLong text / binary data such as imagesdescription TEXT

Watch out: DECIMAL(5,2) only fits up to 999.99, and dates stored as VARCHAR won’t sort properly. Use DECIMAL(8,2) for salaries and DATE for dates.

More detail

Every column needs a type, which is its domain: the set of values it accepts. INT and DECIMAL are exact numeric types; DECIMAL(p,s) has precision p (total digits) and scale s (digits after the point), so DECIMAL(8,2) runs up to 999999.99. Use DECIMAL for money, because FLOAT is approximate (0.1 + 0.2 may not equal exactly 0.3). CHAR(n) always stores exactly n characters (padded), good for fixed codes; VARCHAR(n) stores up to n characters, good for names.

DATE stores year, month and day; TIME stores hours, minutes and seconds; TIMESTAMP or DATETIME stores both; INTERVAL is a length of time in standard SQL. MySQL date literals are written 'YYYY-MM-DD', so '2012-05-01', not '1-May-12' as in one lecture example. BOOLEAN can be TRUE, FALSE or UNKNOWN in standard SQL (UNKNOWN arises from NULLs); MySQL stores it as a tiny integer 1 or 0.

Large objects (CHARACTER LARGE OBJECT and BINARY LARGE OBJECT, called TEXT and BLOB in MySQL) hold long text or files; BIT(n) holds binary strings. Defaults: after the type you can add DEFAULT value, e.g. createdAt DATETIME DEFAULT CURRENT_TIMESTAMP, or expiryDate DATE DEFAULT (CURRENT_DATE + INTERVAL 21 DAY) in MySQL 8 (note: DAY, not DAYS as written on the lecture slide). The default is used whenever an INSERT doesn’t give that column a value.

Constraints: rules the database enforces

Declare a rule once; the DBMS then rejects any INSERT or UPDATE that would break it.

ConstraintSQLMeans
Required datafName VARCHAR(20) NOT NULLEvery row must have a value here
DomainCHECK (salary > 0)Values must make sense
Entity integrityPRIMARY KEY · UNIQUENo duplicates; a PK is never NULL
Referential integrityFOREIGN KEY (branchNo) REFERENCES BranchThe value must exist in Branch
GeneralCHECK (endDate > startDate)Rules involving several columns

In MySQL, CHECK is enforced from version 8.0.16. Standard SQL’s CREATE DOMAIN and CREATE ASSERTION are not available.

Remember: NOT NULL = must exist · CHECK = must make sense · PK = must be unique · FK = must point somewhere real.

More detail

Integrity constraints are properties you want the database to guarantee at all times. The lecture lists five types. Required data: a column may not contain NULL (missing data); add NOT NULL after the column. Domain constraints: values must come from an allowed set, via the data type and CHECK, e.g. CHECK (sex IN ('M', 'F')).

Entity integrity: the primary key uniquely identifies each row and is never NULL; write PRIMARY KEY after a column, or PRIMARY KEY (col1, col2) after the column list for a composite key; you can name it with CONSTRAINT name PRIMARY KEY (…). UNIQUE makes a non-key column unique too (for example email). Referential integrity: a foreign key must match an existing primary key in the parent table: FOREIGN KEY (colName) REFERENCES ParentTable(parentCol). General constraints: any other rule, written with CHECK.

Standard SQL also lets you create a reusable domain (CREATE DOMAIN SexType AS CHAR DEFAULT 'M' CHECK (VALUE IN ('M','F'))) and a database-wide assertion (CREATE ASSERTION name CHECK (condition)), but MySQL supports neither, so in MySQL you use column CHECKs instead. A CHECK that contains a subquery, like CHECK (branchNo IN (SELECT branchNo FROM Branch)), is also not allowed in MySQL; use a foreign key for that.

Part 2 · Speak · DDL

Foreign keys: what if the parent row goes?

FOREIGN KEY (branchNo) REFERENCES Branch(branchNo) ON DELETE ???
DELETE FROM Branch WHERE branchNo = 'B003';  -- Ann, David and Susan work here

NO ACTION

The default. The DELETE is refused while staff still point to B003.

Result: error

CASCADE

The change flows down: Ann, David and Susan are deleted too.

Result: 3 staff rows gone

SET NULL

The staff rows stay, but their branchNo becomes NULL.

Result: no branch

SET DEFAULT

Their branchNo becomes the column’s default value.

Not in MySQL’s InnoDB

The same options work for ON UPDATE: with ON UPDATE CASCADE, renaming B003 to B033 updates every staff row too.

Remember: CASCADE = like a waterfall, the change flows down to the children.

More detail

A foreign key creates a parent–child link: Branch is the parent, Staff rows are children. The question is what should happen to the children when the parent row is deleted or its primary key changes. You choose with ON DELETE … and ON UPDATE … after the REFERENCES clause; you can set them independently, e.g. ON DELETE SET NULL ON UPDATE CASCADE. NO ACTION (the default; RESTRICT behaves the same in MySQL): the delete or update fails because dependent rows exist.

CASCADE: on delete, the child rows are deleted as well, which may in turn cascade to their own children; on update, the children’s foreign key values change to the new value. SET NULL: the children keep existing but their foreign key becomes NULL, so the column must allow NULL. SET DEFAULT: the foreign key is set to the column’s default; standard SQL allows it, but MySQL’s InnoDB engine rejects it.

Pick the option that matches reality: deleting an auction item should probably delete its bids (CASCADE), but deleting a branch should probably not silently delete staff (NO ACTION or SET NULL).

Syntax: change, empty or remove a table

ALTER TABLE table action;   -- where action is one of:

ADD [COLUMN] column TYPE [rules]

add a new column

DROP [COLUMN] column

remove a column and all its values

MODIFY [COLUMN] column TYPE [rules]

change its type or rules (MySQL)

ALTER [COLUMN] column SET DEFAULT value

set the value used when none is given

ADD FOREIGN KEY (col) REFERENCES parent(col)

add a rule to an existing table

-- e.g. ALTER TABLE Staff ADD COLUMN email VARCHAR(50);

DELETE FROM table
[WHERE condition];

Removes rows: all of them if there’s no WHERE. The table stays.

TRUNCATE [TABLE] table;

Removes every row, fast. No WHERE allowed. The table stays.

DROP TABLE [IF EXISTS] table;

Removes the table itself: its structure and all its data.

Remember: DELETE empties the box; DROP throws the box away.

More detail

ALTER TABLE changes the design of a table that already exists, without losing its rows. Each action is one change; you can list several, separated by commas. Examples on the Staff table: ALTER TABLE Staff ADD COLUMN email VARCHAR(50); adds a column (existing rows get NULL, or the DEFAULT if you give one). ALTER TABLE Staff DROP COLUMN email; removes it again, with its data. ALTER TABLE Staff MODIFY position VARCHAR(30) NOT NULL; changes a column’s type or rules (MySQL’s keyword; standard SQL uses ALTER COLUMN).

ALTER TABLE Staff ALTER position SET DEFAULT 'Assistant'; gives a default (DROP DEFAULT removes it). ALTER TABLE Staff ADD FOREIGN KEY (branchNo) REFERENCES Branch(branchNo); adds a constraint afterwards, which is handy when two tables refer to each other. MySQL 8 also has RENAME COLUMN old TO new. The three ways to remove things are easy to mix up. DELETE FROM is DML: it removes rows that match the WHERE, or all rows if there is none, and can be undone inside a transaction.

TRUNCATE TABLE removes every row at once, faster, and resets AUTO_INCREMENT back to 1. DROP TABLE removes the table itself; IF EXISTS avoids an error when it is not there. DROP DATABASE name removes a whole database, so use it with care. A table that other tables point to with foreign keys cannot be dropped first: drop the child tables, or remove their foreign keys, before the parent.

MySQL tables use the InnoDB storage engine by default, which supports foreign keys and transactions; the older MyISAM engine does not.

Syntax: INSERT, UPDATE and DELETE

INSERT INTO table [(column, ...)]
VALUES (value, ...) [, (value, ...) ...];

Values pair up with the listed columns, in order. A column you leave out gets its DEFAULT, NULL or the next AUTO_INCREMENT number. More ( ) groups add more rows.

UPDATE table
SET column = value [, column = value ...]
[WHERE condition];

Changes values in existing rows. value can use the old value, like salary * 1.03. Only rows that pass the WHERE change.

DELETE FROM table
[WHERE condition];

Removes whole rows that pass the WHERE. To blank one value instead, use UPDATE … SET column = NULL.

Test first: run SELECT * FROM table WHERE condition; to see exactly which rows will change.

Remember: INSERT adds rows, UPDATE changes values, DELETE removes rows. Only INSERT has no WHERE.

More detail

The three commands that change data. INSERT INTO adds new rows. The column list is optional, but always write it: without it you must give a value for every column in the table’s exact order, and your INSERT breaks as soon as someone adds a column. Values are matched to columns by position, so the first value goes in the first listed column. Columns you leave out get their DEFAULT, or NULL, or for an AUTO_INCREMENT key the next number; a NOT NULL column without a default must be listed.

Text and dates go in single quotes. You can add several rows in one statement: VALUES (...), (...), (...);. UPDATE changes values in rows that already exist. SET lists one or more column = value pairs, separated by commas; the value can be an expression using the old value, such as salary = salary * 1.03. DELETE FROM removes whole rows; you never name columns in a DELETE.

Both UPDATE and DELETE are controlled by WHERE, which works exactly like the WHERE in a SELECT (section 25): only rows that pass the test are touched, and with no WHERE every row is. That is why the safe habit is to write the WHERE as a SELECT first, check the rows it returns, and then turn it into the UPDATE or DELETE. Foreign keys still apply: an INSERT with a branchNo that does not exist in Branch is rejected, and a DELETE of a parent row follows the ON DELETE rule (section 19).

The next section shows all three filled in.

Add, change and remove rows

INSERT

Adds a row. Values follow the column order.

INSERT INTO Staff (staffNo, fName, lName, position, salary, branchNo)
VALUES ('SG17', 'Joe', 'Brown', 'Manager', 21000, 'B003');

UPDATE

Changes existing rows. Here: a 3% raise for managers.

UPDATE Staff
SET salary = salary * 1.03
WHERE position = 'Manager';

DELETE

Removes rows. Here: just Joe.

DELETE FROM Staff
WHERE staffNo = 'SG17';

No WHERE = every row. UPDATE Staff SET salary = 0; zeroes everyone.

CRUD: Create, Read, Update, Delete = INSERT, SELECT, UPDATE, DELETE.

More detail

The four main DML statements are INSERT, SELECT, UPDATE and DELETE, matching the classic CRUD operations: create, read, update, delete. INSERT INTO Table (columns) VALUES (values) adds one row; the values must be in the same order as the column list, and text and dates go in single quotes while numbers don’t. You can insert several rows at once by listing several bracketed groups separated by commas. Columns you leave out get their DEFAULT value or NULL.

To load many rows from a file, MySQL has LOAD DATA LOCAL INFILE 'staff.txt' INTO TABLE Staff; in phpMyAdmin you can use the Import tab instead. UPDATE … SET … changes values in existing rows; the new value can be calculated from the old one (salary = salary * 1.03). DELETE FROM … removes rows. Both UPDATE and DELETE apply to every row that matches the WHERE clause, and to every row in the table if there is no WHERE at all, which is the most common beginner disaster.

A safe habit: first run SELECT * FROM Staff WHERE … with the same condition, check which rows come back, then change SELECT * to DELETE.

Remember the written order: Some French Waiters Grow Healthy Oranges Lazily.

More detail

Every query is one SELECT statement built from the same seven clauses, always written in this order: SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. Only SELECT and FROM are required. Part by part: SELECT lists what each result row shows, separated by commas. Each item is an expression: a column (fName), a calculation (salary / 12), an aggregate (COUNT(*)), or * for every column. DISTINCT removes duplicate result rows. AS gives an item a new name (an alias) for the result’s heading.

FROM names the table to read; give it a short alias (FROM Staff s) and add JOIN clauses to combine more tables (section 28). WHERE keeps only rows whose condition is true; conditions use comparisons, AND, OR, NOT, BETWEEN, IN, LIKE and IS NULL (section 25). GROUP BY makes one group for each different value; HAVING then keeps only groups whose condition is true (section 27). ORDER BY sorts by one or more expressions, each ASC (ascending, the default) or DESC.

LIMIT is MySQL’s way to return only some rows: LIMIT 3 gives the first three; LIMIT 0, 30 skips 0 rows and returns 30, which is what phpMyAdmin adds to the lab’s S7 query (LIMIT 30 OFFSET 0 means the same). The key insight that the lecture doesn’t spell out: the DBMS evaluates the clauses in a different order: FROM (and joins) first, then WHERE, GROUP BY, HAVING, SELECT, ORDER BY and finally LIMIT. That explains rules that otherwise seem arbitrary.

An aggregate such as AVG can’t appear in WHERE, because WHERE runs before rows are grouped; use HAVING or a subquery. A column alias made in SELECT (salary/12 AS monthlySal) can’t be used in WHERE, because SELECT hasn’t run yet, but it can be used in ORDER BY, which runs afterwards (MySQL also allows aliases in HAVING). The mnemonic adds L for LIMIT to the classic one.

More detail

Aggregation means calculating one value over a set of rows. The ISO standard defines five aggregate functions: COUNT (number of rows or values), SUM (total), AVG (average), MIN (smallest) and MAX (largest). You can combine them in one query and rename them: SELECT MIN(salary) AS lowest, MAX(salary) AS highest, AVG(salary) AS average FROM Staff; returns one row: 9000, 30000, 17000.

More detail

A join builds wider rows by gluing together rows from two tables that match. The pattern: FROM names the first table; each JOIN adds one more table, and its ON condition says which rows belong together. Aliases: after a table name you can write a short nickname, with or without AS (FROM customers AS c, or FROM customers c). From then on you write c.custID instead of customers.custID.

You must prefix a column with its table or alias whenever more than one table has a column of that name, otherwise MySQL stops with “Column 'custID' in field list is ambiguous”. The ON condition is almost always foreign key = primary key, following the arrows in the ER diagram. Join types: JOIN and INNER JOIN mean the same thing and keep only rows that have a partner in both tables.

LEFT JOIN (or LEFT OUTER JOIN) keeps every row of the table on the left, filling the other side with NULL when there is no match; RIGHT JOIN does the same for the right-hand table; MySQL has no FULL OUTER JOIN (section 30). To use more than two tables, chain joins: each new JOIN connects to a table already in the query. The Shop lab needs this: customers link to orders by custID, orders to lineitems by orderID, and lineitems to items by itemID.

Two other forms: USING (column) is a shortcut for ON a.column = b.column when both tables call the column the same thing. The older comma style lists tables in FROM, separated by commas, and puts the matching condition in WHERE; it gives the same result as an INNER JOIN, and it is what the lab’s S7 query uses. If you forget the WHERE condition with the comma style, every row is paired with every other row (a Cartesian product), which is the classic beginner bug.

After the joins, WHERE, GROUP BY and ORDER BY work exactly as on a single table.

More detail

A subquery (also called a nested or inner query) is a complete SELECT statement written inside round brackets where a value or a list would normally go. The DBMS works it out first and uses its answer in the outer query, so read subqueries inside-out. What the inner query must return depends on where it sits.

After a comparison operator (=, <>, <, >, <=, >=) it must return exactly one value, one row and one column, like SELECT AVG(salary) FROM Staff or SELECT MAX(quantity) FROM lineitems; if it returns several rows, MySQL stops with “Subquery returns more than 1 row”. After IN or NOT IN it must return one column, which is treated as a list of values.

After a comparison followed by ANY (or its synonym SOME) or ALL it also returns one column: > ANY means greater than at least one value in the list, > ALL greater than every value. After EXISTS the columns don’t matter at all: EXISTS is true if the subquery returns at least one row, so people often write SELECT * inside it. A subquery that refers to a table from the outer query is correlated and is re-run for each outer row (section 33).

Subqueries can also go in HAVING (keep groups compared with a computed value) and in FROM, where the result acts as a temporary table and must be given an alias. Set operations are different: they don’t nest one query inside another but combine the results of two complete queries. UNION gives rows in either result, INTERSECT rows in both, EXCEPT rows in the first but not the second. Both queries must return the same number of columns with compatible types. Duplicates are removed unless you add ALL.

INTERSECT and EXCEPT exist in MySQL from version 8.0.31; on older servers use IN or NOT IN subqueries instead.

ANY (also spelled SOME) and ALL let you compare one value with every value in a one-column list returned by a subquery. salary > ANY (list) is true if the comparison holds for at least one value in the list, which for “greater than” means greater than the smallest value. salary > ALL (list) is true only if it holds for every value, meaning greater than the largest. More detail

Each card shows the pattern (light box) and a filled-in example (dark box). Views give users a slice of the database suited to their needs (the external level from section 8). CREATE VIEW name AS followed by any SELECT saves that query under a name; afterwards you can SELECT from the view as if it were a table, and DROP VIEW name removes it. Views are convenient and useful for security (show only some columns), but there are limits on updating data through a view, and some performance overhead.

The lecture notes you probably won’t need them for the small coursework database. An index is an extra data structure that makes lookups and sorting on a column much faster: CREATE [UNIQUE] INDEX name ON table (column, ...); UNIQUE also forbids duplicate values. Primary keys are indexed automatically; the trade-off is extra storage and slower inserts and updates. A transaction bundles statements so they are committed or rolled back as a set.

START TRANSACTION begins it; COMMIT makes every change permanent; ROLLBACK undoes every change since the start. The bank transfer is the classic example: taking £100 from one account without adding it to the other must never happen. Transactions have the ACID properties: Atomic (all or nothing), Consistent (rules still hold afterwards), Isolated (concurrent transactions don’t see each other’s half-finished work) and Durable (once committed, it survives a crash). They are covered properly in Weeks 3–6.

Permissions: GRANT privileges ON object TO account; and REVOKE privileges ON object FROM account;. Privileges include SELECT, INSERT, UPDATE, DELETE, REFERENCES and ALL PRIVILEGES. In MySQL, accounts are written 'name'@'host', for example 'reception'@'localhost'.

More detail

This is the SQL lab (the sheet is headed COMP0022; it isn’t marked, and solutions go up on Moodle at the end of week 2). You query a small MySQL database called Shop through phpMyAdmin, a web interface for MySQL. Log in with the username and password printed on the sheet, click the Shop database in the left-hand pane to see its tables, open the SQL tab, type a query and press Go. Before writing queries, click each table and open its Structure tab (column names and types) and Browse tab (sample rows).

The sheet names customers, orders and lineitems; the table that holds item descriptions and prices isn’t named on the sheet, so “items” here is a placeholder: use whatever name you see. The sheet’s first example answers “who ordered an S7?”. It lists three tables after FROM separated by commas, which pairs every row of each with every row of the others (a Cartesian product), and the WHERE conditions keep only the combinations whose keys match. That is exactly an inner join written the old way.

The same query in the JOIN style from section 29: SELECT o.orderID, c.custID, c.firstname, c.familyname FROM orders o JOIN lineitems l ON l.orderID = o.orderID JOIN customers c ON c.custID = o.custID WHERE l.itemID = 'S7'; Columns that exist in two tables (orderID, custID) must be prefixed with the table name or alias; firstname and familyname exist only in customers, so they don’t need one. LIMIT 0 , 30 means skip 0 rows and return at most 30; phpMyAdmin adds it for paging, and you can delete it.

The second example, SELECT state, COUNT(custID) FROM customers GROUP BY state, makes one group per state and counts the customers in each (section 27).

More detail

These are worked approaches for questions 1–4 of the SQL lab, so you can check your own attempts. Try each one yourself first, then compare. Table and column names come from the sheet where it gives them (customers, orders, lineitems, custID, firstname, familyname, state, itemID, quantity); the item table and its price column are not named on the sheet, so adjust them after checking Structure. Q1 is a plain filter (section 25).

The state column may hold a code (AZ) or the full name (Arizona), so Browse the customers table first; text comparison in MySQL is case-insensitive by default. Q2: an order’s value is the sum over its line items of quantity × unit price. SUM can take an expression, so multiply inside it. If the price is stored in lineitems itself (a price at the time of sale), you don’t need the join. Q3 asks for EXISTS (section 33): for each customer c, the subquery looks for at least one of their order lines with quantity above 2.

Because each line item is one item in one order, “more than 2 of the same item in a single order” is just quantity > 2. COUNT(*) then counts the customers that pass. An equivalent without EXISTS is SELECT COUNT(DISTINCT o.custID) FROM orders o JOIN lineitems l ON l.orderID = o.orderID WHERE l.quantity > 2; DISTINCT matters because one customer can have several such lines. Q4 is the sheet’s own example plus sorting: ORDER BY can use the alias from SELECT (customers here), and DESC sorts largest first.

Memory hook: filter rows with WHERE, count groups with GROUP BY, sort last with ORDER BY.

Q5: a question inside a question

Who ordered 2+ different items, and how many of each?

SELECT c.firstname, c.familyname, l.itemID,
       SUM(l.quantity) AS howMany
FROM customers c
JOIN orders o    ON o.custID  = c.custID
JOIN lineitems l ON l.orderID = o.orderID
WHERE c.custID IN (
    SELECT o2.custID FROM orders o2
    JOIN lineitems l2 ON l2.orderID = o2.orderID
    GROUP BY o2.custID
    HAVING COUNT(DISTINCT l2.itemID) >= 2)
GROUP BY c.custID, c.firstname, c.familyname, l.itemID;

Build it in two steps

1

Inner query: who qualifies?

One group per customer; keep groups with 2+ different itemIDs.

2

Outer query: show the detail

For those customers only, one row per customer and item.

COUNT(DISTINCT x) counts different values, not rows: S7, S7, U2 counts as 2.

Remember: big question? Answer the inner question first, then wrap it.

More detail

Question 5 asks two things at once: which customers ordered at least two different kinds of item, and, for each of them, how many of each item they bought. A single GROUP BY can’t do both, because the filter is about the customer as a whole while the output is per customer and item. So answer the inner question first and run it on its own: SELECT o2.custID FROM orders o2 JOIN lineitems l2 ON l2.orderID = o2.orderID GROUP BY o2.custID HAVING COUNT(DISTINCT l2.itemID) >= 2; returns the qualifying customer IDs.

HAVING filters groups (section 27), and COUNT(DISTINCT itemID) counts different items rather than order lines, so a customer who bought S7 three times on separate orders still counts as 1 kind. Then wrap it: the outer query joins customers to their order lines, keeps only the customers IN that list (section 32), and groups by customer and item so SUM(quantity) gives how many of each item they bought across all their orders.

MySQL’s default ONLY_FULL_GROUP_BY mode wants every non-aggregated SELECT column either in GROUP BY or determined by it, which is why firstname and familyname are listed in GROUP BY alongside custID. The inner query uses different aliases (o2, l2) to avoid confusing it with the outer tables; it doesn’t refer to the outer query, so it is not correlated and runs once. Sort the output with ORDER BY c.familyname, l.itemID if you like.

Q6 · Umbrella buyers per state

LIKE + DISTINCT

SELECT c.state,
  COUNT(DISTINCT c.custID) AS buyers
FROM customers c
JOIN orders o ON o.custID = c.custID
JOIN lineitems l ON l.orderID = o.orderID
JOIN items i ON i.itemID = l.itemID
WHERE i.description LIKE '%umbrella%'
GROUP BY c.state;

DISTINCT stops a customer who bought two umbrellas being counted twice.

More detail

Q6: to know which item is an umbrella you need the item description, so the query joins all four tables: customers → orders → lineitems → items, following each foreign key. LIKE '%umbrella%' matches any description containing the word, whatever comes before or after (% means “any characters”, section 25); in MySQL, LIKE is case-insensitive with the default collation, so it also matches “Umbrella”. If you know the umbrella’s itemID from Browse, WHERE l.itemID = '…' is simpler and skips the items join.

Grouping by state gives one row per state; COUNT(DISTINCT c.custID) counts different customers, because the join produces one row per matching order line and a customer who bought umbrellas twice would otherwise be counted twice. States with no umbrella buyers don’t appear, which is what the question asks. Q7: the subquery (SELECT MAX(quantity) FROM lineitems) returns a single number, so it can be compared with = (a scalar subquery, section 32).

Every order line with that quantity is returned, including ties; the sheet hints there may be three. Sorting with ORDER BY quantity DESC LIMIT 1 is a common mistake here because it returns only one row even when several share the top value. An alternative is WHERE l.quantity >= ALL (SELECT quantity FROM lineitems), using ALL from section 33.
