Why not just use files?

Before: every app keeps its own files

Sales app

sales.csv

HR app

staff.xlsx

Lettings app

lets.txt

  • The same data is copied in many places
  • Copies drift out of sync
  • Different formats, hard to combine

After: one shared database

Sales app

HR app

Lettings app

DBMS + one shared database

  • Each fact is stored once, in one format
  • Every app sees the same, current data
  • Rules, security and backups in one place

Remember: a database is one shared “source of truth” instead of many private copies.

More detail

Before databases, the common approach was the file-based system: each application defined its own data format and kept its own files, unaware of the others. Imagine an estate agent where the sales team, HR and the lettings team each keep a list of staff. When someone changes branch, one list gets updated and the others don’t, so the data becomes inconsistent. Combining information (for example “which staff manage the most properties?”) is hard because the files use different formats.

A database centralises the data so it is stored and managed in one place, with one standard format and minimal duplication. Every organisation produces data (employees, products, sales) and behind nearly every web application there is a database holding users, posts, settings and so on.

Database vs. DBMS

Database

A shared collection of related data, plus a description of that data (its schema).

DBMS

Database Management System: the software that defines, creates, maintains and controls access to a database. MySQL is one.

What a DBMS does for you

Access: one language (SQL) to read and change data

Speed: indexes and query optimisation

Security: who may see or change what

Integrity: rules the data must always obey

Recovery: survives crashes and failed updates

The price: more size, complexity and sometimes cost.

Remember: the database is the books; the DBMS is the librarian who files, finds, guards and repairs them.

More detail

Two textbook definitions from the lecture. A database is “a shared collection of logically related data (and a description of this data), designed to meet the information needs of an organisation”, or more briefly “a self-describing collection of integrated records”. The description of the format is called the schema. A DBMS is “a software system that enables users to define, create, and maintain a database and that provides controlled access to this database”.

In everyday speech people say “the database” for both, but in exams keep them separate. Products: relational DBMSs include MySQL and MariaDB (open source; MySQL is used in this module with the phpMyAdmin web interface), PostgreSQL, SQLite, Oracle, Microsoft SQL Server and IBM Db2. Relational databases are the oldest mature type and still dominant; before them came hierarchical databases, and modern alternatives include document databases such as MongoDB, which store JSON documents instead of tables.

The lecture lists MongoDB among open-source products, but note it is not relational. To work with any DBMS you need a data definition language (DDL) and a data manipulation language (DML); for relational databases SQL is both. Cloud providers (AWS, Azure, Google Cloud) also offer “database as a service”.

The relational model: data lives in tables

Staff

staffNofNamepositionsalarybranchNo
SL21JohnManager30000B005
SG37AnnAssistant12000B003
SG14DavidSupervisor18000B003
SA9MaryAssistant9000B007

Written as a schema: Staff (staffNo, fName, position, salary, branchNo). The underlined column is the primary key.

Table · relation

One kind of thing: Staff, Branch. Named in UpperCamelCase.

Column · attribute

One property, like salary. Its allowed values are its domain. lowerCamelCase.

Row · record · tuple

One instance: one staff member.

Degree · cardinality

Number of columns · number of rows. Here: 5 and 4.

Remember: Degree goes across (columns); Cardinality Counts down (rows).

More detail

In a relational database the basic unit is a two-dimensional table, a lot like a spreadsheet tab, but stricter: every row has the same columns, each cell holds one value, and each column only accepts values from its domain (for example salary must be a number). One table represents one kind of thing (an entity such as Staff) or a relationship. The formal words come from maths: a table is a relation, a row is a tuple, and a column is an attribute. Degree is the number of columns; cardinality is the number of rows.

Every table has a primary key: an attribute (or set of attributes) that uniquely identifies each row; in schema notation it is underlined, as in Branch (branchNo, street, city, postcode). A database is a set of such tables. To build one you must define the columns and their domains (data definition) and then fill the tables with rows (data manipulation). Why tables?

They are simple, regular and easy to analyse, and the relational model is backed by a formal theory (relational algebra), standardised by SQL and implemented by many products.

Keys link the tables together

Staff

staffNofNamebranchNo
SG37AnnB003
SG14DavidB003
SL21JohnB005

Staff.branchNo holds a value that must exist in Branch.branchNo

Branch

branchNocity
B003Glasgow
B005London
B007Aberdeen

Primary key (PK)

The column(s) chosen to identify each row. Unique, never empty.

Foreign key (FK)

A column holding another table’s PK, so rows can link up.

Candidate key

Anything that could be the PK, like staffNo or email.

Composite key

A key made of 2+ columns together, e.g. (clientNo, propertyNo).

Remember: PK = your passport number. FK = someone else writing your passport number down to refer to you.

More detail

Keys are what make a set of separate tables behave like one connected database. The primary key (PK) is the one way you have chosen to identify a row: no two rows may share it and it may never be NULL (missing). A candidate key is any attribute, or minimal set of attributes, that could serve as the PK (staffNo, or an email address if every staff member has a unique one); you pick one of them to be the PK.

A composite key is a key made of several columns that only identify a row together: in a Viewing table, clientNo alone repeats and propertyNo alone repeats, but the pair (clientNo, propertyNo) is unique. A foreign key (FK) is a column in one table that stores the primary key of a row in another table. Here Staff.branchNo stores a Branch’s branchNo, which is how we know Ann works at the Glasgow branch without copying “Glasgow” into the Staff table.

The DBMS can enforce that every FK value really exists in the parent table (referential integrity, section 18).

Three levels of abstraction

1 · External level: views

What each user or app sees. Payroll sees names and salaries; reception sees names and phone numbers only.

2 · Conceptual level: the schema

Every table, column, key and rule, with no storage details. One for the whole database.

3 · Internal level: storage

How the data physically sits on disk: files, indexes, data structures and algorithms.

Why layers?

You can change one level without breaking the others. This is called data independence.

  • Move data to a faster disk: apps don’t change.
  • Add a column: existing views still work.

Remember: a restaurant. Menu = external, recipe book = conceptual, pantry = internal.

More detail

This is the classic three-tier (ANSI/SPARC) architecture of a DBMS. The external level holds views and subschemas: each user or application gets the part of the data it needs, and details it shouldn’t see are hidden. The conceptual level is the full logical description of the database (all tables, columns, constraints) without platform-specific details. The internal or physical level is how data is actually stored: file layouts, indexes, data structures and algorithms.

Each layer hides the details of the one below, so you can change one with minimal impact on the others (reduced coupling). This gives you the flexibility of specialised applications plus centralised storage. Vocabulary warning: the lecture also defines three kinds of schema used in design. A conceptual schema describes data independently of the type of database (this is the ER diagram in Part 3). A logical schema describes it for a specific type of database; for a relational database, that is the full set of tables.

A physical schema is how it is stored on a particular machine. So the word “conceptual” appears in both lists with slightly different meanings.

Where the database lives in a web app

1 · Browser

Shows pages and sends requests, like “show my bids”.

HTTP request

HTML page

2 · App server

Your code (PHP, Python…): checks input, sends SQL, builds the page.

SQL query

rows

3 · Database server

The DBMS (MySQL): runs the SQL and stores the data safely.

Inside the DBMS

Query processor: turns SQL into low-level steps
Database manager: security, rules, optimising, recovery
File manager: reads and writes the disk

In the cloud

Database as a Service (DBaaS): AWS, Azure or Google Cloud run the database server for you; you configure it and connect.

Remember: the browser never talks to the database directly; your app server does.

More detail

Multi-user databases settled on a client–server architecture. In the three-tier version used by web apps: the thin client (a web browser) only displays pages and handles the user interface; the application server holds all the application logic and handles requests; and the data server stores and retrieves data. In very busy systems the data server can be split further into a transaction manager (queues and schedules updates, handles rollbacks) and a resource manager (reads and writes files).

Inside the DBMS, the lecture names three common parts: the query processor (translates queries into low-level instructions), the database manager (a large component handling authorisation, integrity checks, query optimisation, scheduling, failure recovery and temporary storage) and the file manager (stores data and auxiliary structures on disk, talking to the operating system). Cloud computing is “on-demand network access to a shared pool of configurable computing resources”.

The traditional model is to install the DBMS on your own machines; the trend is database as a service (DBaaS), a kind of software as a service, where the provider hosts the database and you configure it remotely. You will see this tier picture again in Part 4, where we build a small app.
