Part 13 · Objects

The translation tax

What the relational model makes awkward

Normalisation flattens composite values into simple columns and extra tables. The application then rebuilds the objects on every read and flattens them on every write. That repeated translation is the impedance mismatch.

Two directions, and a middle

SystemWhat was added
Object databasepersistence, added to an object language such as Java or C++
Object-relational DBMSobject features, added to a relational database
Relational DBMSneither, by itself

An object database is still well structured. Unlike XML, the classes are known. Unlike a relational schema, a class can contain structure and behaviour.

Remember: Impedance mismatch is the cost of rebuilding objects from rows on every trip. An object database stores the objects.

More detail

The lecture draws the bridge both ways. Starting from the language and adding a database gives an OODB. Starting from the database and adding objects gives an object-relational system. Exams like that distinction.

Source: Lecture 9b, drawbacks of relational databases and the two directions.

Part 13 · Objects

Classes, extents, and an identity that is not a key

ODL

The Object Definition Language describes classes in a portable text that looks like a C++ header: attributes, relationships, and the operations. An extent is the set of all persistent objects of a class, the nearest thing to a table. A key can still be declared.

class Branch
(extent branchOffices key branchNo) {
  attribute string branchNo;
  relationship Manager ManagedBy;
}

What a programming language does not already have

  • Every object has an OID, a permanent identity. Two objects with the same field values are still different objects. A primary key is a value. An OID is not.
  • The database tracks the schema: classes, attributes, relationships, and the exceptions operations can raise.
  • Objects are made persistent by reaching them from a named root, or by being created as persistent. Ordinary local variables die with the method.

Remember: An extent is the set of objects of a class. An OID identifies an object independently of its field values.

More detail

The ODMG object model is the lecture’s standard for what an object database is allowed to contain. ODL is how you write that model down. You are not expected to memorise the whole syntax. You are expected to read a class, its extent and a relationship.

Source: Lecture 9b, ODL and object identity.

Part 13 · Objects

SQL that can follow a pointer

From the lecture’s DreamHome schema

SELECT b.branchNo
FROM b IN branchOffices
WHERE b.address.city = "London";

branchOffices is the extent. b.address.city walks from the branch into its address object. No join is written.

A few more shapes

  • The extent name alone is a query: staff is all staff.
  • A relationship is a path: branchOffices.ManagedBy is the managers.
  • SELECT struct(lName: s.lName, age: s.age) builds a value with no identity.
  • Aggregates work, and unlike SQL they can appear in the WHERE of a nested query.
  • GROUP BY still exists, for an average salary per branch.

Remember: OQL looks like SQL, but a path such as b.address.city replaces a join, and an extent replaces a table.

More detail

Design still starts from an enhanced ER diagram. Entities become classes, and a primary key is no longer the only identity, because the OID exists. The diagram also shows behaviour, so it looks like a class diagram. The lecture’s warning on storage: objects live in a program’s heap, and writing that heap to disk, in a form another program can read, is the unsolved-looking part.

Source: Lecture 9b, the OQL examples and designing an object database.
