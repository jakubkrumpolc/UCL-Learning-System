Part 11 · Spread

Split the data, not just the work

The definition

A distributed database is one logical database stored at several sites on a network. A distributed DBMS manages it and hides some of that split. Each site has its own DBMS. They talk to each other.

Distributed processing is different: many programs share the work, but the data still sits in one place.

Why bother, and why it hurts

  • More sites can mean better availability, growth by adding cheap machines, and data near the people who use it.
  • The same features are harder: transactions, integrity, and a single schema, now across a network that can fail.
  • A heterogeneous system mixes DBMS products and must translate. A homogeneous one does not.

Remember: A distributed database is one logical database physically split across a network. Distributed processing still keeps the data in one place.

More detail

Not every site has to store a fragment. Some only run applications and request data. The lecture’s diagram is a mix of sites with fragments and sites without.

Source: Lectures 7–8, definitions, structure, advantages and disadvantages.

Horizontal, vertical, mixed, derived

How a table is cut

FragmentDefined byPut back with
Horizontala selection, so each fragment is a subset of the rowsunion
Verticala projection, so each fragment is a subset of the columnsnatural join. Every fragment keeps the key
Mixedselections and projections in sequencethe matching unions and joins
Derived horizontala semijoin, splitting a child table according to its parentunion

Where the fragments go

The aim is locality: data sits near the queries that use it, so the network stays quiet.

SchemeIdea
Centralisedone site stores everything. Simple, and a single point of failure.
Partitionedeach fragment lives at exactly one site. No copies.
Replicatedcopies of fragments live at several sites. Reads are local. Writes must reach the copies.

Remember: Horizontal fragments are selections, glued back with union. Vertical fragments are projections that keep the key, glued back with a natural join.

More detail

The comparison the lecture draws is qualitative. Centralised placement has the worst communication and the least reliability. Full replication has the best locality and availability and the highest storage cost. Partitioning sits between them.

Source: Lectures 7–8, fragmentation and allocation.

Part 11 · Spread

The user should not have to know

The transparencies

  • Fragmentation: the user does not know the table is split.
  • Location: the user does not know which site holds a fragment.
  • Replication: the user does not know there are copies.
  • Transaction: a transaction that touches several sites still commits or aborts as a whole.
  • Failure, concurrency, performance, DBMS: crashes, interleaving, speed and foreign products are hidden too.

Date’s rule, shortened

To the user, a distributed database should look like one that is not distributed. The lecture lists twelve rules under that principle. The ones to be able to say are local autonomy, location independence, fragmentation independence, replication independence, and distributed query processing.

Transparency is not free. Hiding the split makes administration and tuning harder, and not every designer wants every transparency.

Remember: Transparency means the user does not see the split: not the fragments, not the sites, not the copies.

More detail

Distribution transparency has levels. Fragmentation transparency is the strongest: you name the table, and the DBMS finds the pieces. If you must name the fragments yourself, you have lost that level.

Source: Lectures 7–8, transparencies and Date’s 12 rules.

Part 11 · Spread

Move the small result, not the big table

The lecture’s query

Property, 10,000 rows, lives in London. Viewing, 1,000,000 rows, lives in London. Client, 100,000 rows, lives in Glasgow. Find Aberdeen properties viewed by clients whose budget exceeds £200,000.

Each tuple is 100 characters. The network moves 10,000 characters a second, and every message pays a 1-second delay. Computation is treated as free beside communication.

Only 10 clients qualify, and there are 100,000 Aberdeen viewings.

Two strategies you can cost by hand

Shipping every client row to London moves 100,000 × 100 characters.

10,000,000 / 10,000 = 1,000 seconds
plus 1 second delay
= 1,001 seconds

Selecting the 10 clients in Glasgow and shipping only those moves 1,000 characters.

1,000 / 10,000 = 0.1 seconds
plus 1 second delay
= 1.1 seconds

Same answer. The second plan does the selection where the table already is, and the network carries the tiny result.

Remember: Communication time is the delay plus the characters divided by the transfer rate. Filter before you ship.

More detail

The lecture then replaces each table in the algebra tree by the union or join of its fragments, and pushes selections into the fragments that can possibly qualify. A fragment defined as “not flats” can be deleted from a query that asks only for flats. Statistics then estimate which of the remaining transfers is cheapest.

Source: Lectures 7–8, the distributed query example and the assumptions on page 40.

Part 11 · Spread

Every site votes, then every site commits

Two-phase commit

A transaction that wrote at several sites needs one decision. The coordinator sends PREPARE. Each participant votes COMMIT or ABORT. If every vote is commit, the coordinator sends COMMIT. One abort, and it sends ABORT.

Participants write a Ready record before voting, and a final commit or abort record when the decision arrives. The coordinator writes Begin Commit, then the decision, then End of Transaction.

It can block

If the coordinator dies after a participant has voted but before the decision arrives, that participant cannot safely commit or abort. It has promised to obey a decision it cannot see. Two-phase commit is a blocking protocol. Three-phase commit is the lecture’s named way around that, at more cost.

On restart, the log says what to do. No decision recorded: abort, or start the vote again. A decision recorded: resend it. A participant with Ready and no decision: ask, and wait.

Remember: Two-phase commit is a vote, then a decision. A participant that has voted and not heard back must wait. That wait is the blocking.

More detail

Replicas make the same problem worse: an update should reach every copy, but a copy may be down. Waiting for every copy sacrifices availability. Updating the copies you can reach, and repairing the rest later, sacrifices an immediate consistent read. That trade-off returns as CAP in Part 14.

Source: Lectures 7–8, two-phase commit and recovery from the log.
