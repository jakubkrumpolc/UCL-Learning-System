Connect, query, fetch, close

The shape of a PHP query

Tutorial 4’s strategy is four steps. Connect. Build a SQL string. Run it. Read the rows.

$c = mysqli_connect('localhost', 'user', 'secret', 'db');
$r = mysqli_query($c, 'SELECT first_name FROM Users');
$row = mysqli_fetch_array($r);
mysqli_close($c);

Check the connection. Root should not be the account the website uses. Close the connection when the page is done.

Input is still not SQL

Part 4 already says not to glue a typed string into a query. Tutorial 4 shows mysqli_real_escape_string as a minimum, and tutorial 5 shows the classic attack: a password field containing ' OR TRUE makes the WHERE succeed.

Escaping is a patch. A prepared statement, with the value kept out of the SQL text, is the fix Part 4 already uses.

Remember: mysqli_connect, mysqli_query, mysqli_fetch_array, mysqli_close. Do not give the web page the root account.

More detail

A failed connect should be detected before you build a query on it. The tutorial checks the connection and stops with a message rather than continuing into mysqli_query on a false value.

Source: Project tutorial 4, PHP and MySQL, and tutorial 5’s injection reminder.

Store a hash, not the password

The rule

Do not store the password. On registration, hash it and store the hash. On login, hash what was typed and compare hashes. A stolen table then does not contain passwords.

A salt is extra per-user data mixed in before hashing, so two users with the same password do not produce the same hash, and a precomputed table of common passwords fails.

Where it can be hashed

MySQL can hash in the INSERT, with SHA1 producing a 40-character hex string. PHP can hash before the query is sent, which is the better place: the database never sees the password.

The form field is type="password" so the browser hides the characters. That is display, not storage. Validate first: isset checks the field arrived, is_numeric checks a value that should be a number.

Remember: Store a salted hash. Compare hashes at login. The password field only hides the typing.

More detail

SHA1 is what the tutorial demonstrates. It is no longer a good choice for new passwords; PHP’s password_hash is the current function. The lecture’s principle still holds: store the hash, salt it, and never store the password itself.

Source: Project tutorial 5, storing passwords.

HTTP forgets you between requests

Cookies

HTTP is a sequence of unconnected requests. A cookie is a name, a value and an expiry, stored by the browser and sent back with later requests.

setcookie('userID', '10');
// logout: expire it
setcookie('userID', '', time() - 3600);

A cookie can be viewed and forged on the client. Do not put a password or a privilege in it. Privacy law also requires consent before you store one.

Sessions

A session keeps the data on the server. session_start() sends only a session id, usually in a cookie. $_SESSION['userID'] is then the login.

Prefer the session for anything that decides what the user is allowed to see. The cookie, if you use one directly, should be an id you can check, not the authority itself. Logout destroys the session, or expires the cookie.

Remember: A cookie lives in the browser and can be forged. A session lives on the server; the browser only holds the id.

More detail

Tutorial 6’s login-with-a-cookie example still builds the WHERE from the typed username. That is the injection pattern again. The new idea in the tutorial is the state, not a new way to write the query.

Source: Project tutorial 6, cookies and sessions.

Mail, and a job that runs without a click

Sending mail

PHP’s mail() hands a message to a local mail queue. It needs an SMTP server: one you install, or Gmail’s, which wants an app password and a configured sendmail. The function returning true means the queue accepted the message, not that the recipient has read it.

If mail cannot be made to work, the tutorial’s own fallback is a notification inside the site.

Cron

A cron job runs a command on a timetable, with nobody clicking. An auction that must close at a deadline is that kind of job.

Do not trust the schedule alone. The tutorial also says to check, in PHP and in SQL, that the work still needs doing, so a late or repeated run does not close the same auction twice.

Remember: mail() queues a message. Cron runs a command on a clock. Check in the database that the job has not already been done.

More detail

The tutorial spends many slides on XAMPP paths and Gmail settings. Those steps depend on the machine. The durable ideas are the queue, the schedule, and the idempotent check.

Source: Project tutorial 7, mail and scheduled events.
