Which plan is actually cheaper

Heuristics suggest a shape. Statistics and indexes decide the algorithm: a scan, a hash lookup, a nested loop, or a sort-merge.

Sections 72–76 · Lecture 5 · Week 5

Part 9 is Lecture 5. It estimates the cost of selections, joins, projections, set operations and aggregates, then narrows the search to left-deep pipelined trees and dynamic programming. Oracle’s rule-based and cost-based optimisers are the case study.

Part 9 · Cost

The numbers the optimiser keeps

Per table

StatisticMeaning
nTuples(R)how many rows
bFactor(R)how many rows fit in one block
nBlocks(R)how many blocks R occupies

Per column

StatisticMeaning
nDistinct(A)how many different values A takes
min(A), max(A)the ends of the range
SC(A)how many rows a selection on A is expected to return

Refreshing the numbers after every update is itself expensive, so the DBMS often collects them when the system is quiet.

Remember: Cost estimates come from row counts, blocks, distinct values, and how many rows a selection is expected to keep.

More detail

An index, usually built for the primary key, stores where each column value lives so a search need not read the whole table. Hashing computes a location instead of walking a B+ tree, and can collide. Both were built in Part 5; this lecture uses them as alternative algorithms.

Source: Lecture 5, “Statistics”, and the review of indexes and hashing.

Part 9 · Cost

How a selection is actually run

Pick the access method from the file

  • Linear search when the file is unordered and there is no index. Cost is about nBlocks(R).
  • Binary search when the file is ordered on the column and there is no index.
  • Hash lookup when the column is hashed. Often a handful of block reads, plus any overflow.
  • Index lookup when a B+ tree or similar index exists.

AND and OR

For an AND, test the cheapest column first: the one whose index or ordering throws away the most rows. A composite index can test several columns in one lookup.

For an OR, you generally cannot stop at the first match. Each clause may contribute rows the others miss, so the results have to be combined.

The size of the output is the selection cardinality, SC(A).

Remember: Scan an unordered heap. Binary-search an ordered file. Use a hash or an index when one exists. On an AND, test the most selective column first.

More detail

The lecture’s point is that the same σ can have very different costs. The algebra operation does not name the algorithm. The optimiser does, when it annotates the tree.

Source: Lecture 5, “Selection ops” and the main strategies.

Part 9 · Cost

Four ways to join

The menu

AlgorithmUse it when
Nested loopyou have nothing else. For each row of R, scan S. Work in blocks, and keep the smaller table in memory.
Indexed nested loopS has an index on the join column. For each row of R, look up the match.
Sort-mergethe join is an equality. Sort both sides, then scan once.
Hash jointhe same idea as sort-merge, but partition with a hash instead of sorting.

How big is the result?

A join is never bigger than the product, nTuples(R) × nTuples(S), and a selective join is far smaller. The cost is not that product if you never materialise it.

Projections that keep a key still have nTuples(R) rows. Projecting one non-key column leaves about nDistinct(A) rows. A set operation’s result sits between the two inputs, and is computed like a join: sort or hash, then one pass. An aggregate with no GROUP BY returns one row and costs a scan. With GROUP BY it returns one row per group.

Remember: Nested loop always works. An index, a sort-merge, or a hash join is how an equijoin avoids the product.

More detail

The lecture’s summary of the other operators is short on purpose. Their costs are estimated the same way as joins: know the output size, then charge for the blocks you must read, and for a sort or a hash if you use one.

Source: Lecture 5, join strategies, projections, set operations and aggregates.

Part 9 · Cost

Left-deep trees can stream

Materialise or pipe

Materialisation writes an intermediate table to disk and reads it back for the next operation. Pipelining feeds each output row straight into the next operator.

A bushy tree joins two intermediate results, so at least one of them has to be stored. A left-deep tree only ever joins one stored table onto the rows flowing up from the left, so the whole query can be pipelined.

Three restrictions that shrink the search

  • Only consider left-deep trees, the ones that can be fully pipelined.
  • Apply selections as the table is first read, and projections as rows are passed on.
  • Never form a Cartesian product unless the query asked for one. Only join tables that share a compared column.

Remember: A left-deep tree pipelines. A bushy tree has to store an intermediate result. The optimiser often refuses every plan that is not left-deep.

More detail

These restrictions can ignore a plan that would have been faster. The lecture accepts that. Exhaustive search of every join order is the more expensive mistake.

Source: Lecture 5, pipelining, materialisation, and the three restrictions.

Part 9 · Cost

Dynamic programming, then Oracle

Remember the best small plan

A query with several joins has too many orders to cost them all. Dynamic programming keeps the cheapest way to join each subset of the tables, and builds larger subsets from those.

It also keeps plans that leave a result in an interesting order: sorted on a column a later merge-join or ORDER BY can use. A slightly dearer sort now can be cheaper than sorting again later.

What Oracle actually does

  • The old rule-based optimiser ranked about 15 access methods from best to worst, from a unique index down to a full scan. It is deprecated.
  • Cost-based optimisation estimates the cost and picks the cheapest plan, for throughput or for response time.
  • Statistics are collected automatically. Histograms are the exception, and Oracle’s are height-balanced.
  • A hint, a stored plan, or EXPLAIN lets you see and nudge the choice.

Remember: Dynamic programming keeps the best plan for each subset, including plans that leave the rows in a useful order. Oracle now costs plans instead of ranking rules.

More detail

A height-balanced histogram gives each bucket the same number of rows, so a skewed column is not treated as uniform. Width-balanced buckets each cover the same range of values and hide the skew.

Source: Lecture 5, dynamic programming and “Query processing in Oracle”.
