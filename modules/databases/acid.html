Part 10 · Atomic

Several updates that must stand or fall together

A transfer is two writes. A crash or a second customer in the middle of those writes can invent or destroy money. Transactions, locks and a log are how the DBMS refuses that.

Sections 77–81 · Lecture 6 · Weeks 6–7

Part 10 is Lecture 6. It covers why transactions exist, ACID, serializability and recoverability, locking and timestamp ordering, and recovery by deferred update, immediate update and shadow paging.

Part 10 · Atomic

One task, several writes

Two ways a transfer breaks

Debit one account and credit another. If the system dies after the debit, money has vanished. If a second transaction reads the balance in between and writes its own result last, the first update is lost.

A third failure is the inconsistent analysis: one transaction sums balances while another moves money, so the sum never matched any real moment. An uncommitted dependency is worse: you read a value that is later rolled back.

ACID

PropertyPromise
Atomicityall of the transaction’s writes happen, or none do
Consistencythe database moves from one valid state to another
Isolationconcurrent transactions do not see each other’s half-finished work
Durabilityafter COMMIT, the result survives a crash

In SQL, BEGIN TRANSACTION and COMMIT or ROLLBACK mark the bundle. Until commit, the transaction is active. After commit it cannot be undone.

Remember: A transaction is a bundle of writes that commits or rolls back as a whole. ACID is atomic, consistent, isolated and durable.

More detail

The lecture’s transfer subtracts 20 from the payer and adds 20 to the payee. Any schedule that shows the payer’s new balance without the payee’s, or that lets another update overwrite one of them, has broken the transaction.

Source: Lecture 6, why transactions matter, the SQL commands, and ACID.

Part 10 · Atomic

Interleaved, but equivalent to some serial order

Conflict serializability

A serial schedule runs one transaction to completion, then the next. An interleaved schedule mixes their reads and writes. It is conflict serializable when it has the same effect as some serial order.

Two operations conflict when they touch the same item and at least one writes it. Draw a precedence graph: an edge Ti → Tj means Ti must come before Tj in the serial order. A cycle means it is not conflict serializable.

T1: Read(A)
T2: Read(A)
T1: Write(A)
T2: Write(A)

T1 read before T2 write  →  T1 → T2
T2 read before T1 write  →  T2 → T1

A cycle. Not conflict serializable.

View serializability, and recovery

View serializability is weaker. It only insists that each transaction reads the same values, and that the same transaction writes the final value of each item. Every conflict-serializable schedule is view serializable. The converse is false, and checking view serializability is harder.

Serializability is not enough. If T2 reads T1’s write and commits, and T1 then aborts, T2 must be undone too, but a commit cannot be undone. That schedule is not recoverable. A recoverable schedule does not let a transaction commit until every transaction it read from has committed.

Remember: Draw the precedence graph of conflicting reads and writes. A cycle means the interleaving is not conflict serializable. A commit must not depend on a transaction that might still abort.

More detail

Reads that do not overlap anyone’s write can run freely. So can operations on disjoint data. The hard cases are a read and a write, or two writes, on the same item. A cycle is broken by aborting one transaction on the cycle.

Source: Lecture 6, schedules, the precedence-graph exercise, and recoverability.

Part 10 · Atomic

Lock, and do not release too soon

Shared and exclusive

A read lock (shared) allows other readers and blocks writers. A write lock (exclusive) blocks everyone else. Taking locks is not enough: if you unlock a row and then later lock another, a second transaction can slip into the gap and the schedule need not be serializable, and it may not be recoverable.

Two-phase locking forbids that. In the growing phase a transaction only acquires locks. In the shrinking phase it only releases them. Strict two-phase locking holds the write locks until commit, which prevents cascading rollbacks.

Deadlock

Two transactions can each hold the lock the other needs. That is deadlock. Livelock is the variant where a transaction keeps being overtaken and never gets the lock.

  • Timeouts: give up a request that waits too long.
  • Deadlock detection: build a wait-for graph and abort one transaction on each cycle.
  • Prevention: conservative two-phase locking grabs every lock at the start. It works and is rarely practical.
  • Wound-wait and wait-die use timestamps so an older transaction is not stuck behind a younger one.

Remember: Two-phase locking grows, then shrinks. Strict two-phase locking keeps write locks until commit. A cycle in the wait-for graph is a deadlock.

More detail

Locking a whole table is coarse and simple and blocks a lot of work. Locking a field is fine-grained and expensive to manage. Multiple-granularity locking uses a tree: a lock on a node locks its descendants, and an intention lock on the ancestors warns that somebody below wants a lock.

Source: Lecture 6, locking, two-phase locking, and deadlock.

Part 10 · Atomic

Order transactions by when they started

The timestamp rules

Each transaction gets a timestamp when it starts. The equivalent serial order is that timestamp order. Each data item remembers the timestamp of the last transaction that read it and the last that wrote it.

  • A read is rejected if a newer transaction has already written the item. The reader is too late.
  • A write is rejected if a newer transaction has already read or written the item. The writer would change a value the future has already used.

The rejected transaction aborts and restarts with a new timestamp. Multiversion timestamp ordering keeps old versions so a late reader can still see the version that was current for it.

Optimistic control

If conflicts are rare, do not lock. Let the transaction run, and check at the end. The lecture tracks a start timestamp, a validation point and a finish. Validation asks whether any overlapping transaction wrote something this one read or wrote. If so, abort.

Conflict serializability rejects some schedules that view serializability would allow. Timestamping and locking each allow schedules the other refuses. None of them is uniformly better.

Remember: A read or write that would contradict a newer transaction’s work is aborted. Optimistic control checks once, at the end, instead of locking.

More detail

The lecture’s comparison is worth remembering as a warning against a single favourite. A schedule can be view serializable without being conflict serializable, and a schedule allowed by timestamps need not be one that locking would have produced.

Source: Lecture 6, timestamping, versioning, and optimistic concurrency.

Part 10 · Atomic

The log is how a crash is undone

What can be lost

Main memory, including the buffers, disappears when the machine stops. A transaction can commit before its buffers are flushed, and a buffer can be flushed before the transaction commits. Recovery has to redo the first and undo the second.

A log records, for each change, the transaction, the time, the operation, the item, and the before-image and after-image. A checkpoint forces every buffer to disk and records which transactions were active.

Three recovery methods

MethodRule
Deferred updatedo not write the database until commit. A crash before commit needs no undo. After commit, redo from the log.
Immediate updatebuffers may reach disk early. Redo committed work and undo uncommitted work.
Shadow pagingno log of values. Keep the old page table as the shadow. Commit is switching to the new page table. A crash throws the new table away.

If the disk itself is damaged, restore a backup and reapply the committed log. Keep the backup, the log and the database in different places.

Remember: Deferred update only needs redo. Immediate update needs undo and redo. A checkpoint limits how far back you read the log.

More detail

After a checkpoint, transactions that committed before it are already on disk. Transactions active at the checkpoint must be redone if they later committed, and undone if they did not. Oracle’s practical answer, at the end of the lecture, is multiversion read consistency: readers are not blocked by writers, because they see a snapshot.

Source: Lecture 6, recovery, checkpoints, deferred and immediate update, shadow paging.
