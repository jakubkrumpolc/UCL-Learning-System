64

Revision · Cheat sheet

SQL on one page

Build · DDL

CREATE TABLE T (
  id INT PRIMARY KEY,
  name VARCHAR(50) NOT NULL,
  uId INT,
  FOREIGN KEY (uId)
    REFERENCES U(id));
ALTER TABLE T ADD c INT;
DROP TABLE T;

Change · DML

INSERT INTO T (id, name)
  VALUES (1, 'Ann');
UPDATE T SET name = 'Bo'
  WHERE id = 1;
DELETE FROM T
  WHERE id = 1;
-- no WHERE = every row!

Ask · SELECT, in writing order

SELECT cols, COUNT(*)
FROM T JOIN U ON T.uId = U.id
WHERE row filter
GROUP BY cols
HAVING group filter
ORDER BY col DESC
LIMIT 10;

WHERE tools

= <> < > · BETWEEN · IN (…) · LIKE 'a%' · IS NULL

Aggregates

COUNT · SUM · AVG · MIN · MAX · COUNT(DISTINCT x)

Joins

JOIN: matches only. LEFT JOIN: keep all of the left.

Subqueries

IN (…) · EXISTS (…) · > ALL (…) · = (SELECT MAX …)

Runs in this order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

More detail

A one-page summary for revision and for keeping open during the labs. DDL (data definition language) creates and changes structure: CREATE TABLE with a type and rules per column, PRIMARY KEY and FOREIGN KEY constraints, ALTER TABLE to change a table, DROP TABLE to delete it. DML (data manipulation language) changes rows: INSERT adds, UPDATE changes, DELETE removes; UPDATE and DELETE without a WHERE clause affect every row in the table, so write the WHERE first.

Queries: write the clauses in the order shown; only SELECT and FROM are required. The database evaluates them in a different order, shown in the bar at the bottom: it first builds the rows (FROM and joins), filters rows (WHERE), forms groups (GROUP BY), filters groups (HAVING), and only then computes the SELECT list, sorts and limits.

That order explains two classic errors: you can’t use an aggregate in WHERE (groups don’t exist yet), and in standard SQL you can’t use a SELECT alias in WHERE (it hasn’t been computed yet; MySQL does allow aliases in GROUP BY, HAVING and ORDER BY). Strings and dates go in single quotes ('Ann', '2025-05-24'); LIKE uses % for any run of characters and _ for exactly one; test for missing values with IS NULL, never = NULL. The full explanations are on sections 11–35.

More detail

All the main memory hooks from this site in one place, grouped by part: Store (what a database is), Speak (SQL), Shape (design) and Ship (using it in an app). A hook only works if it points to an understanding, so for each one, try to give the full idea and an example without looking. DBMS = librarian: the software that files, finds, guards and repairs data on your behalf. PK = passport number: the unique identifier; FK = someone else writing your passport number down to refer to you.

Degree = number of columns; cardinality = number of rows. DDL defines structure (CREATE, ALTER, DROP); DML changes rows (INSERT, UPDATE, DELETE). WHERE filters individual rows before grouping; HAVING filters groups after GROUP BY. LEFT JOIN keeps every row from the left table even with no match. > ANY means greater than at least one value (the smallest); > ALL means greater than every value (the largest). A comma-separated FROM list is a Cartesian product until the WHERE matches the keys.

Nouns become entities, verbs relationships, and asking “how many?” both ways gives multiplicities, which are written next to the entity being counted. In a one-to-many relationship, the FK goes in the table on the many side. 1NF: every cell depends on the key (one value); 2NF: on the whole key; 3NF: on nothing but the key. In apps, design each page around one query, and always pass user values through placeholders.

Active recall like this (testing yourself rather than rereading) is one of the most effective ways to remember material.
