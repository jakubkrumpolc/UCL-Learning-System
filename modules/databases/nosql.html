Availability instead of an immediate single answer

Relational systems promise ACID and a stable schema. NoSQL relaxes both, so a store can grow by adding machines and stay up when those machines disagree for a while.

Part 14 · Base

Not only SQL

What is being given up

A relational DBMS spends its effort on ACID and on a schema that refuses duplicates and broken references. Across many sites that coordination is exactly what limits growth. NoSQL means not only SQL: some of these systems still accept SQL-like queries. The goal is near-linear horizontal scaling, and eventual consistency instead of an immediate common value.

CAP and BASE

The CAP theorem: a distributed system does not simultaneously guarantee consistency (every read sees the latest write), availability (every request gets a response), and partition tolerance (the system keeps going when the network splits). A partition forces a choice between the other two.

BASE is the NoSQL answer. Basically available: the store answers. Soft state: the value can be stale. Eventual consistency: if updates stop, the copies agree.

Remember: CAP says a partition forces a choice between consistency and availability. BASE chooses availability, and consistency later.

More detail

The lecture’s comparison table is the overview. Relational systems store tables and promise ACID. NoSQL systems store key-value pairs, documents, graphs, columns or XML, and promise scale and availability. The schema is the thing that moved.

Source: Lecture 10, shortcomings of relational systems, CAP and BASE.

Part 14 · Base

Keys on a ring

Key-value stores

A row is a key and a value. The key decides which server stores it, by a hash. The simplest split is hash(key) mod n across n servers.

Adding or removing a server changes n, so almost every key moves. That is the failure of modulus sharding.

Consistent hashing

Place servers and keys on a ring of values from 0 up to, but not including, 1. A key is stored at the nearest server clockwise.

Add or remove one server and only the keys that walked to or from that server move: about 1/n of them, not all of them.

A coordinator accepts a request and collects the answer. Membership gossip does not promise that every node currently knows every other node. It catches up. That lag is eventual consistency again.

Remember: Modulus sharding moves almost every key when a server is added. Consistent hashing moves about 1/n of them, around the ring.

More detail

A key-value store can be the whole database or a cache in front of one. By itself it offers put and get, not joins and not rich constraints. The lecture is frank about that limit.

Source: Lecture 10, key-value stores and consistent hashing.

Part 14 · Base

Documents, then map and reduce

Richer values

A tuple store keeps a key and a vector of fields, without forcing every vector to have the same length. A document store keeps a key and a semi-structured document, usually JSON. Filters are possible and can be awkward, because two documents need not share a field.

MapReduce

MapReduce, from Google and later Hadoop, scales an aggregation across machines.

  • Map turns each input into a new key and value. For pages per genre, each book becomes (genre, pages).
  • The system groups the pairs by that key.
  • Reduce folds each group into one answer. Summing the pages of a genre is the fold.

The lecture’s sketch ends with totals such as education 340 and thriller 100. The pattern matters more than those two totals: map emits, reduce folds one key.

Remember: Map emits (key, value) pairs. Reduce receives one key and all its values, and emits one result.

More detail

Column stores are the other family the lecture names: tables stored by column rather than by row, which suits an aggregate over one column of many rows. XML and object databases appear again here as further non-relational options, already covered in Parts 12 and 13.

Source: Lecture 10, document stores and the MapReduce example.

Part 14 · Base

When the relationship is the data

A graph store

Nodes are the things. Edges are the relationships. The earlier NoSQL models mostly throw relationships away and reconstruct them at query time. A graph store keeps them, which suits social networks, recommendations, maps and knowledge graphs.

Cypher

Neo4j’s language draws the pattern you want.

MATCH (b:Book)-[:WRITTEN_BY]->(a:Author)
WHERE a.name = 'Le Guin'
RETURN b.title
  • Parentheses are nodes. (b:Book) is a node of label Book, bound to b.
  • An undirected edge is --. A directed one is -[:WRITTEN_BY]->.
  • NewSQL is the later swing back: NoSQL systems adding durability, and relational systems adding scale and flexible schemas.

Remember: A graph store keeps the edges. Cypher draws the path in the query: nodes in parentheses, relationships in arrows.

More detail

The lecture’s closing line is the scope. NoSQL fits flexible schemas, heavy distribution, and a preference for availability. It is not a replacement for a payroll database that needs ACID tonight.

Source: Lecture 10, graph databases, Cypher, and NewSQL.
