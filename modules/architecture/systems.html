Part 6 · Systems

Between the user and the hardware

Four layers

Users

Applications

Operating system

Hardware

Hardware is the CPU, memory and devices. Applications are how that hardware gets used: a browser, a compiler, a game. Users are people, or other computers.

The operating system is the layer that makes the hardware convenient and keeps it shared fairly. From the user’s side that means ease and speed. From the system’s side it means two jobs: resource allocator, and control program that stops a faulty program from wrecking the machine.

Kernel, and everything else

There is no single official definition. Two working ones from the lecture:

  • “Everything a vendor ships when you order an operating system.” That bundle varies wildly.
  • “The one program running at all times.” That program is the kernel. The rest is either a system program that shipped with it, or an application.

The names to recognise: Windows, macOS, Linux, and on phones Android and iOS.

Remember: The kernel is the program that is always running. It allocates hardware and stops programs damaging each other. Everything else is a system program or an application.

More detail

A shared mainframe has to keep every user happy. A personal machine can spend its resources on one person. A phone is tuned for battery and a small screen. An embedded computer in a car may have no screen at all. The definition does not change; the policies do.

The boot lecture’s last arrow, “user executable in RAM”, is an application sitting on top of this kernel. The kernel was the thing the bootloader fetched.

Source: Lecture 12, “What is an Operating System?”, “Four components”, “Kernel”.

Part 6 · Systems

Polling asks; an interrupt rings

Devices do not wait their turn

Key presses, arriving packets and disk completions happen when they happen. The CPU needs a way to notice.

Polling is the CPU repeatedly asking each device if it wants anything. It costs time even when the answer is no, and a device waits until the next round. It pays off only when events are constant.

An interrupt is a wire the device raises. The CPU stops, runs the interrupt service routine whose address is in the interrupt vector, and then goes back. The address of the interrupted instruction is saved, so the return is well defined. While nothing is happening, the cost is nothing.

The lecture’s phone, and a trap

Polling is picking up the phone every few seconds to see if anyone is there. An interrupt is waiting for it to ring.

A trap (or exception) is a software-generated interrupt: a divide by zero, or a program asking for a service. The hardware path and the software path meet in the same mechanism. Most of a modern kernel is organised as “wait until something interrupts”.

Each device has a controller with a small local buffer, and a device driver that knows that controller and presents a plain interface to the rest of the kernel. I/O finishes by the controller raising the interrupt.

Remember: Polling keeps asking. An interrupt is the device ringing, and the vector says which routine answers. A trap is an interrupt caused by the program: a fault, or a request for a service.

More detail

The interrupt can arrive in the middle of another instruction’s aftermath. The lecture’s definition: an event external to the current process that changes the flow of execution. Saving the return address is what makes it like a procedure call rather than a crash.

BIOS, in the previous part, installs the first vector table so that interrupts mean something before the kernel has loaded its own handlers.

Source: Lecture 12, “Polling”, “Interrupts”, “trap or exception”, device controllers.

A ladder of faster and smaller

What sits near the CPU

  • Registers are touched in a clock cycle, and only by the instruction that names them.
  • Cache sits between the registers and main memory.
  • Main memory is random access and, on a normal machine, volatile: power off, contents gone. It is too small to hold everything permanently.
  • Secondary storage is the extension: a hard disk (platters, tracks, sectors) or an SSD (no moving parts, non-volatile, faster).

The file system is how the kernel makes those devices look like named files in directories, rather than like platters.

A cache is a copy of what you are using

Copy the working set from a slow store into a fast one. Look in the fast one first. If the data is there, use it. If it is not, fetch it and leave the copy behind. The fast store is smaller, so choosing what to keep is the whole design problem.

The same idea is used in hardware (the CPU cache), in the kernel, and in applications. Part 8’s page replacement is this problem, one level up: RAM is the cache, the disk is the slow store.

Remember: Closer to the CPU means faster, smaller and more expensive. A cache holds a temporary copy of what is in use. Main memory forgets when the power goes; a disk or SSD does not.

More detail

Lecture 12’s size ladder uses powers of two: a kilobyte is 1024 bytes, and so on up to a petabyte. It repeats Part 2’s warning that manufacturers often mean a decimal billion, and that networks quote bits.

I/O has three overlapping tricks, named together in the lecture. Buffering holds data while it moves. Caching keeps a copy for next time. Spooling overlaps the output of one job with the input of another, so a slow printer does not stall the CPU.

Source: Lecture 12, “Storage structure”, “Caching”, “I/O system”.

Part 6 · Systems

More than one processor

On one board

  • A single-processor system has one general-purpose CPU, plus small controllers that are not general-purpose.
  • Asymmetric multiprocessing: one processor is in charge and hands work to the others.
  • Symmetric multiprocessing (SMP): every processor can run any task, including kernel code. Throughput goes up, cost per extra processor is lower than a second machine, and a failed processor can degrade the system rather than stop it.
  • A multicore chip is several processors in one package, sharing a socket.

Several machines

A cluster is whole computers working together, usually sharing storage. Asymmetric clustering keeps one machine as a hot standby. Symmetric clustering runs work on all of them and lets them watch each other. High-performance clusters need programs written to run in parallel.

A Beowulf cluster is the cheap version the lecture names: ordinary PCs, a Unix-like system, and libraries that share the work. The first was built at NASA in 1994.

Further out, the lecture’s map of environments is client-server, peer-to-peer (every node can be either), and cloud: public, private or hybrid, sold as software, platform, or infrastructure.

Remember: Symmetric multiprocessing lets every CPU run any task. Asymmetric multiprocessing keeps a boss processor. A cluster is separate computers sharing the work.

More detail

Cloud computing, in the lecture, sits on virtual machines plus the ordinary operating systems, with firewalls and load balancers in front. SaaS is an application, PaaS is a stack such as a database server, IaaS is machines or storage.

You do not need the product names for the test so much as the shape: who shares the CPUs, and whether a failure of one node is survivable.

Source: Lecture 12, multiprocessors, clusters, Beowulf, client-server, peer-to-peer, cloud.

Part 6 · Systems

User mode and kernel mode

A bit the hardware checks

The CPU has a mode bit. User mode runs ordinary programs. Kernel mode (also called supervisor or privileged mode) runs the operating system.

Some instructions are privileged: they execute only in kernel mode. I/O and changing the mode bit itself are in that set. A program that could do either, on its own, could bypass the allocator.

A system call is the legal crossing. It flips the machine into kernel mode, the service runs, and the return flips the bit back. A trap from a fault takes the same crossing.

What goes wrong without it

The lecture’s list of damage is an infinite loop, a process writing another process’s memory, and a process writing the kernel. Dual mode does not make those bugs impossible to attempt. It makes the hardware refuse the attempt, and turns it into a trap the kernel can handle.

Timer interrupts are the other half. Without a timer, a user program that never makes a system call and never faults would keep the CPU forever. The timer is a privileged mechanism that makes preemption possible. Scheduling, in the next part, is the policy for what runs when the timer fires.

Remember: A mode bit separates user code from kernel code. Privileged instructions run only in kernel mode. A system call flips the bit; the return flips it back.

More detail

The lecture draws the transition as: user process, syscall or interrupt, mode bit to kernel, service, mode bit back, resume. The PCB, next part, is what “resume” restores.

Kernel code is not magically correct. A fault in the kernel is a crash dump rather than a core dump of one process. The protection boundary limits the blast radius of user code; it is not a proof of the kernel.

Source: Lecture 12, “Dual-mode operation”, “Transition from User to Kernel Mode”.

Part 6 · Systems

Processes, memory, files, devices

What the kernel owes a process

A process is a program in execution. The program on disk is passive. The process is active: it has a program counter, registers, and memory. The kernel creates and deletes processes, suspends and resumes them, and provides synchronisation, communication and deadlock handling. Many of them share one CPU by taking turns. That is multiprogramming.

Memory management decides which processes, and which parts of them, are in RAM. To run, a process needs its instructions and the data they touch to be addressable. The activities are: track who owns what, choose what to move in and out, and allocate and free.

Files and devices

  • Storage devices differ in speed, size and whether they are read sequentially. The kernel presents all of them as files and directories, with permissions.
  • Creating and deleting files, reading and writing, mapping a file onto the device, and backing it up are the file-system activities.
  • Thousands of devices would otherwise each need their own interface. Drivers sit under one driver interface.

Protection is controlling which process or user may touch a resource. Security is defending the system against attack. Users are identities (a user id, and often a group id) attached to processes and files. Privilege escalation is changing to an identity with more rights, on purpose.

Remember: A process is a running program. The kernel schedules processes, tracks memory, presents files, and hides each device behind a driver.

More detail

The kernel’s own data structures are ordinary ones: linked lists, stacks, FIFO queues, binary search trees (balanced, so lookup is logarithmic), hash maps, and bitmaps where each bit is the state of one object. Linux keeps these in the usual include files. You already know the shapes from algorithmics; the lecture’s point is that the kernel is built out of them.

Open-source kernels (Linux, the BSD code under macOS) are the ones you can read. The lecture’s note is that the business around them is support, training and hardware, not a secret binary.

Source: Lecture 12, process, memory, storage and I/O management; protection; kernel data structures.

Part 6 · Systems

Services, and the calls that ask for them

What a running program can ask

  • User interface: a command line, a graphical desktop, a batch job, or a touchscreen. Windows is a GUI with a shell. macOS is a GUI on a Unix kernel. Linux is a shell with a GUI available.
  • Program execution: load a program, run it, end it normally or with an error.
  • I/O and files: read, write, create, delete, search, and set permissions.
  • Communication between processes, on this machine or across a network.
  • Errors: notice them in the CPU, memory, devices or the program, and do something defined.
  • Allocation, accounting, protection.

A system call is the programming interface

Calls are usually written in C or C++, and programs reach them through an API rather than by issuing the trap themselves. The two APIs the lecture names are Win32 and POSIX (Unix, Linux, macOS).

GroupExamples
Processcreate, terminate, load, wait, allocate memory
Filecreate, open, close, read, write, seek
Devicerequest, release, read, write
Informationget or set the time, or a process’s attributes
Communicationsend and receive
Protectionget and set permissions

MARS syscall with a number in $v0 is a teaching version of this table. Code 10 is exit. Code 1 is print. The real tables are longer and the numbers differ; the shape is the same.

Remember: Programs call an API, and the API makes the system call. The groups are processes, files, devices, information, communication and protection.

More detail

A command shell is often not the kernel. It is a system program that reads a line and runs another program. Adding a command can then be adding a program, without changing the shell. That is why the lecture bothers to separate “built-in” from “the name of a program”.

Copying a file, the lecture’s worked sequence, is a chain of these calls: open or create, then a loop of read and write, then close, with an error path at each step. You do not need the vendor’s spelling. You need the chain.

Source: Lecture 13, operating-system services, system-call types, CLI and GUI.

Part 6 · Systems

Policy, mechanism, and how a kernel is built

Decide separately from doing

Policy is what will be done. Mechanism is how. A timer interrupt is a mechanism. “Processes get 20 ms each” is a policy sat on top of it. Split them, and the policy can change without a new mechanism.

User goals for a kernel: convenient, learnable, reliable, safe, fast. System goals: easy to build and change, flexible, correct, efficient. Both lists are the lecture’s, and they pull against each other. That is why the split matters.

What the code is made of

  • Early kernels were assembly. The body of a modern one is C or C++, with assembly only at the bottom, and scripts and system programs above.
  • A higher-level language is easier to move to another machine, and easier to get wrong in the small. Emulation can run a kernel on hardware it was not built for.
  • Loadable kernel modules keep drivers and filesystems out of a monolith: each is loaded when needed and talks through a known interface. Linux works this way.
  • SYSGEN is the configuration step that specialises a kernel for one machine’s devices, rather than carrying every driver forever.

When it fails, an application can write a core dump, and a dead kernel can write a crash dump. Profiling samples the program counter to see where time goes.

Remember: Policy is what should happen. Mechanism is how it happens. Keep them apart so a new decision does not mean a new machine.

More detail

Boot, restated from the implementation lecture: at power-on the CPU starts at a fixed address in firmware. That code loads a second loader from a known boot block. GRUB can then choose a kernel. This is the same chain as Part 5, told from the kernel’s side.

The next part is the policy that sits on the timer mechanism: which process runs next, and for how long.

Source: Lecture 13, “policy and mechanism”, implementation, modules, SYSGEN, system boot.
