Who runs next, and for how long

A process is more than a program. The kernel keeps its identity in a control block, stops it from trampling shared data, and picks the next one with an algorithm you can run by hand.

Part 7 · Schedule

A program in execution

What a process contains

  • Text: the code.
  • A program counter and the registers: exactly where execution stopped.
  • A stack of calls: parameters, return addresses, locals.
  • A data section of globals, and a heap of memory allocated as it runs.

As it runs it moves through states. New (being created), ready (waiting only for a CPU), running, waiting (asleep on an event, often I/O), and terminated.

The process control block

The PCB (also called a task control block) is the kernel’s record of one process:

  • State, program counter, saved registers
  • Scheduling numbers: priority, and pointers into the queues
  • Memory maps
  • Accounting: CPU time used, and limits
  • I/O: open files, and devices it holds

A process is identified by a pid. Parents create children, which creates a tree. The parent may share all, some, or none of its resources, and may wait for the child or run alongside it. A child ends with exit, returning a status the parent can wait for. A parent can abort a child that has overrun, or whose work is no longer wanted.

Remember: A process is a running program: code, program counter, registers, stack, data and heap. The PCB is the record that lets the CPU leave and come back. States are new, ready, running, waiting, terminated.

More detail

Chrome is the lecture’s picture of multiple processes by design. One browser process owns the UI and the network. Each site gets a renderer, sandboxed so a hostile page cannot touch the disk. Plug-ins are separate again. One bad page then does not have to take down the window.

Phones, in the same lecture, keep one foreground process and a few tightly limited background ones (a short task, a notification, audio). The screen is too small for a dozen visible apps, and the battery is the other constraint.

Source: Lecture 14, “Process concept”, PCB, creation and termination, Chrome.

The context switch is pure overhead

Saving one identity, loading another

When the CPU moves from process A to process B it writes A’s registers and program counter into A’s PCB and loads B’s. That is a context switch. During it, no user instruction runs. A fatter PCB, or a fatter kernel, makes it slower. Some CPUs keep several register sets so more than one context is already loaded.

The queues the scheduler walks:

  • Job queue: every process in the system.
  • Ready queue: in memory, waiting for a CPU.
  • Device queues: waiting on a particular device.

A process migrates: ready, running, then perhaps a device queue, then ready again.

Two schedulers, very different speeds

SchedulerChoosesHow often
Short-term, the CPU schedulerWhich ready process runs nextMilliseconds. It must be cheap
Long-term, the job schedulerWhich jobs are admitted to memory at allSeconds or minutes. It sets the degree of multiprogramming

Many systems have only the short-term one. The dispatcher is the code that actually switches context, switches to user mode, and jumps to the right instruction. Dispatch latency is how long that takes.

Remember: A context switch saves one PCB and loads another, and does no useful work while it does. The short-term scheduler picks the next process every few milliseconds. The long-term scheduler decides who is allowed into memory.

More detail

CPU scheduling points, from Lecture 16, are four: a process goes from running to waiting, from running to ready, from waiting to ready, or it terminates. Decisions at the first and the last can be non-preemptive: the process has given the CPU up. The other two are preemptive: the kernel takes the CPU. Preemption is why shared data needs the next sections, and why a timer interrupt during a kernel update is dangerous.

A process’s life is a cycle of CPU bursts and I/O bursts. The length of the next CPU burst is what the short-term algorithms are really guessing.

Source: Lecture 14, context switch, queues, schedulers; Lecture 16, when a scheduling decision happens, the dispatcher.

Processes that need to talk

Two models

Independent processes do not affect each other. Cooperating ones do, for sharing information, for speed, for modularity, or because it is convenient. They need inter-process communication.

  • Message passing: send and receive. No shared variables. Easy to reason about, and it works across a network.
  • Shared memory: both processes map the same pages. Faster, and the kernel is not involved in every word. The processes themselves must synchronise, which is the next section.

The lecture’s examples of real mechanisms: POSIX shared memory, and message passing in Mach and in Windows.

Pipes, sockets, remote calls

  • An ordinary pipe is one-way, parent to child (or the reverse). The producer writes one end, the consumer reads the other. Windows calls these anonymous pipes.
  • A named pipe has a name, works both ways, can cross a network, and does not need a parent-child pair. Several processes can use it.
  • A socket is one end of a network connection: an IP address plus a port. 161.25.19.8:1625 is port 1625 on that host. Ports below 1024 are the well-known services. 127.0.0.1 is the loopback address, this machine.
  • A remote procedure call looks like a call. The client stub finds the server and marshals the arguments; the server stub unpacks them and runs the procedure.

Remember: Cooperating processes share memory or pass messages. An ordinary pipe is one-way between parent and child. A socket is an IP address plus a port. 127.0.0.1 is this machine.

More detail

Shared memory being “under the control of the users” is the lecture’s warning. The kernel sets up the mapping. It does not, by that setup alone, stop two writers racing. Synchronisation is a separate mechanism.

Marshalling is turning arguments into a byte stream that survives the trip, including disagreements about byte order. Part 2’s endianness is why a stub cannot just copy the registers onto the wire.

Source: Lecture 14, IPC, pipes, sockets, RPC.

One process at a time in the critical section

The problem

Processes are interrupted mid-update. Two of them updating the same variable can lose an update. The critical section is the stretch of code that touches the shared data. The protocol has an entry section, the critical section, an exit section, and the rest of the program (the remainder).

A solution has to meet three tests.

  • Mutual exclusion. If one process is inside, no other process is.
  • Progress. If the critical section is free and somebody wants it, the decision of who goes in cannot be postponed forever.
  • Bounded waiting. After a process has asked to enter, there is a limit on how many times others may enter before it does.

Peterson’s algorithm, for two processes

Shared: turn, and flag[2]. Process i does:

flag[i] = true
turn = j
while flag[j] and turn == j:
    wait
# critical section
flag[i] = false
# remainder

Process i enters only when j does not want to, or when it is i’s turn. The lecture shows this meets all three tests on the simple model it was written for. On modern machines with several CPUs, stores can be reordered, and the algorithm as written is not enough. Hardware has to help.

Remember: Only one process may be in the critical section. A correct protocol has mutual exclusion, progress, and bounded waiting.

More detail

Inside the kernel the same problem appears. A preemptive kernel can be interrupted while running kernel code, so kernel data needs the same care. A non-preemptive kernel runs until it leaves kernel mode, blocks, or yields, so one kernel path runs at a time.

Peterson’s paper, cited on the slide, is G. L. Peterson, “Myths About the Mutual Exclusion Problem”, 1981. You will not be asked for the citation. You will be asked for the three conditions and what turn and flag are for.

Source: Lecture 15, the critical-section problem and Peterson’s solution.

Locks, and a semaphore that can sleep

A lock, if the hardware can make it atomic

Atomic means the CPU cannot be interrupted in the middle. Two instructions the lecture names: test-and-set (return the old value, write true) and compare-and-swap (write the new value only if the old value is the one you expected, and return the old value).

A mutex is the tool an application actually uses. acquire waits until the lock is free and then takes it. release frees it. Both must be atomic. If acquire waits by spinning in a loop, the lock is a spinlock. It is simple, and it burns a CPU.

test-and-set alone gives mutual exclusion and does not give bounded waiting. The lecture’s later loop, which walks a waiting[] array and hands the lock to the next waiter, is what adds the bound.

A semaphore is an integer with two operations

wait(S):                signal(S):
    while S <= 0:            S = S + 1
        wait             
    S = S - 1

Those are the only legal updates. The original names are P and V. The version above still spins. The useful implementation gives each semaphore a queue of PCBs: block moves the caller onto that queue, and wakeup moves one waiter back to ready. Waiting then costs no CPU.

A mutex is the special case of a lock that is either taken or free. A semaphore can count, so it can allow a fixed number of processes into a section, or stand for “there are n items in the buffer”.

Remember: A mutex is a lock: acquire waits, release opens it. A spinlock waits by looping. A semaphore is an integer changed only by wait and signal; with a queue, wait sleeps instead of spinning.

More detail

Initialise a mutex so it is available, and a binary semaphore to 1 if the section starts free. wait before the critical section and signal after is the whole protocol. Forgetting the signal is a permanent lockout, which fails progress.

Compare-and-swap is the instruction behind a large amount of lock-free code as well, but the lecture uses it to build a lock: loop until the swap of 0 to 1 reports that you saw a 0.

Source: Lecture 15, test-and-set, compare-and-swap, mutex locks, semaphores.

First come, and shortest job

What “better” means

MeasureWant
CPU utilisationthe CPU busy
Throughputmore processes finished per unit time
Turnaroundless time from arrival to completion
Waiting timeless time spent in the ready queue
Response timeless time until the first response, which is not the same as finishing

The lectures compare algorithms by average waiting time.

FCFS runs processes in arrival order and does not preempt. With bursts 24, 3, 3 in that order, the waits are 0, 24 and 27. The average is 17. Arrive as 3, 3, 24 and the waits are 0, 3 and 6. The average is 3. A short job stuck behind a long one is the convoy effect.

Shortest job is optimal, and unknowable

SJF runs the ready process with the shortest next CPU burst. It minimises average waiting time for a given set. The obstacle is that the next burst is in the future.

If P1–P4 with bursts 6, 8, 7 and 3 are all ready at time 0, the order is P4, P1, P3, P2. Waits: P1 = 3, P2 = 16, P3 = 9, P4 = 0. Average 7, which is the figure on the slide.

The same slide also prints arrival times 0, 2, 4 and 5. Non-preemptive SJF must then finish P1 before it looks: P1 runs 0–6, then P4 (6–9), P3 (9–16), P2 (16–24). Waits are 0, 14, 5 and 1. Average 5. Use the arrival times when a question gives them. The average 7 is the all-ready-at-0 reading.

The estimate of the next burst is exponential smoothing, α usually ½:

τₙ₊₁ = α · tₙ + (1 − α) · τₙ

With α = 0.5, τ₁ = 5 and actual bursts 4, 8, 5, 6: τ₂ = 4.5, τ₃ = 6.25, τ₄ = 5.625, τ₅ = 5.8125, which the lecture rounds to 5.81.

Remember: FCFS can trap a short job behind a long one: the convoy effect. SJF gives the shortest average wait if you know the next burst. Estimate that burst with τₙ₊₁ = α tₙ + (1−α) τₙ.

More detail

Preemptive SJF is shortest remaining time first. The lecture’s processes arrive at 0, 1, 2, 3 with bursts 8, 4, 9, 5. P1 runs until t = 1, P2 (shorter) runs until t = 5, P4 runs until t = 10, P1’s remainder runs until t = 17, P3 until t = 26. Waiting times are P1 9, P2 0, P3 15, P4 2. Average 26/4 = 6.5.

Check a waiting time as completion − arrival − burst, or by adding the gaps spent in the ready queue. Both give 6.5 on that trace. The Gantt chart is the thing to draw; the average is arithmetic on it.

Source: Lecture 16, criteria, FCFS, non-preemptive SJF, exponential averaging, preemptive SJF.

Priority, and a slice of the CPU

Priority, and starvation

Give every process an integer priority and run the best one. The lecture’s worked example treats a smaller integer as higher priority (and notes that a site can choose the opposite). SJF is priority scheduling in disguise: the priority is the predicted burst.

Bursts 10, 1, 2, 1, 5 with priorities 3, 1, 4, 5, 2, all ready at the start. Order: P2, P5, P1, P3, P4. Waits 6, 0, 16, 18, 1. Average 8.2.

A low priority can wait forever. That is starvation. Ageing raises a process’s priority as it waits, so the number cannot sit at the bottom indefinitely.

Round robin

Each process gets a quantum q, often 10–100 ms, and then joins the back of the ready queue. With n processes, nobody waits more than (n−1)q before its next slice. A timer interrupt is what makes the slice end.

The lecture’s queue is bursts 24, 3 and 3, with q = 4.

P1 P2 P3 P1 P1 P1 P1 P1
0  4  7  10 14 18 22 26 30

P2 and P3 finish inside their first slice. Waits: P1 = 6, P2 = 4, P3 = 7. Average 17/3. Response is better than SJF’s habit of letting a long job run whole; turnaround of the long job is worse.

A huge q is FCFS. A tiny q spends the processor on context switches. The switch is microseconds and q is milliseconds, and q has to stay large beside the switch.

Remember: Priority scheduling can starve a low-priority job; ageing raises it as it waits. Round robin gives each job a quantum q, and nobody waits longer than (n−1)q. A huge q is FCFS.

More detail

In the priority example the Gantt ends at time 19: P2 on 0–1, P5 on 1–6, P1 on 6–16, P3 on 16–18, P4 on 18–19. P4’s wait of 18 is “arrived at 0, first ran at 18”.

Round-robin waiting time for P1 is only the gap from 4 to 10. After t = 10 the other two have finished, so P1 runs to completion. It is easy to double-count that tail as waiting. It is running.

Source: Lecture 16, priority scheduling (average 8.2) and round robin with q = 4.

A queue for each kind of job

Multilevel queue: a job stays put

Split the ready queue. The lecture’s split is foreground (interactive) and background (batch). Each queue has its own algorithm: round robin in the foreground, FCFS in the background. A process is born into one queue and stays there.

Between queues, either the foreground has absolute priority (and the background can starve), or each queue gets a fraction of the CPU, such as 80% and 20%.

Feedback: a job can fall

  • Q0: round robin, quantum 8 ms. New jobs enter here.
  • Q1: round robin, quantum 16 ms. A job that does not finish in Q0 drops here.
  • Q2: FCFS. A job that does not finish in Q1 drops here.

A short interactive job never leaves Q0. A CPU-bound job sinks. Ageing can be implemented by promoting a job that has waited, which is the same idea as in priority scheduling. Windows, the lecture notes, is a priority-driven preemptive scheduler with 32 levels (0 to 31) and an idle process for when nobody is runnable.

Remember: A multilevel queue keeps a job in one queue. A feedback queue lets it fall: in the lecture, RR for 8 ms, then RR for 16 ms, then FCFS.

More detail

The point of feedback is that the scheduler learns the burst without being told it. A job that keeps using its quantum is, empirically, the long job SJF would have run later. Dropping it is an approximate SJF that does not need the formula.

Draw the three queues as a staircase before you memorise the milliseconds. The numbers 8 and 16 are the lecture’s; the shape (short quantum, longer quantum, then a batch queue) is the idea.

Source: Lecture 16, multilevel queue, multilevel feedback queue, Windows scheduling.
