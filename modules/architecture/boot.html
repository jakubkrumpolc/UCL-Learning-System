Part 5 · Boot

Three residents of memory, in order

Power on. The CPU runs firmware from ROM or flash: BIOS or UEFI.

That firmware copies a bootloader, and the bootloader copies the operating system into RAM and jumps to it.

The operating system copies a user program into RAM and jumps to that.

Nothing in the user program runs until those two copies have happened. The disk holds the operating system; RAM is where the CPU executes it. Firmware is the program that is there before either.

Why there is a chain at all

The first code has to live in non-volatile memory, because RAM is empty at power-on. It is deliberately small. Its job is to find a larger program, on a disk, a USB stick or the network, and to hand over.

The lectures draw this on the same von Neumann picture as Part 1: CPU, RAM, and a disk, with the firmware chip off to the side. Each stage adds one more program to RAM.

An executable file on disk is not yet a running program. Lecture 11’s closing pictures are a compiled image being copied into memory, which is the last arrow of the chain.

Remember: Firmware runs first, from ROM or flash. It loads an operating system into RAM. The operating system loads your program.

More detail

“Bootstrap” is the name for a program that loads the next program. The chain can be more than two links: a tiny first loader whose only knowledge is the disk address and the length of a second loader.

Lecture 12 lists the loaders you will actually meet: GRUB (choose among operating systems), NTLDR (older Windows NT), LILO (Linux, from a disk), and a network boot such as PXE from the network card.

Source: Lecture 11, the three-stage boot diagram; Lecture 12, “Computer Startup”.

Part 5 · Boot

BIOS: the original firmware

What it does, in order

  • Starts as soon as the machine has power. The code lives in a chip and is copied into RAM to run.
  • Reads settings from battery-backed CMOS: the clock, and the order of devices to try.
  • Initialises the CPU, memory, keyboard, video and the disks. Cards such as a graphics card may run a BIOS of their own.
  • Installs interrupt handlers, building the interrupt vector table.
  • Runs POST, the power-on self-test, including a read and write of RAM.
  • Searches the boot devices for a Master Boot Record. The MBR’s code is the bootloader. BIOS loads it and jumps to it.

Where a boot sector might be

The lecture’s list is a hard drive, an SSD, a floppy, an optical disc, a USB stick, or a network card. The CMOS setting chooses the order they are tried. The first one with a usable MBR wins.

BIOS dates from CP/M in 1975. It is a small operating system whose whole career is the few seconds before a real one starts. You reach its setup screen with a key pressed during those seconds.

Remember: BIOS reads CMOS, initialises the hardware, runs POST, finds a Master Boot Record, and jumps to that bootloader.

More detail

The MBR is both a partition table and a tiny program. It is too small to be the operating system. It knows how to load the next, larger, loader. Lecture 13 describes GRUB in that second slot: it can pick a kernel, a disk and kernel options.

Interrupt handlers installed here are how devices will later get the CPU’s attention. Part 6 defines an interrupt properly. The boot lecture’s point is that the table must exist before the operating system is even loaded.

Source: Lecture 11, “The BIOS”, “What happens after turning on a computer”, “Bootstrapping under BIOS”.

Part 5 · Boot

UEFI does the same job with fewer limits

The modern firmware

  • Replaces legacy BIOS. Developed by Intel, standardised by the UEFI Forum, stored in flash on the board.
  • Settings live in NVRAM, flash that keeps its contents, rather than in a battery-backed CMOS chip.
  • Can draw a graphical setup screen and take a mouse. Secure Boot checks the operating system before it is allowed to start.
  • Understands GPT partition tables, so disks larger than 2 TB are ordinary boot disks.
  • Loads its own drivers, builds tables the operating system will read (ACPI, SMBIOS), runs POST, then hands over to a bootloader such as bootx64.efi on the EFI system partition.

The six steps, beside BIOS

UEFI firmware starts

Settings come from NVRAM

Devices are initialised

POST runs

Bootable devices are scanned

A .efi bootloader is started

You still enter setup with a key during startup (often F2 or Delete). The menus add Secure Boot, diagnostics, and power settings to the old boot-order list.

Remember: UEFI is firmware in flash. It boots large GPT disks, can check the OS before running it, and starts a .efi loader rather than a 512-byte MBR.

More detail

Secure Boot is a signature check, not a second operating system. If the check fails, the hand-off does not happen. That is the lecture’s “verifies OS integrity before loading”.

The CPU still begins at a fixed place in non-volatile memory. What changed is the program stored there, and how much hardware it knows how to describe to the kernel.

Source: Lecture 11, “UEFI”, the essential steps, and configuring UEFI.

What actually changed, and what did not

Stored inROM or flash chipFlash on the board
SettingsBattery-backed CMOSNVRAM

Boot recordMaster Boot RecordEFI system partition, GPT
Disk sizeAwkward past 2 TBLarge disks are normal
Device setupOption ROMs and an interrupt tableUEFI drivers and ACPI tables

The hand-off is the same shape

Both end by jumping to a bootloader that is now in RAM. The bootloader’s job is the kernel. When the kernel is running, firmware is out of the way, and the next lecture’s subject has started: the program that sits between you and the hardware.

Lecture 13’s version of the last step is worth pairing with this one. Execution starts at a fixed address. A small loader in firmware pulls in a second loader from a known disk block. GRUB, in that second slot, chooses which kernel. Then the kernel runs.

Remember: BIOS and UEFI both end by jumping to a bootloader in RAM. They differ in where settings live, how the disk is partitioned, and whether the operating system is checked first.

More detail

If a machine offers a “legacy BIOS” mode, it is emulating the older path, MBR included, so an old disk can still boot. The lectures treat the two as alternative firmware, not as two operating systems.

The next part starts from the sentence the boot lecture ends on: once the kernel is in memory, what is it for?

Source: Lecture 11, “Differences between BIOS and UEFI”, the summary; Lecture 13, “System Boot”.
