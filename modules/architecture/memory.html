Addresses, pages, and the disk arm

The address a program names is not the address the RAM chip sees. Virtual memory pages the difference, and the disk that backs those pages has a scheduling problem of its own.

Part 8 · Memory

The program’s address is not the chip’s

Logical, physical, and when they are tied

A logical (virtual) address is what the CPU generates. A physical address is what the memory unit sees. Binding them can happen at three times.

  • Compile time, if the load address is already known. Move the program and you must recompile.
  • Load time, if the compiler emitted relocatable code and the final address is chosen as the program is loaded.
  • Execution time, if the process can be moved after it has started. This is the usual case, and it needs hardware.

A pair of base and limit registers mark the legal range. Every user-mode access, including the program counter, is checked against them.

The MMU adds the relocation

The memory-management unit maps virtual to physical as the reference happens. The simplest map adds a relocation register (the base) to every address the process generates. The process only ever sees logical addresses. The chip only ever sees physical ones.

Registers are one cycle. A cache sits in front of main memory. Main memory is many cycles and will stall the CPU on a miss. Protection is not optional: a process that can forge a physical address can read its neighbour.

Remember: The CPU generates logical addresses. The MMU turns them into physical ones, in the simple scheme by adding a relocation register. Binding at run time is what makes that possible.

More detail

User programs are typically loaded above the operating system, which sits in low memory with the interrupt vector. The relocation register is what lets the program be written as if it started at address 0.

The check is base ≤ address < base + limit. Failing it is a trap, not a wrapped read. That is the hardware half of the dual-mode story in Part 6.

Source: Lecture 17, logical and physical addresses, base and limit, binding, the MMU.

Part 8 · Memory

Holes, three ways to pick one

Contiguous allocation

Early schemes give each process one block. Memory starts as one hole. A new process takes a piece; an exit frees one; adjacent free pieces merge.

PolicyChoosesCost
First fitthe first hole that is big enoughstops at the first success
Best fitthe smallest hole that is big enoughsearches the whole list, leaves the smallest leftover
Worst fitthe largest holesearches the whole list, leaves the largest leftover

First fit and best fit both beat worst fit on speed and on how much memory is left usable.

Two kinds of waste

External fragmentation: the free bytes would satisfy the request, but they are not in one piece. The lecture’s rule of thumb is that N allocated blocks leave about 0.5 N blocks lost this way, so roughly a third of memory cannot be used.

Compaction slides processes together until the free space is one block. It is only legal if addresses can be rebound at run time, because every process moves.

Internal fragmentation: the block handed out is larger than the request, and the slack inside it is wasted. Compaction does not recover that. It was never free.

Remember: First fit takes the first hole that fits. Best fit takes the smallest. Worst fit takes the largest. External fragmentation is free memory in the wrong shape. Internal fragmentation is waste inside an allocation.

More detail

Variable partitions, sized to each process, limit how many processes fit (the degree of multiprogramming) by how the holes fall, not by a fixed number of slots.

Non-contiguous allocation is the way out: a process may own several blocks that are not neighbours. Segmentation and paging are the two schemes that follow.

Source: Lecture 17, contiguous allocation, first/best/worst fit, fragmentation, compaction.

Part 8 · Memory

Segments follow the program; pages do not

Segmentation

A program is already a collection of segments: code, a procedure, globals, the stack, an array. A logical address is a pair <segment, offset>. The segment table holds a base and a limit for each. The hardware checks the offset against the limit and adds the base.

This matches the programmer’s view, and it suffers external fragmentation, because segments are different lengths.

Paging

Physical memory is cut into fixed frames. Logical memory is cut into pages of the same size. A logical address is <page, offset>. For a logical space of 2m bytes and pages of 2n bytes, the top m−n bits are the page number and the low n bits are the offset. The page table turns a page number into a frame number. The offset is copied across.

The lecture’s tiny machine: 32 bytes of RAM, pages of 4 bytes, so n = 2 and a 16-byte logical space has m = 4. The pair <0, 0> lands at physical address 20, which means page 0 lives in the frame that starts at 20.

A process of 72,766 bytes with 2,048-byte pages needs 35 pages plus 1,086 bytes. The last frame wastes 2,048 − 1,086 = 962 bytes. That is internal fragmentation. The worst case is a whole frame minus one byte. Smaller pages waste less and need a bigger page table. Solaris, the lecture notes, supports both 8 KB and 4 MB pages.

Remember: A segment address is <segment, offset> and matches the program. A page address is <page, offset> into equal frames. Segmentation fragments the gaps. Paging fragments the last frame.

More detail

Modern general-purpose systems (Windows, Linux, macOS) page, usually at 4 KB, with an MMU and a TLB that caches recent translations. Segmentation as a memory-allocation scheme is now rare; it survives in older x86 stories. The lecture’s comparison table is: paging does not keep the user’s view of “the stack is one region”, and it does not need a search for a hole of the right shape, because any free frame will do.

The page table itself occupies memory. That is the argument against making pages tiny to win the 962-byte waste.

Source: Lecture 17, segmentation, paging, the 32-byte example, internal fragmentation of 962 bytes, the comparison table.

Part 8 · Memory

Bring a page in when it is touched

Virtual memory

Most of a program is rarely used: error paths, unusual routines, large structures. Virtual memory lets a process run with only some of its pages in RAM, the rest backed by disk. The logical address space can be larger than physical memory. More processes fit. Less I/O is done up front.

Demand paging is the policy “do not load a page until a reference needs it”. Each page-table entry has a valid/invalid bit: valid means resident. Invalid on a reference is a page fault. Starting with no pages loaded at all is pure demand paging.

Copy-on-write lets a parent and child share pages. The copy is made only when one of them writes. Forks get cheaper, and so do the faults.

The fault, step by step

  • The reference traps. The kernel checks a second table: a truly illegal address aborts the process; a missing page does not.
  • Find a free frame. If there is none, choose a victim (next section). If the victim is dirty, write it out first.
  • Read the wanted page into the frame. Point the page table at it and set the bit to valid.
  • Restart the instruction that faulted. It must be restartable, because one instruction can touch several pages (fetch it, read two operands, write a result) and fault more than once.

Swapping an entire process out, and back in, is the coarser version. The lecture notes it is usually disabled until memory pressure crosses a threshold, then disabled again. Transfer time dominates, and it grows with the amount moved.

Remember: Virtual memory runs a process with only some pages resident. A valid bit says the page is in RAM. A page fault loads it and restarts the instruction.

More detail

Locality is why this is cheap enough. The pages a process touches next are usually near the pages it has just touched, so the fault rate falls after the first touches. The first touch of every page, under pure demand paging, faults. That is expected, not a bug.

A modify (dirty) bit saves writes: a victim that still matches its disk copy need not be written back. The lecture folds that into the replacement steps.

Source: Lecture 18, virtual memory, demand paging, valid bit, page-fault steps, copy-on-write.

Part 8 · Memory

FIFO, OPT, and LRU on one string

The string, and the three counts

The lecture evaluates algorithms on

7 0 1 2 0 3 0 4 2 3 0 3 0 3 2 1 2 0 1 7 0 1

with 3 frames. Repeated references to a page that is already resident are hits. The counts are FIFO 15, OPT 9, LRU 12.

  • FIFO evicts the page that has been resident longest. A queue is enough.
  • OPT evicts the page whose next use is furthest away. It needs the future, so it is a yardstick, not a policy.
  • LRU evicts the page unused for the longest time. It needs a counter or a stack of page numbers. It does not suffer Belady’s anomaly. OPT does not either.

15 faults. Belady’s anomaly: on 1 2 3 4 1 2 5 1 2 3 4 5, FIFO with 3 frames faults 9 times and with 4 frames faults 10 times. More frames, more faults. LRU and OPT do not do this.

How OPT picks

On a fault, look forward from the next reference. The resident page that appears latest, or never, leaves. One walk of the string:

  • 7, 0, 1 fill the frames (3 faults).
  • 2 evicts 7, the one used furthest ahead.
  • 3 evicts 1. 4 evicts 0. The later 0 evicts 4.
  • 1 evicts 3, which is never used again. 7 evicts 2, which is never used again.

That is 9 faults, and it is the minimum for this string and these three frames. Any real policy is judged by how close it gets.

Who uses what

Linux demand-pages and replaces with a global policy in the LRU family. macOS ages pages: a counter, periodically updated, stands in for an exact stack, so a frequently used page keeps a high count. An exact LRU stack is six pointer updates per reference; the approximation is the one that ships.

A counter implementation of exact LRU stamps each page with the clock on use and, at a fault, scans for the smallest stamp. A stack implementation moves the used page to the top and evicts the bottom, with no scan and a more expensive update.

Remember: FIFO evicts the oldest page and can fault more with more frames: Belady’s anomaly. OPT evicts the page used furthest ahead. LRU evicts the page unused for longest. On the lecture’s string, the counts are 15, 9 and 12.

More detail

Read the FIFO table a row at a time and cover the next row. The queue never reorders on a hit. Only a fault of a full memory pops the left-hand page. If your fifteenth fault is the final 1, and the frames end as 7 0 1, you have the lecture’s trace.

OPT’s “never used again” beats “used in a hundred steps”. When two pages tie, the yardstick only cares that you evict one of the furthest; the fault count on this string does not depend on the tie-break.

Source: Lecture 18, the reference string, FIFO and Belady’s anomaly, OPT (9 faults), LRU (12 faults).

Part 8 · Memory

Seek, spin, then transfer

What a request costs

A moving-head disk stores data on platters. A request waits for the arm to reach the right cylinder (seek time), then for the sector to rotate under the head (rotational latency). Those two together are the positioning time. The transfer rate is how fast bytes then move. The lecture’s desktop figures are roughly 3–12 ms seek (9 ms typical), 5,400 to 15,000 rpm, a theoretical transfer around 230 MB/s and a real one nearer 120 MB/s.

The drive is addressed as a one-dimensional array of logical blocks. Block 0 is the first sector of the first track on the outermost cylinder, and the numbering walks inward. A constant angular velocity means the outer tracks could hold more, but this mapping keeps the arithmetic simple, apart from bad sectors.

Host and device each have a controller. The lecture’s attachment list includes SATA, SCSI, USB, Fibre Channel and FireWire. Magnetic tape still exists, and it is sequential: cheap per byte, and the wrong device if you need a single block in the middle.

Remember: A disk access is seek, then rotational latency, then transfer. An SSD has no arm and no platter, so it has neither of the first two. Seek time grows with how far the arm moves.

More detail

The first commercial drive, the lecture’s history slide, is the IBM 350 on the RAMAC machine in 1956: 50 platters, 24 inches across, about 5 million characters, access under a second. The shape (platters, tracks, an arm) is what the scheduling algorithms are still about.

Bandwidth, for the scheduling lecture, is bytes transferred divided by the time from the first request to the end of the last. Reordering the queue changes that number even when the bytes do not.

Source: Lecture 19, disk structure, HDD versus SSD, logical block mapping.

Part 8 · Memory

The arm should not zig-zag

The lecture’s queue

Cylinders 0–199. The head is at 53. The queue, in arrival order, is 98, 183, 37, 122, 14, 124, 65, 67. Scheduling only matters when the disk is busy enough to have a queue.

FCFS serves that order. The head travels 640 cylinders, which is the total on the slide:

45 + 85 + 146 + 85 + 108 + 110 + 59 + 2 = 640

SSTF always takes the closest request. From 53 the path is 53 → 65 → 67 → 37 → 14 → 98 → 122 → 124 → 183. The distances are 12, 2, 30, 23, 84, 24, 2, 59, and the total is 236. Like SJF, it can starve a request that is repeatedly just a bit further away than a new arrival.

Sweep, instead of chasing

  • SCAN (the elevator) travels in one direction to the end, then reverses. Toward cylinder 0 from 53: 53 → 37 → 14 → 0 → 65 → 67 → 98 → 122 → 124 → 183. Total 236. Toward 199, going all the way to the end before reversing, the same queue costs more, because 199 and then the long jump back to 37 are both movement. State the direction when you give a number.
  • LOOK is SCAN that turns around at the last request, not at the end of the disk.
  • C-SCAN services in one direction only. At the end it returns to the start without serving on the way back, so the cylinders are a circle and the wait is more even. Requests piled at the far end no longer wait for a full return trip of service.
  • C-LOOK is that idea, turning at the last request rather than the last cylinder.

SSTF is a reasonable default and beats FCFS. SCAN and C-SCAN behave better under a heavy load because they starve less. The lecture’s advice is to keep the algorithm in its own module, so it can be replaced. The numbers above are this queue and a stated direction; a question that reverses the direction wants a new sum, not a memorised 236.

Remember: FCFS serves the queue in order (640 on the lecture’s queue). SSTF takes the closest request (236) and can starve. SCAN sweeps like an elevator. C-SCAN returns without serving, so the wait is fairer. LOOK turns at the last request, not at the rim.

More detail

Write the path, then add absolute differences. For FCFS the first step is |98−53| = 45 and the last is |67−65| = 2. For SSTF, after 65 the next closest is 67 (distance 2), not 98. After 67, 37 is closer than 98 (30 against 31). Missing that comparison is the usual way to get a wrong SSTF total.

Seek time is approximated by seek distance. Rotational latency is ignored by all of these algorithms. They are arm schedulers, not full models of the drive.

Source: Lecture 19, FCFS total of 640 on this queue, SSTF, SCAN, C-SCAN, C-LOOK.
